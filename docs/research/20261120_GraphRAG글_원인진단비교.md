# Microsoft GraphRAG 글이 우리 원인 진단에 더할 것이 있는지, 우리 방식과 나란히 놓아 본다 (2026-11-20)

- 왜: 사용자가 Microsoft Research 글 "The evolution of GraphRAG: Advancing systems and evaluation together"([원문](https://www.microsoft.com/en-us/research/story/the-evolution-of-graphrag-advancing-systems-and-evaluation-together/))을 두고 "우리가 필요했던 원인 진단? 부분에 유용하지 않을까" 물었다. Fable 5.2 high 판단에 맡기기 전에 사실 자료를 먼저 만든다.
- 어떻게: 주 세션(Claude Opus 5.5)이 글 본문을 내장 브라우저로 끝까지 읽었다(Table 1은 그림이라 못 읽음). 우리 기록은 HISTORY [324]·[325]·[467]·[490]·[499]·[532]·[533]과 05 결과 줄, `docs/research/20261119_RAG15개념_적용검토.md`(566줄 가운데 한눈에 표·⑪·⑭·⑮ 절), `.claude/tools/needed_count.py`(107줄 전부), `needed_20261118.json`의 다섯 차례를 직접 읽었다. 초안을 advisor가 점검해 세 곳을 고쳤다(맨 아래). 돈 0, 하위 에이전트 0.

## "원인 진단"을 두 가지로 읽는다

- **읽기 A(제품 쪽): 제품이 증상에서 원인 기능을 짚어 내는가.** [533]의 사용자 말 "결국 핵심은 원인 진단 -> 답 모델이 얼마나 판단할 거리가 간결하고 핵심적이냐"는 05 문맥에서 나왔다. 05는 필요 조각과 원인 줄을 손으로 넣어 준 시험이다([499]). 그래서 이 말은 원인을 짚는 단계를 제품이 스스로 해내야 한다는 뜻일 가능성이 크다(주 세션의 읽기, 사용자에게 확인하지 않음).
- **읽기 B(평가 쪽): 틀린 답이 어느 단계 탓인지 가르기.** [324]의 ① 검색이 못 찾음 ② 받고도 안 씀 ③ 핵심이 설명서보다 넓음.
- 주 세션이 앞서 사용자에게 한 답은 읽기 B만 봤다.

## 글이 말하는 것 (글의 말, 우리가 잰 것 아님)

| 이름 | 하는 일 |
|---|---|
| GraphRAG Zero | 임베딩의 거리만으로 그래프를 만들어, 관련 있고 자료 전체를 대표하는 근거를 모은다. 색인 때 LLM 호출 0번, 실시간 설정에서는 검색 때도 0번. 근거 준비 평균 0.93초(질문 임베딩 포함, 답 생성 제외) |
| 질문 종류 | local, linked multi-hop(여러 사실을 이어야 하는 질문), global. GraphRAG Zero 시험은 multi-hop과 global 반반(200문) |
| 검증 문장(assertion) | 질문마다 답에 들어가야 할 사실 문장을 자료에서 LLM이 미리 만든다 |
| 답 쪽 채점 | 생성된 답이 검증 문장을 몇 개 담았나. 글이 밝힌 숫자는 **global 질문만** vector RAG 53.4% → GraphRAG Zero 57.4%(조각 50개 예산) |
| 근거 쪽 채점 | 답과 상관없이, 검색된 조각마다 LLM이 검증 문장을 온전히 받침 1 / 일부 0.5 / 없음 0으로 매긴다. 검증 문장마다 가장 좋은 조각 점수를 쓰고 평균. 겹친 근거는 점수가 안 늘고 빠진 사실을 받치면 는다 |
| 정밀도·주제 묶음 재현율 | GraphRAG Zero는 묶음 재현율이 높고, vector RAG는 조각 정밀도가 높았다 |
| 판정 다시 쓰기 | 자료·질문·검증 문장·채점 절차를 고정하면 (검증 문장, 조각) 판정을 저장해 두고 새 판에서는 처음 보는 조각만 채점한다 |

글의 조건: 질문·검증 문장·채점 모두 LLM이 만든 것이고, 자료는 팟캐스트 대본과 뉴스다. 글 스스로 이 값이 제품 성능을 잰 것은 아니라고 적었다.

## 읽기 A: 원인을 짚는 검색에 GraphRAG Zero가 닿는가

우리 기록이 말하는 것:
- 검색이 못 가져오는 주된 까닭은 검색어에 원인 기능 이름이 안 들어가는 것이다. [490]: 멀던 필요 묶음 27개가 원인 기능 이름을 넣은 모범 검색어로는 8위 안 14·9-30위 10·31-50위 2·50위 밖 1.
- [325] 결과 3: "질문은 증상만 말하고 검색어 모델은 질문과 최근 조작만 봐서 다른 기능을 겨눈다. 원인은 답 모델에 가는 줄에는 있다." 그래서 계획의 후보는 G-1(바뀐 설정 줄을 질문 바꾸기에 줌)·G-2(흔한 원인 규칙)다([491]·[492]).
- RAG15 검토 ⑪은 GraphRAG를 "맞지 않음"으로 닫았다. 근거는 원 논문(말뭉치 전체 요약 질문을 겨눔)이었고, LLM 호출 없는 GraphRAG Zero는 따로 보지 않았다.

맞대 보면(추측, 잰 것 없음):
- 증상 → 원인 기능은 글의 linked multi-hop과 닮았다. 증상 조각 옆에 원인 조각이 그래프로 이어져 있으면 검색어에 원인 이름이 없어도 닿을 수 있다. 다만 이것은 우리 설명서에서 두 조각이 임베딩으로 가까워야 성립하고, [490]의 "멀던" 묶음은 바로 임베딩으로 먼 경우다.
- 걸림돌: 글 본문에 multi-hop 숫자는 따로 없다(global만). 조각 예산은 50개 대 우리 8개다. 근거 준비 0.93초는 첫 글자 2초 목표의 절반에 가깝다. 우리 임베딩 끝이 이미 1.21초다([532]).
- 비교 대상: G-1·G-2는 검색어를 고치는 쪽이라 기다림이 거의 늘지 않는다. GraphRAG Zero 꼴은 색인을 다시 만들어야 하고, 오픈소스 구현이 있는지는 확인하지 않았다(글에는 Foundry IQ·Repo Mind Light 제품만 나옴).

## 읽기 B: 평가 방법을 우리 방식과 나란히

| 글의 방법 | 우리에게 있는 것 | 같은 점 | 다른 점 |
|---|---|---|---|
| 검증 문장 | 문항마다 정답 핵심과 필요 묶음 목록 `needed_20261118.json`(54차례, 필요 묶음 82개, 빈 차례 6개, [467]) | 질문마다 꼭 있어야 할 것을 미리 고정한다 | 글은 사실 문장 단위, 우리는 설명서 조각 주소 단위. 묶음 하나에 대안 주소가 여럿 들 수 있다 |
| 근거 쪽 채점 0/0.5/1 | `needed_count.py`: 등록된 대안 주소 가운데 하나의 조각 글 전체가 답 모델에 보낸 글 안에 그대로 있으면 그 묶음을 채운 것으로 센다(코드 6·38-46줄) | 답과 따로 근거가 왔나를 재서 ① 검색 탓과 ② 답 탓을 가른다 | 등록하지 않은 쪽이 같은 사실을 받쳐도 못 센다. 부분 점수가 없다 |
| 답 쪽 채점 | `answer-grader`의 맞음·부분·틀림, 엄격 채점, "답의 문장마다 출처를 찾는다"(`grading.md:49`) | 핵심을 다 담았나를 본다 | 비율이 아니라 3단 판정이고, 출처에 작업 상태·연습 과정 글이 들어간다 |
| 검색 정밀도 | 재지 않음. RAG15 검토 ⑮: 필요 묶음이 문항당 약 1.7개라 "precision@8의 상한이 약 0.2" | | 글도 정밀도만으로는 방향을 못 정한다고 했다 |
| 판정 다시 쓰기 | 찾지 못함(HISTORY·`docs/experiment.md`에서 `캐시`·`다시 쓰`·`재사용`으로 찾음) | 고정한 자로 판을 견주는 생각은 같다 | 우리 비용은 대부분 답 채점이라 아끼는 몫이 작을 것이다(추측) |

우리 기록이 이미 답한 것:
- **[325]의 미등록 5문항은 지금 목록에서 메워졌다.** [325]가 "설명서 다른 곳에 있고 정답 위치로 미등록"이라 한 Q11·Q18-2·Q25·Q27·Q38은 `needed_20261118.json`에 그 조각이 들어 있다(예: Q11 `show_hide.html#show-hide`, Q27 `selecting/linked.html#linked`, Q38 `cycles/baking.html#render-baking`). 지금 목록에 다른 빈틈이 몇 개인지는 세지 않았다.
- **근거를 넣어 줘도 맞음은 조금만 오른다.** 05(5회 중 3회 이상 맞음, 48문항 짝): none_조각만 대 04 지금 7:4(단측 p 0.274). 생각 켜기 medium 대 none은 11:2(p 0.011), 바로잡은 뒤 11:3(p 0.029).
- **근거를 넣어 준 조건에서 남은 실패는 대부분 근거 밖의 까닭이다.** [533] Fable 문제 정의의 100답은 05 medium 판(필요 조각 + 원인 줄을 넣고 생각 medium)이다. 그 조건에서 맞음이 아닌 100답 가운데 원인·전제를 못 잡은 것이 주된 까닭인 답은 9이고, 나머지는 화면 글자·메뉴 자리 20, 받은 글이 5.2와 어긋남 18, "없어요" 다루기 18, 덧붙인 말 14, 단계 빠짐 14, 상태 읽기 5, 호출 실패 2다. 근거 부족은 이 조건에서 일부러 없앤 것이라, 제품 조건의 실패 비율로 읽으면 안 된다.
- **LLM이 매기는 recall은 들이지 않기로 했었다.** RAG15 검토 ⑮: "RAGAS의 LLM판 recall로 바꿀 이유 없음".

## 글에서 새로 볼 만한 것 (판단 전)

1. **읽기 A: 원인 짚기에 그래프로 이웃 조각을 따라가는 검색.** 위 걸림돌(임베딩으로 먼 묶음, 2초, 조각 예산, 구현 유무) 때문에 G-1·G-2보다 앞설 근거는 지금 없다.
2. **읽기 B: 근거 쪽 LLM 채점(0/0.5/1).** 미등록 5문항이 메워져 처음 기대한 쓸모(주소 목록 빈틈 찾기)의 근거는 약해졌다. 남는 쓸모는 부분 점수, 그리고 사용자가 말한 "판단할 거리가 간결하고 핵심적이냐"를 덮음과 정밀도로 함께 보는 것이다. 다만 정밀도에는 상한 0.2 문제가 있고, LLM "관련 있음" 판정을 쓰면 필요 목록과 기준이 둘이 된다(RAG15 ⑮).
3. **판정 다시 쓰기.** 2를 들일 때만 의미가 있다.

## Fable에 맡긴다면 물을 것 (하나)

"이 글에서 7번 전체 계획의 원인 진단(제품이 원인을 짚는 일, 그리고 틀린 까닭을 가르는 평가)에 넣을 가치가 있는 것이 있나. 있다면 무엇이고, 지금 후보 G-1·G-2보다 앞서나 뒤서나." 줄 자료: 이 파일, 글 원문, RAG15 검토 ⑪·⑮ 절, [325]·[490]·[533] 원문, 7번 계획 문서. 기대 답은 주지 않는다.

## 확인하지 못한 것

- 글의 Table 1(지표 정의 표)은 그림이라 못 읽었다. BenchmarkQED·GraphRAG Zero 소스나 공개 여부는 보지 않았다.
- 우리 설명서에서 증상 조각과 원인 조각이 임베딩 그래프로 이어지는지는 재지 않았다.
- 지금 필요 목록에 다른 빈틈이 몇 칸인지 세지 않았다.
- 사용자의 "원인 진단"이 읽기 A인지 사용자에게 확인하지 않았다.

## advisor 점검으로 고친 것 (초안 → 이 판)

- 초안은 읽기 B만 다뤘다 → 읽기 A 절을 더하고 Fable 물음을 넓혔다.
