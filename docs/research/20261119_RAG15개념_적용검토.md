## ① Chunking(청킹)

1. 한 줄: 긴 문서를 검색·임베딩에 쓸 조각으로 자르는 일(어디서 어떤 크기로 자를지).
2. 1차 자료
   - LlamaIndex 계층 파서 `HierarchicalNodeParser` 기본 크기는 [2048, 512, 128], 겹침 20 ([소스](https://raw.githubusercontent.com/run-llama/llama_index/main/llama-index-core/llama_index/core/node_parser/relational/hierarchical.py)). 즉 라이브러리 기본값은 토큰 단위로 큰 구역을 작은 조각의 부모로 둔다.
   - 검색 단위(granularity) 자체가 성능을 좌우한다: Dense X Retrieval은 문단보다 더 작은 "명제" 단위로 색인하면 문단 단위보다 검색이 "크게 앞섰다"고 보고(초록, 수치는 초록에 없음) ([논문](https://arxiv.org/abs/2312.06648)).
   - 조각에 문서 맥락을 붙이는 방법: Anthropic Contextual Retrieval은 조각마다 50-100토큰 맥락을 붙여 임베딩해 상위 20개 놓침률 5.7% → 3.7%(35% 감소), BM25 합치기까지 2.9%, 리랭크까지 1.9%. 한 번 만드는 비용 약 $1.02 / 문서 100만 토큰(800토큰 조각 기준). 조건: 그 회사의 자체 데이터 모음들 평균, 조각 크기 800토큰 ([글](https://www.anthropic.com/news/contextual-retrieval)). 지식이 20만 토큰 미만이면 통째로 프롬프트에 넣으라고도 함(우리 설명서는 훨씬 큼).
3. 이 프로젝트에서 이미 한 것
   - 설명서 HTML의 소제목(`<section>`) 하나 = 청크 하나, 400낱말 넘으면 옵션 경계에서 고르게 나눔(`manual_chunks.py:20`, `MAX_WORDS = 400`). HISTORY [6] 사용자 "법조문 처럼 메타데이터상 이런걸 구분할 데이터를 넣어주는게 맞지 않을까요?" → 합치지 않고 위계 메타데이터. [33] 범주·옵션 경로를 뒤 조각 경로에 붙임.
   - 청크 글 앞에 "쪽 제목 > 소제목 (> 옵션)" 경로를 붙여 임베딩·답에 씀(`Chunk.text`, `manual_chunks.py:111-113`) = 값싼 맥락 붙이기가 이미 있음.
   - 그림·영상만 있는 소제목은 앞 청크 예시로 붙임([32]), 다른 키맵 쪽 9개 빼기([471], `manual_chunks.py:37`).
   - 청크 크기를 바꿔 견준 기록은 못 찾음(HISTORY·experiment.md에서 "청크 크기", "MAX_WORDS", "400단어" grep: 구현 기록뿐, 크기 비교 실험 없음).
   - 맥락 붙이기 쪽: 5.7→3.7% 수치는 후보 판정 문서가 "아. 쪽 단위로 넓혀 읽기, 조각에 쪽 맥락 붙이기"로 따져 "약함"으로 닫음. 이유: 몫이 Q40 한 문항(2답, 회차당 0.7)이고 짧은 조각엔 이미 형제를 붙인다(`3_후보별비판.md` "아" 절, `4_최종판정.md` 125줄, Git 밖).
4. 맞대기: 기록상 실패 모양은 "검색어가 기능 이름을 못 짚음"이 주된 몫이고 조각 쪽 몫은 작다(조각만 넣어도 +3~4문항, 불확실). 48%가 50낱말 미만이라 조각이 작은 것은 사실이나, 작은 조각은 이미 형제·자식을 붙여 보강한다. 조각 앞 경로 붙이기도 이미 있다. 청킹을 새로 건드릴 자리는 좁다. 다만 5.7→3.7%류 효과를 우리 조각으로 재 본 적은 없다(요점: 확인 안 함).
5. 판단: **이미 씀(소제목 단위 + 경로 머리글 + 짧은 조각 보강)**. 크기 비교·LLM 맥락 붙이기는 **해 볼 후보지만 우선순위 낮음**. 잰다면 청크 8,988개 × 맥락 한 줄 생성은 Haiku로 약 몇 달러(추측: 조각 평균 수십 낱말이라 입력 약 100만 토큰대), 재임베딩 약 $0.13([106] 실제 $0.126)과 재측정이 따로 든다. 확인한 사실: 위 3번 전부. 추측: 효과 크기, 비용.

## ② Embedding models(임베딩 모델)

1. 한 줄: 글을 숫자 벡터로 바꿔 "뜻이 가까운 글"을 찾게 하는 모델.
2. 1차 자료
   - OpenAI 공식 문서: text-embedding-3-small 1536차원 MTEB 62.3%, text-embedding-3-large 3072차원 64.6%, ada-002 61.0%, 입력 최대 8192토큰. `dimensions` 매개변수로 줄이면 개념 성질이 유지된다고 하고 줄인 뒤엔 정규화 필요. 벡터가 길이 1로 정규화돼 있어 코사인과 유클리드 순위가 같다 ([문서](https://developers.openai.com/api/docs/guides/embeddings)). 발표글의 MIRACL·"256차원 large가 ada-002를 앞섬" 수치는 페이지가 403이라 확인 못 함.

## ③ Vector database(벡터 DB, ANN 색인)

1. 한 줄: 벡터를 저장해 "가장 가까운 것"을 빨리 찾는 저장소. ANN(approximate nearest neighbor, 근사 최근접 이웃)은 정확히 다 비교하지 않고 그래프·묶음으로 거의 맞는 이웃을 빠르게 찾는 방식이다.
2. 1차 자료
   - HNSW 원 논문: 여러 층의 근접 그래프로 로그 규모의 검색 복잡도를 주장 ([논문](https://arxiv.org/abs/1603.09320)).
   - FAISS 공식 위키: IndexFlat은 정확한 전수 비교("모든 벡터를 차례로 비교"), HNSW는 근사. "M이 크면 정확하나 메모리 큼", HNSW는 벡터 제거 미지원. 어느 크기부터 HNSW가 낫다는 기준은 이 페이지에 없음 ([위키](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes)).
3. 이 프로젝트에서 이미 한 것
   - 쓰지 않기로 함: [106] 저장 방식 4안 중 "D 벡터 DB"를 권하지 않고 A numpy 파일을 고름. [117]에 근거 적음: "numpy 전수 비교는 Chroma HNSW보다 같거나 정확하고 … 전체 뜻 검색 중앙 0.008초". 지난 프로젝트(`rag_korea_history`, 803청크 Chroma)도 where는 시점 거르기에만 씀(같은 [117] 줄).
   - 코드: `AnswerEngine.search`가 `self._vectors @ 질문벡터`로 전수 내적(`answer_engine.py:491-494`). 8,988 × 3,072 float32.
   - 실측: 질문 하나 전체 비교·정렬 0.007초([106]), 검색 0.011-0.030초([127] 부근, `search_compare` 시간 기록). 전체 답 흐름이 2초 안팎인데 검색은 1% 미만.
4. 맞대기: 병목이 아님이 숫자로 확인됨. 근사 색인은 정확도를 더 잃을 수는 있어도 시간을 줄일 자리가 없다(0.01초 대 2초). 벡터 DB를 넣으면 의존 부품(Chroma 등)과 도우미 설치물이 늘어난다(추측: 제품 설치 부담).
5. 판단: **맞지 않음(전수 numpy가 이미 충분)**. 8,988개 규모에서 확인한 사실은 위 시간. 규모가 수십만 개로 커질 때만 다시 볼 일.

## ④ Metadata filtering(메타데이터 거르기)

1. 한 줄: 청크에 붙은 꼬리표(분야·쪽·종류 등)로 검색 후보를 미리 줄이는 것.
2. 1차 자료: 이번엔 라이브러리 소스·문서를 직접 읽지 못했다(LangChain 자기 질의 검색기·Qdrant·Chroma where 문서는 열어 보지 않음). 따라서 "필터가 실제 몇 퍼센트 오르내리나"는 1차 자료로 못 적는다. 일반론(후보를 먼저 거르면 속도·정확도가 오를 수도, 틀린 거르기가 정답을 지울 수도 있음)은 추측이다.
3. 이 프로젝트에서 이미 한 것
   - 청크 메타(field·group·위계·옵션·reference·ui_names)를 만들었고 `Chunk.field/group`이 있음(`manual_chunks.py:58-75`). 검색 거르기엔 안 쓰임 — [117] 사용자 "애초에 메타데이터를 만들어 놓고 안썼니?" → Claude "경로 붙이기·형제 넓히기·링크에 쓰고 검색 거르기에는 쓴 적 없다".
   - 그 직후 비교([117], large, 설명서 전체 8,997청크, 상위 6개): luna 바꾼 검색어 전체 72.5%(13) / 질문 분야만 62.5%(11) / 뺀 나머지 72.5%(13) / 초보자만 40%(7). 질문 그대로는 10%·15%·10%·10%. luna가 분야를 못 고른 문항 W6·W9·A1·A2, 뺄 분야는 거의 안 골라 "뺀 나머지"는 전체와 같음. Gemma도 같은 경향: "범위 거르기는 Gemma에서도 전체보다 낫지 않았다"([119]). 사용자 정한 목표: "분명하게 자유 질문 시 잘 찾아주는거도 목표"([118]) → 범위 거르기는 뺌.
   - 코드의 `area_of`(`answer_engine.py:67-72`)와 `REWRITE_PROMPT`의 areas·exclude 칸은 검색 거르기용이 아니라 지시문 습관용으로 남음("분야를 함께 고르게 한 이 지시가 더 잘 찾았다 86.7% 대 77.3%", 주석 `answer_engine.py:51-52`).
   - 지금의 "분야 고르기"(32분야, Haiku 1번)는 설명서 청크 거르기가 아니라 애드온이 읽은 설정 값 줄 묶음을 고르는 것(STRUCTURE 38-41줄, `setting_fields.py`). 이름이 같아 헷갈리기 쉽다.
   - 쪽 단위로 뺀 것(다른 키맵 쪽 [471])은 인덱스에서 영구 제외한 정적 거르기.
4. 맞대기: 기록의 실패는 "검색어가 기능을 못 짚음"이라 후보를 분야로 줄여도(분야를 틀리게 고르면 정답을 지움) 이득이 안 났다. 거르기는 0.01초 검색을 빠르게 할 일도 없다. 남은 가능성: 05 진단의 "9-30위에 남은 묶음"처럼 같은 분야 안 비슷한 쪽에 밀리는 경우엔 분야 거르기가 도울 수 없다(같은 분야). 반대로 [117]의 미러 질문에서 애니메이션·그리스 펜슬 쪽이 1-6위를 차지한 것은 다른 분야의 같은 이름이라 분야 거르기가 이론상 맞는 사례이나 실측 10→15%로 작았다(질문 그대로 조건).
5. 판단: **해 봤고 결과는 이랬다(전체 대비 같거나 낮음)**. 지금 상태는 "메타는 있고 거르기엔 안 씀". 더 한다면 "분야를 거르지 않고 점수에 가산(부스트)"하는 약한 형태가 후보지만 근거는 약함(추측). 새 호출 없이 저장된 상위 50개 순위로 다시 채점할 수 있어 돈 0(`search_compare`가 이미 지원, [117] 부근 구현 기록).

## ⑩ Small-to-big retrieval(작은 조각을 찾고 부모 구역을 보냄)

1. 한 줄: 작은 조각으로 정확하게 찾고, 모델에게는 그 조각이 속한 더 큰 구역(부모)을 넘겨 맥락을 채우는 방식.
2. 1차 자료
   - LangChain `ParentDocumentRetriever` 소스 docstring: 부모 분할기는 큰 조각, 자식 분할기(필수)는 임베딩해 저장하는 작은 조각이며 각 자식에 부모 ID를 달고, 검색은 자식에서 하고 부모 문서를 돌려준다 ([소스](https://raw.githubusercontent.com/langchain-ai/langchain/master/libs/langchain/langchain_classic/retrievers/parent_document_retriever.py)). 정량 효과는 이 소스에 없음.
   - LlamaIndex `AutoMergingRetriever`: 부모 아래 자식의 검색된 비율이 `simple_ratio_thresh`(기본 0.5)를 넘을 때만 자식을 빼고 부모를 넣고(예: 자식 4개 중 3개 이상), 이웃 사이 빈 노드를 채움. 부모 점수는 자식 점수 평균 ([소스](https://raw.githubusercontent.com/run-llama/llama_index/main/llama-index-core/llama_index/core/retrievers/auto_merging_retriever.py)). 계층 파서 기본 [2048, 512, 128]. 정량 효과는 소스에 없음. 원 논문 같은 정량 근거는 못 찾음(조사 4도 "부모 문서 방식은 정량 숫자가 없다" `3_후보별비판.md` 표 8행).
3. 이 프로젝트에서 이미 한 것(이미 쓰는 개념)
   - 코드: `_widened`(`answer_engine.py:391-414`). 찾은 청크가 `SHORT_WORDS=50`낱말 미만이면 아래 소제목(자식·손자, 설명서 차례)을 `MAX_WORDS=400`까지, 없으면 같은 부모의 형제 소제목을 가까운 순으로 붙여 넘김(`_descendants`·`_siblings`, 같은 파일 416-432). 먼저 볼 소제목은 붙이지 않음.
   - HISTORY [40] 2026-10-22: 사용자 "이건 가 방안이 맞음 근데 이러면 애초에 형제를 넘길 청크가 아니었던거 아닌가? 자식을 다 합쳐버리면 충분한거잖아?" → 자식 먼저, 없으면 형제. 사용자 "우리가 형제를 붙이는 목적은 청크가 짧은 경우 보완을 하기 위함이잖아". 쪽 첫머리 짧은 청크 916개 중 776개에도 쪽 앞 소제목이 붙게 됨. 짧은 청크 3,451개 중 235개가 자식이 진짜 내용인 꼴(Location Scouting 26단어 → Capturing Shots 210단어, 합 236단어).

   - 후보 비판 "아"에서 "쪽 단위 넓혀 읽기"를 "약함", 최종 판정은 "하지 않을 것"에 "쪽 넓혀 읽기" 포함(`docs/research/20261118_검색답_다시설계.md` "하지 않을 것" 절, `4_최종판정.md` 125줄). 이유: 몫이 Q40 1문항(회차당 0.7), 입력 약 1.3-2배(추측), 무관한 글이 늘면 "가운데 정보를 놓침"(조사 4), 해로운 글 유입 위험(Q17 꼴).

5. 판단: **해 볼 만한 후보(약함)**. 재는 법: 04 기록 위에서 Haiku none으로 "검색어 2-3개(한 가지는 하려는 일, 한 가지는 의심할 원인 후보 이름들)를 한 번에 JSON으로" 내게 하는 지시문 1개, 54 × 5회, 필요 조각 순위로만 판단, 호출 1번 유지(시간 +출력 토큰 비례, 이전 조사 기준). 돈 어림 $0.3-0.5(옛 [294] 54×3×3조건 규모 $0.45에서 환산). 합치기(RRF)에서 밀릴 위험은 [300] 선례 있음 → 순위 합치기 방식을 먼저 정해야 함.

## ⑬ Agentic RAG (에이전트가 언제·어디서·몇 번 찾을지 정함)

1. 한 줄: 한 번 찾고 끝내지 않고, AI가 찾은 결과를 보고 다시 찾거나 도구를 골라 부르며 여러 번 찾는 방식.
2. 1차 자료
   - Self-RAG (Asai 외, 2310.11511, 조사 4가 원문에서 확인): 검색 필요 여부·관련성·뒷받침을 나타내는 토큰을 모델에 학습시킴. 7B/13B, 훈련 필요. 지연 숫자 없음.
   - CRAG (Yan 외, 2401.15884): 0.77B 평가기가 찾은 글을 판정해 나쁘면 웹 검색. 평가기 정확도 84.3(PopQA). 지연 숫자 없음. 둘 다 훈련 필요가 한계.
   - Adaptive-RAG(위 ⑦): 여러 단계가 한 번 대비 시간 3.3-8.8배.
   - Anthropic 엔지니어링 글 "multi-agent research system" [확인, 직접 읽음]: 멀티에이전트(리드 Opus 4 + 하위 Sonnet 4)가 단일 Opus 4보다 내부 평가에서 90.2% 나음. 토큰은 채팅의 약 4배(에이전트), 약 15배(멀티에이전트). 병렬 호출로 복잡한 질문 연구 시간 최대 90% 줄었다고 함. 맞지 않는 곳: 에이전트끼리 맥락을 공유해야 하거나 서로 의존이 큰 일, 코딩. 동기 실행에서 느린 하위 에이전트를 기다림이 병목. 조건은 "연구 과제(웹 넓게 찾기)".
   - 사용자 맞춤 질문(Blender 초보 질문) 같은 짧은 한 번 질문에 에이전트형을 잰 1차 자료는 못 찾음.
3. 이 프로젝트에서 이미 한 것
   - 질문 바꾸기·분야 고르기를 부르는 것 자체가 프로그램이 정한 고정 순서이고, 모델이 도구를 골라 부르는 구조는 안 씀 [확인, STRUCTURE.md].
   - 기록: [105] HISTORY 1034줄 "모델이 표를 직접 찾아보게(도구 호출) 하면 답변 모델 호출이 한 번 더 생겨 첫 글자가 늦어진다. 그래서 넘기는 청크 글에 나온 영어 낱말의 줄만 붙이기로 함"(Claude 판단, 항목 번호 [105]는 주 세션이 채움). 11-18 다시설계 문서 "하지 않을 것": "도구 호출 되풀이: 2초와 부딪힌다." 같은 문서 하위 "Sonnet: 비용이 크게 느는 안, 약 18배".
   - 이전 조사: 지난 프로젝트 `RerankRetriever`(AI 재순위) 질문당 6-13.5초([120]).
   - 사용자 [530]: 기다림은 줄이지 못해도 단계를 보여 주는 방향(티켓 51)으로 보완.

## ⑧ 하이브리드 검색 (낱말 검색 BM25 + 뜻 검색을 RRF로 합침)

1. **한 줄**: 질문 낱말이 글에 겹치는 정도(BM25)로 찾은 순위와 임베딩(글을 숫자 묶음으로 바꾼 것)으로 찾은 순위를, RRF(순위 r인 조각에 1/(k+r)점을 주고 더하는 합치기)로 합쳐 상위를 고르는 방법.

2. **1차 자료가 말하는 것**
   - BEIR 논문(18개 자료, 제로샷): "BM25는 튼튼한 기준선"이고, 재순위·늦은 상호작용 모델이 평균 최고지만 계산이 많이 든다. 밀집·희소 검색은 새 분야로 일반화가 모자란다. [arXiv 2104.08663](https://arxiv.org/abs/2104.08663)
   - Anthropic Contextual Retrieval(자사 실험, 상위 20개 중 놓친 비율): 맥락 임베딩 5.7% → 3.7%(35% 감소), 맥락 임베딩 + 맥락 BM25 → 2.9%(49% 감소). 조건: 코드·소설·arXiv·과학 논문 평균, 임베딩 Gemini Text 004. [Anthropic 글](https://www.anthropic.com/news/contextual-retrieval) (회사 발표 글이라 엄밀한 논문은 아님)
   - RRF 원 논문(Cormack·Clarke·Büttcher, SIGIR 2009)은 읽지 못함(위 한계).

3. **이 프로젝트에서 이미 한 것: 해 봤고, 끔**
   - 코드: `blender_tutor/answer_engine.py:21`(`rank_bm25`), `:47-48`(`RRF_K = 60`, `RRF_DEPTH = 50`), `:192`(`use_bm25: bool = False`), `:300`(색인 만들기), `:491-502`(뜻 순위 + 낱말 순위를 RRF로 합침). 기본값이 꺼져 있어도 켤 때 색인을 만든다(0.52초, [108]).
   - [6] 2026-10-19 사용자 "시작은 일단 RRF 로 가보죠 ... 속도가 생명인 작업".
   - [102] 2026-10-29 (200청크·20질문·1,080회 측정): large·BM25 원문+번역 상위 4/6/8 = 0.550/0.650/0.725, BM25 끔 = 0.500/0.675/0.725. 사용자 "1순위는 large 임베딩 api 만 붙이고 원문만 가져다 쓰고 BM25를 빼는거로 하고 top_k 는 6".
   - [117] 설명서 전체(8,997청크) + 질문 바꾸기: BM25 끔 상위 4/6/8 57.5/72.5/85(13문항), 켬 60/72.5/77.5(13). 질문 그대로 한국어: 끔 10%, 켬 15%.
   - [120] Claude 판단: "BM25는 large에서 상위 6개 같고 상위 8개는 떨어졌다". 사용자 "흠 ㅇㅋ". 이후 기본 흐름은 "BM25 끔"([121]의 정리 줄).
   - 3회차 질문 바꾸기 결과를 RRF로 합친 것(BM25와 별개의 RRF 사용)은 [121]에서 82.5%로 올랐으나, [127]은 "A6에서 검색어 2개가 정답을 1·2위로 찾았는데 하나가 엉뚱한 기능을 떠올려 RRF로 합치니 정답이 18위로 밀렸다"고 적었고 도우미는 "먼저 닫힌 1개"로 정함. 제품 현재 흐름: 영어 검색어 1개 + 임베딩(STRUCTURE.md 앞부분).
   - 06 계획서 항목 G: "이미 재 본 것은 다시 하지 않는다: … 낱말 일치 검색 섞기([102]에서 끔, 사용자 "BM25를 빼는거로 하고")."
   - 찾은 낱말: `grep -n -i "bm25|rrf|rerank|하이브리드"` (HISTORY.md, blender_tutor/*.py). 근거가 된 [102]·[117]은 설명서 20문항 개발셋(2026-10) 기준이라 지금 54문항 개발셋·Haiku 흐름에서 다시 재 본 적은 없다(확인한 사실: 그 뒤 BM25를 켠 시험 기록을 못 찾음).

4. **이 프로젝트 조건에 맞대기**
   - 실패 모양: G 진단 [순위 자료를 직접 셈] 809칸(문항 × 필요 묶음 × 10번 중) 가운데 8위 밖이 451칸. 그 안에서 9-20위 72, 21-30위 41, 31-50위 65, 50위 밖 273(그중 200위 밖 140). 모범 검색어(원인 기능 이름을 넣은 검색어)를 주면 멀던 묶음 27개 중 14개가 8위 안으로 옴("주된 몫은 검색어 쪽").
   - BM25는 질문(검색어)에 있는 낱말이 조각에 있어야 잡는다. 지금 실패는 검색어가 원인 기능 이름을 안 쓰는 것이라, 같은 검색어를 낱말 쪽으로 봐도 같은 낱말이 없어 안 온다. 영어 검색어에 기능 이름이 있으면 뜻 검색도 이미 대개 잡는다(추측). 반대로 기능 이름이 정확한 사용자 질문(메뉴 이름·영어 이름 입력)에서는 BM25가 도움이 될 수 있다(추측, 재 본 적 없음).
   - 속도: BM25 계산 자체는 8,997청크에 작다(색인 0.52초는 시작 때 한 번). 질문당 비용은 미미하다(확인: [102] 검색 시간 중앙값 0.18-0.23초 모든 조건).
   - 문항 20 → 54 사이 새 기록이 없어 낡은 근거라는 한계가 있다.

5. **판단: 해 봤고 결과는 이랬다(끔).** 
   - 확인한 사실: 20문항·질문 바꾸기 앞뒤 시험에서 이득 없음/상위 8개에서 손해([102]·[117]). 사용자가 직접 끄기로 정함.
   - 추측: 지금 주 실패(검색어가 원인 이름을 안 씀)에는 닿지 않는다. 다시 재 볼 가치는 낮다. 재 본다면 무료(돈 0, 저장된 검색어 491개로 BM25 순위만 다시 계산, 반나절 이내)지만 G 진단 순위 자료와 같은 조각에서만 비교 가능.

## ⑨ 리랭킹 (후보를 교차 인코더 등으로 다시 줄 세움)

1. **한 줄**: 1차 검색이 넓게 뽑은 후보 수십 개를, 질문과 조각을 한 쌍씩 함께 읽는 모델(교차 인코더)이나 큰 언어 모델이 다시 점수 매겨 위로 올리는 것.

2. **1차 자료가 말하는 것**
   - BERT로 다시 줄 세우기: MS MARCO 통로 검색에서 당시 최고, MRR@10 상대 27% 향상. [Nogueira·Cho, arXiv 1901.04085](https://arxiv.org/abs/1901.04085)
   - BEIR: 재순위가 제로샷 평균 최고지만 계산이 크다. [arXiv 2104.08663](https://arxiv.org/abs/2104.08663)
   - Anthropic 실험: 상위 150개에서 재순위해 20개를 남기면 놓친 비율 2.9% → 1.9%(Cohere 리랭커). 글은 "작지만 지연이 더해진다"고 적고 지연 숫자는 없음. [Anthropic 글](https://www.anthropic.com/news/contextual-retrieval)

## ⑪ GraphRAG (개체 지식 그래프)

1. **한 줄**: 모델이 글에서 사람·물건·개념(개체)과 그 관계를 뽑아 그래프를 만들고, 서로 가까운 개체 무리(커뮤니티)마다 요약을 미리 써 두었다가 질문 때 요약들로 답을 짜는 방법.

2. **1차 자료가 말하는 것**
   - 원 논문(Edge 외, Microsoft, 2024): 일반 RAG는 "말뭉치 전체의 주제는?" 같은 **전역 질문**(질의 중심 요약)에 약하다는 문제를 겨눴다. 모델이 개체 지식 그래프와 커뮤니티 요약을 미리 만들고, 질문 때 요약마다 부분 답을 만들어 합친다. 약 100만 토큰 규모 자료에서 일반 RAG보다 답의 포괄성·다양성이 좋았다고 보고(초록에 점수 숫자 없음). 지시 대상은 "찾기"가 아니라 "요약". [arXiv 2404.16130](https://arxiv.org/abs/2404.16130)
   - 비용·시간 숫자는 초록에 없어 읽지 못함(전문은 안 읽음).

3. **이 프로젝트에서 이미 한 것: 안 해 봄·논의도 없음**
   - 찾은 낱말: `graphrag|지식 그래프|knowledge graph` — `docs`, `.scratch`, `HISTORY.md`에서 0건(`grep -rli`). 코드에도 없음.
   - 가까운 것: [324]-[327]의 "설정 이름을 설명서 표지(`bpy-types-…` 앵커)에 잇는 대응표"(항목 H)는 작은 그래프 비슷한 연결이지만 개체 추출이 아닌 Blender 소스에서 뽑은 4,668쌍 표라서 다른 일이다. [327]에서 "약함"으로 닫음, 06 항목 H.

4. **이 프로젝트 조건에 맞대기**
   - 우리 질문은 "이 증상은 어떤 설정 때문인가"처럼 한두 조각을 찾는 지역 질문이다. GraphRAG가 겨눈 전역 요약 질문과 다르다(확인: 논문 초록과 문항 54개 모양 대조는 이 보고에서 직접 하지 않음, 문항은 개발 질문 목록 파일을 안 열어 추측).
   - 실패 모양은 "검색어가 원인 기능 이름을 안 씀"이라, 그래프를 만들어도 질문 쪽에서 그 개체에 닿지 못한다. 개체 연결이 도움이 되는 경우(증상 → 설정 이름 연결)는 이미 질문 바꾸기 + 대응표 후보가 맡는다.
   - 비용: 설명서 8,997청크 전체에 개체 추출을 모델 호출로 돌려야 해 다시 임베딩보다 훨씬 크다(어림, 근거 숫자 없음). 질문 때도 요약 여러 개를 읽어 속도 목표와 부딪힌다(추측).

5. **판단: 맞지 않음.** 확인한 사실: 논문이 겨눈 질문 종류가 전역 요약이다. 추측: 이 프로젝트의 지역·원인 찾기 질문과 속도 조건에 안 맞고 마감(11-30)에 비용 대비 근거가 없다.

## ⑫ 문맥 압축 (조각에서 관계 있는 문장만 남김)

1. **한 줄**: 찾은 조각을 모델에 그대로 넘기지 않고, 질문과 관계 있는 문장·낱말만 남기거나 짧게 요약해 입력을 줄이는 것.

2. **1차 자료가 말하는 것**
   - LLMLingua(2023): 낱말(토큰) 단위로 덜 중요한 부분을 지워 프롬프트를 최대 20배까지 줄여도 성능 손실이 작다고 보고. 자료는 GSM8K·BBH·ShareGPT·Arxiv-March23. 목적은 추론을 빠르고 싸게 하는 것이나 초록에 속도 숫자 없음. [arXiv 2310.05736](https://arxiv.org/abs/2310.05736)
   - RECOMP(2023): 찾은 문서를 모델 입력에 붙이기 전에 짧은 요약으로 압축한다. 문장 고르기(추출형)와 여러 문서 요약(추상형) 둘, 둘 다 최종 과제 성능을 높이게 학습. 압축률 약 6%에서 언어 모델링·열린 영역 질의응답 성능 손실이 작았다. 관계없으면 빈 글을 내 "선택적 덧붙이기". [arXiv 2310.04408](https://arxiv.org/abs/2310.04408)

## ⑭ Faithfulness (충실도: 답의 주장 가운데 검색 글이 뒷받침하는 몫)

### 1. 한 줄
답을 낱낱의 주장(문장 조각)으로 쪼개서, 각 주장이 모델에 준 설명서 글만으로 "그렇다고 말할 수 있는지" 확인하고, 뒷받침되는 주장의 비율을 낸다. 지어낸 말(환각)을 잡는 지표다.

### 2. 1차 자료가 말하는 것
- **정의·계산식.** RAGAS 논문: LLM이 답에서 주장 집합 S를 뽑고, 각 주장이 주어진 글에서 추론되는지 예/아니오로 판정해 F = |V| / |S| (V = 뒷받침된 주장). 근거 없이(정답 문서 없이) 답과 검색 글만 본다. [ar5iv 판 논문 3절](https://ar5iv.labs.arxiv.org/html/2309.15217), [arXiv](https://arxiv.org/abs/2309.15217)
- **공식 문서도 같다.** "답의 주장 중 검색 글이 뒷받침하는 수 ÷ 전체 주장 수", 정답(reference) 불필요. 예: "아인슈타인은 1879년 3월 20일 독일에서 태어났다" → 주장 2개 중 1개만 맞아 0.5. [RAGAS 문서 Faithfulness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)
- **구현.** LLM 호출 두 번: (1) 답을 "대명사 없는 독립 주장"으로 쪼갬 (2) 주장마다 "글에서 직접 추론되면 1, 아니면 0". 점수 = 1의 비율. 주장이 하나도 안 나오면 점수는 NaN(점수 없음)이다. [소스 `_faithfulness.py`](https://raw.githubusercontent.com/explodinggradients/ragas/main/src/ragas/metrics/_faithfulness.py) (도구 요약으로 읽음)
- **사람과의 일치.** 저자들이 만든 WikiEval(위키백과 50쪽, 2022년 이후 사건, 사람 두 명이 라벨, 두 사람 일치 약 95%)에서 두 답 중 더 충실한 쪽을 고르는 쌍 비교로 RAGAS 0.95, 단순 GPT 점수 0.72, GPT 순위 0.54. [논문 4절 표](https://ar5iv.labs.arxiv.org/html/2309.15217) 한계는 논문이 별도 절로 쓰지 않았다. 표본이 50쪽이고 프롬프트가 모두 gpt-3.5-turbo-16k라는 점은 읽는 쪽이 짚어야 한다(내 해석).
- **LLM 채점기의 일반적 흔들림.** 위치·장황함·자기 모델 선호 편향, 제한된 추론 능력이 알려져 있고, 강한 모델은 사람과 80% 넘게 맞는다고 보고된다. [MT-Bench 논문 초록](https://arxiv.org/abs/2306.05685) RAGAS 문서는 판정 호출의 재현성(같은 답을 두 번 매기면 같은가)을 따로 보장하지 않는다. 소스에 `max_retries = 1`이 선언만 되고 쓰이지 않는다는 점은 확인했으나, 그것이 흔들림과 관계가 있는지는 추측이다.
- **핵심 전제.** "뒷받침"의 기준은 **검색 글**이다. 검색 글이 틀리거나 낡아도 그대로 옮기면 충실하다.

## ⑮ Context precision & recall (검색 결과가 관계있나 / 필요한 걸 다 가져왔나)

### 1. 한 줄
- **Context precision(검색 정밀도)**: 모델에 넘긴 조각 8개 중 관계있는 것이 얼마나 되고, 관계있는 것이 위쪽에 있나.
- **Context recall(검색 재현율)**: 답에 필요한 내용 가운데 넘긴 조각들이 실제로 담고 있는 몫(필요한 걸 다 가져왔나).

### 2. 1차 자료가 말하는 것
- **Context precision.** 검색기가 관계있는 조각을 관계없는 조각보다 위에 올렸는지를 본다. 공식은 Precision@K 평균: (각 순위 k에서 Precision@k × v_k의 합) ÷ (상위 K 안의 관계있는 조각 수), Precision@k = k개 중 관계있는 것 비율, v_k는 k번째 조각이 관계있으면 1. 순서가 중요해서 관계없는 조각이 맨 위면 약 0.5로 떨어진다. 변형이 여럿: 정답(reference)과 견주는 LLM 판정판, 정답 없이 **생성한 답**과 견주는 판(`WithoutReference`, 새 API 이름 `ContextUtilization`), 문자열 거리로 견주는 비LLM판, 주소(ID)만 견주는 `IDBasedContextPrecision`(순위 가중 없음, 받은 주소 중 정답 주소 비율). 옛 API는 0.4에서 폐기 예고. [RAGAS 문서 Context Precision](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/)
- **Context recall.** 정답 답(reference)을 주장들로 쪼개 각 주장이 검색 글에서 뒷받침되는 비율: (정답 주장 중 검색 글이 뒷받침하는 수) ÷ (정답 주장 수). 정답 문서 주소를 달기 어려워 **정답 문장을 대신 쓴다**고 문서가 밝힌다. 비LLM판: 필요한 조각 중 받은 비율, ID판: (정답 주소 중 받은 것) ÷ (정답 주소 수). 정답이 반드시 필요하다. [RAGAS 문서 Context Recall](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/)
- **원 논문은 이 둘을 다르게 정의했다.** 2023년 논문에는 context precision·recall이 없고 "context relevance"(CR = 질문에 필요한 문장 수 ÷ 글 전체 문장 수)만 있다. 정밀도 성격이다. WikiEval에서 RAGAS 0.70(GPT 점수 0.63, GPT 순위 0.52)로 세 지표 중 가장 낮고, 저자들도 ChatGPT가 긴 글에서 핵심 문장을 가려내기 어려워했다고 쓴다. [논문 3-4절](https://ar5iv.labs.arxiv.org/html/2309.15217) 현재 라이브러리의 precision·recall은 논문 이후에 추가된 것이라 논문의 근거(사람 일치도)가 직접 적용되지 않는다(내 해석, 논문 본문에 둘이 없음은 ar5iv 판에서 확인).
- **일반론.** 이 둘은 정보검색의 정밀도·재현율과 같은 개념이고, RAGAS의 새로움은 정답 문서 라벨 대신 LLM으로 관련 여부를 매긴다는 점이다. RAGChecker 논문도 검색·생성 각각의 진단 지표 묶음을 제안하며 사람 판단과의 상관이 더 높다고 주장하나, 초록만 읽어 세부 정의는 확인 못 했다. [RAGChecker 초록](https://arxiv.org/abs/2408.08067)
- **LLM 판정판의 흔들림**: ⑭와 같다(편향·재현성). 주소 판은 LLM이 없어 흔들림이 없지만 "정답 주소 목록"을 사람이 만들어야 한다.

### 3. 이 프로젝트에서 이미 하는 것

**Recall은 이미 쓰고 있다. 가장 가까운 것은 RAGAS의 `IDBasedContextRecall`이고 더 엄격하다.**
- 필요 조각 주소 목록 `data/eval/dev50/needed_20261118.json`: 문항마다 "답에 꼭 필요한 설명서 조각 주소"를 묶음(대안 주소 중 하나만 오면 됨)으로 고정(`docs/plan/01` B, HISTORY [465]·[467], 갈린 14차례는 Fable high가 정함). 48문항에 87개 주소, 6문항은 설명서가 필요 없어 빈 목록(`docs/experiment.md` 04 자료).
- 세는 도구 `.claude/tools/needed_count.py`: "주소의 조각 글 전체가 **모델에 실제로 보낸 글** 안에 그대로 있으면 그 주소가 넘어간 것"(머리 설명). 차이점이 둘이다. 정답 주소가 검색 8위 안인지가 아니라 **모델이 받은 글 전체**(먼저 볼 소제목, 짧은 조각의 형제 소제목 포함)를 본다. 그리고 조각 글을 글자까지 맞대 확인한다(도구가 순위가 아니라 내용 존재로 판정).
- 숫자(`docs/experiment.md` 04 실행 뒤): 필요 내용이 다 넘어간 차례(48 중) 지금 17·16·18·16·17, 새 뼈대 16·17·14·14·16(5회). 5회 모두 0인 문항 30·29개, 묶음이 한 번도 안 찬 문항 11·12개. 05 판정 문항 무리: "늘 13 / 가끔 6 / 일부 19 / 하나도 10".
- 옛 방식: "정답 위치"(등록된 청크) 적중. HISTORY [166] "엄격한 검색 적중 24 / 49". 이 방식이 필요 조각과 어긋남이 [459]에서 드러남(Q05는 등록 위치가 와도 필요 조각 0/3, Q41은 조각이 없어도 3번 모두 맞음, `docs/plan/01` 왜 하나/B). 필요 목록은 그 보정이다.
- **recall을 더 쪼개 보는 일도 했다.** 06 G 진단(`docs/experiment.md` "06 항목 G 진단"): 10번 모두 못 받은 10문항의 묶음이 "120번 중 50위 밖 103번" → 주된 몫은 검색어. 그리고 recall이 답으로 이어지는지: 05에서 none_조각만 대 지금 7:4, 차이 3, p 0.274(조각 recall을 올려도 맞음이 거의 안 오름).

**Precision은 재지 않았다. 그러나 비슷한 읽기는 있다.**
- `답.jsonl`의 "적중 순위" 칸(`docs/plan/01` 지금 상태 절)은 정답 위치의 순위라서 MRR(첫 정답의 순위)에 가깝다. 찾은 곳: `docs/plan/01` 지금 상태 절 칸 목록. 정밀도 점수로 쓴 기록은 못 찾음.
- "관계없는 조각이 자리를 차지한다"는 가설을 따로 쟀다: HISTORY [166] 가설 2(비슷한 청크가 자리 차지): "겹침 줄이기는 +1-2개, 완전히 같은 글(Bevel 모서리·꼭짓점)만 빼도 안전".
- "근거가 와도 답이 쓰지 않거나(Q07·Q43)" 관찰(`docs/experiment.md:973`)은 RAGAS의 `ContextUtilization`(답이 받은 글을 얼마나 쓰나)과 같은 질문이다.
- 05 천장 측정이 "필요 조각을 맨 위에 넣고 04 꼬리 조각 1.51개(최대 7)를 빼는" 갈아 끼움이었는데(`docs/experiment.md` 05 독립 검토 3), 맞음이 거의 안 올랐다. 곧 **관계없는 꼬리 조각을 빼도(정밀도를 올려도) 맞음 이득이 작다**는 간접 증거다(내 해석, 맞음 +3, p 0.274는 사이).

못 찾음: `precision`·`recall`·`재현율`·`정밀도`로 저장소(`data/`·`results/`·`archive/` 제외) 검색. precision은 `blender_tutor/tools/local_embeddings.py`·HISTORY의 "정밀도"가 임베딩 수치 정밀도 이야기였고, 검색 정밀도 지표는 없음.

### 4. 이 프로젝트 조건에 맞대기

| | RAGAS식(LLM 판정) | 지금(주소 목록 + 글 대조) |
|---|---|---|
| Recall 얻는 것 | 정답 주소 목록을 안 만들어도 정답 문장만 있으면 됨 | 이미 만든 주소 목록을 쓰니 LLM 흔들림 0, 돈 0, 글자 단위로 결정적 |
| Recall 잃는 것(확인) | 정답 문장(reference)을 사람이 써야 하고, LLM이 "이 조각이 이 주장을 뒷받침하나"를 매겨 흔들림이 생긴다 | 필요 목록 자체가 정답을 본 AI가 만든 것이라 편향 가능성(05 목표 검토가 이미 짚음: "정답 본 AI가 만든 목록·원인 줄") |
| Precision 얻는 것 | 8개 중 관계있는 몫과 순서를 숫자로 줌. 검색 자료가 지저분한지 알 수 있음 | (없음. 재지 않음) |
| Precision 잃는 것(확인) | **필요 목록이 너무 작아 정밀도가 의미 없다.** 필요 묶음이 문항당 평균 약 1.7개(82묶음/48문항, 서로 다른 주소는 87개·대안 포함 113개, 주 세션이 다시 셈)이고 모델에 가는 조각은 8개 이상이라, 필요 주소 기준 precision@8의 상한이 약 0.2이다. 이 상한은 검색 품질이 아니라 목록 크기가 정한다 | |
| Precision 잃는 것(추측) | "관계있음"을 LLM이 매기면 필요하진 않지만 도움 되는 조각(예: 다른 설명 쪽)이 섞여, 필요 목록 기준과 다른 숫자가 나옴 | |
| 돈·시간(어림) | precision LLM판은 답 하나당 조각 8개를 따로 판정: 호출 8번 또는 한 번에 8개. 입력은 조각 8개(약 1만 토큰)라 ⑭와 비슷하게 540답 약 $1-2(추측) | 이미 만든 도구로 0원 |

검색 정밀도의 쓸모가 낮은 이유(확인한 사실 위주): 지금 흐름은 검색 상위 8개를 **그대로** 모델에 넘기고 재정렬·거르기가 없다(`STRUCTURE.md` 흐름: 질문 바꾸기 → 분야 고르기 → 임베딩 상위 8개 → Haiku 답). 정밀도를 알아도 올릴 손잡이(리랭커·거르기)가 06 항목에 없다(06 항목 표 A-J). 06 G 후보도 "검색어"를 건드릴 뿐이다. 그리고 05에서 입력을 정확하게 해도 맞음이 오른 몫은 생각 켜기(medium 대 none 11:2, p 0.011)가 가장 컸고 조각 몫은 사이였다. 즉 지금 병목은 recall 쪽의 검색어와 모델의 답 쪽이지 precision이 아니다(05 판정 기준, 추측 섞임).

### 5. 판단

- **Context recall: 이미 씀(이름만 다름, 더 엄격한 꼴).** `needed_count.py` + `needed_20261118.json`이 `IDBasedContextRecall`과 같은 개념이다(대안 묶음·글 대조로 더 엄격). RAGAS의 LLM판 recall로 바꿀 이유 없음. 확인한 사실: 04에서 세는 도구를 다른 경로로 맞대 못 잡은 것 0, 저장된 162답 검색 8개만 세면 26%(38/144)와 1회차 35%·33%가 같은 방향.
- **Context precision: 해 볼 만한 후보지만 우선순위 낮음. 지금은 "맞지 않음"에 가깝다.**
  - 후보가 된다면 가장 싼 길은 **LLM 없이** 주소만 쓰는 `IDBasedContextPrecision` 꼴: 모델이 받은 글에 든 조각 중 필요 목록 주소의 몫. 돈 0, 하루 안 걸림, 코드는 `needed_count.py`에 한 함수. 다만 위에 적은 것처럼 목록이 작아 숫자 상한이 낮아 읽기 어렵다(확인: 87주소/48문항).
  - 쓸모가 있을 만한 대안: **"필요 조각 위쪽 순위" 지표**. 04에서 "5회 모두 0 문항 목록"을 낸 것에 순위(몇 번째로 왔나)를 더하면 G-1이 건드릴 문항을 고르는 데 도움이 된다. 06 G 진단이 이미 순위 계산(`g_diag_rank.py`)을 했으므로 새로 만들 일이 아니다.
  - 맞지 않음: RAGAS의 LLM 판정 `context_precision`을 540답에 돌리는 것. 이유: 올릴 손잡이가 없고, 필요 목록이 아닌 "관계있음" 기준을 새로 들이면 두 기준이 어긋난다.
- 확인 못 한 것: RAGChecker의 세부 정의, RAGAS 최신 소스의 context precision 프롬프트 문구(문서 요약만 읽음), 실제 호출 비용(어림만).

# 덧붙임: 결정 모델 Gemini Decision 1 (2026-11-19, 주 세션이 공식 문서를 직접 읽음)

- 왜: 사용자가 ⑬ 에이전트 RAG에 "디시전 모델"을 쓰는 안을 물었고, Jev(TypeSafe AI)보다 Google 쪽을 쓰고 싶다고 함("되도록 제미나이 디시전을 쓰고 싶긴해 jev 는 좋긴한데 뭔가 믿음이 덜가는 작은 회사라 그런가"). Jev는 2차 기사만 읽었다(Amplitude 분석: 호출 70-500ms, 정확도는 큰 LLM보다 낮았음).
- 읽은 1차 자료(내장 브라우저, 쿠키는 '나중에'로 거절): [Google 발표 글 2026-11-11](https://blog.google/innovation-and-ai/technology/developers-tools/gemini-decisions-api/), [Decisions API 문서](https://aistudio.google.com/docs/decisions-api), [모델 쪽](https://aistudio.google.com/docs/models/gemini-decision-1), [요청 한도](https://aistudio.google.com/docs/rate-limits#gemini-decision).

## 공식 문서가 말하는 것

- 무엇: 글을 만들지 않고, 정해진 질문에 확률을 매겨 돌려주는 모델(`gemini-decision-1`, Gemini Developer API `v1beta`만). 질문 꼴 셋: 예/아니오 `noul`(0.01-0.99), 하나 고르기 `choice`(선택지 2-255개, 선택지별 확률), 등급 `score`(2-255단계). 답마다 confidence(그 답이 맞을 확률 어림).
- 한 요청에 공통 입력 하나 + 질문 1-1,000개. 질문끼리는 서로 못 보고 따로 매겨진다. 공통 입력은 요청마다 한 번만 센다.
- 시간: "150-250 ms end-to-end", 모델 계산 중앙 50-100ms, "contexts up to 16K tokens"에서, 질문 1-100개 사이에 거의 같음(발표 글, Google 자체 수치).
- 값: 입력 100만 토큰당 $0.10, 출력 0. AI Studio에 무료 단계가 있음. 문맥 캐시·Batch·Flex·Priority는 안 됨(같은 입력을 되풀이해도 그때마다 셈).
- 한도(무료 단계): 분당 200요청, 분당 5만 토큰, 하루 1만 요청. Tier 1: 분당 1,500·100만 토큰·하루 5만.
- 입력 한도 262,144토큰. 질문 글은 글자만. 대화 기록·도구 호출 블록은 못 넣고 글로 펴서 넣는다.
- 문서의 주의: "Send only the fields the questions need. Unrelated content lowers accuracy.", 문턱은 자기 자료의 라벨 예로 정하라. `choice`는 맞는 것이 없어도 확률을 나눠 주므로 confidence나 별도 예/아니오로 거른다.
- 한국어 지원은 문서·모델 쪽 어디에도 적혀 있지 않다(확인 못 함). 우리 쪽 입력은 영어 검색어·영어 설명서 조각이 대부분이고, 한국어 질문을 넣는 자리만 걸린다.
