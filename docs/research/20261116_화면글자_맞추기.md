# 화면 글자 맞추기: 사람들은 어떻게 하나 (2026-11-16 조사)

## 먼저 읽을 것

- 질문: 모델이 쓰는 한국어 설명 안에서 Blender 메뉴·옵션 이름을 공식 한국어 번역(화면 글자)으로 맞추는 방법.
- 표시: **[확인]** = 아래 링크의 원문에서 확인한 사실. **[추측]** = 내 판단이며 근거 자료 없음.
- 조사의 한계: 학술 연구(기계 번역 분야)는 "영어 문장을 한국어로 번역할 때 용어 지키기"를 다룬다. 우리 문제는 "모델이 쓴 한국어 글 안의 이름 고치기"라서 똑같은 문제를 푼 논문은 찾지 못했다. 그래서 방법은 빌려 오되 효과 숫자는 우리 상황에 그대로 옮길 수 없다.
- PDF 원문 두 개(WMT 2023 오버뷰, Moslem 논문 PDF)는 도구가 읽지 못해 초록·HTML 버전만 읽었다. 읽은 범위는 각 항목에 적었다.
- 참고한 우리 코드: `blender_tutor/menu_names.py` 머리 부분(1-80행). 거기에 이미 `[[ ]]`로 메뉴 이름을 감싸는 표시(`MARK_OPEN`, `MARK_CLOSE`)가 있다. 답 모델이 이 표시를 쓰는지는 이 조사에서 확인하지 않았다.

## 용어 한 줄 풀이

- 용어 제약 번역: 번역할 때 "이 낱말은 꼭 이렇게 옮겨라"라는 용어 목록(용어집)을 같이 주는 기계 번역.
- 제약 디코딩: 모델이 글자를 한 조각씩 고르는 단계(디코딩)에서 정해 둔 낱말이 나오도록 강제하는 방식.
- 후교정(APE): 이미 나온 번역을 다시 손봐서 고치는 일.

## 방법 1. 생성 도중 강제(lexically constrained decoding)

- **무엇**: 모델이 다음 글자를 고를 때 "이 낱말이 반드시 나와야 한다"는 규칙을 검색(빔 서치)에 끼워 넣는다.
- **근거**: Post & Vilar 2018은 제약 개수가 늘어도 비용이 늘지 않는 방식을 제안했고 Sockeye에 들어 있다 **[확인]** (https://arxiv.org/abs/1804.06609). Dinu 외 2019는 이 방식이 번역 시간을 약 3배 늘린다는 이전 연구를 인용하고(약 0.68초 대 0.19초), 강제한 낱말이 문법에 맞게 변해야 할 때(독일어 humanitär) 점수가 1점 안팎 떨어졌다고 보고한다 **[확인]** (https://ar5iv.labs.arxiv.org/html/1906.01105). Hugging Face에는 `bad_words_ids`(특정 낱말 금지)와 `PrefixConstrainedLogitsProcessor`(다음에 올 글자를 제한)가 있다 **[확인]** (https://huggingface.co/docs/transformers/en/internal/generation_utils).
- **어려운 경우를 푸나**: 아니다. 이 방식은 "이 자리에 이 낱말을 써라"를 이미 알고 있을 때 쓴다. "뜻 설명인지 메뉴 이름 옮김인지"를 가르는 문제는 그대로 남는다.
- **스트리밍**: 맞는다(생성 중에 걸므로). 다만 직접 모델 안의 확률 계산에 손댈 수 있어야 한다. 외부 API 모델로는 보통 못 쓴다 **[추측]**(어떤 API가 지원하는지 전부 확인하지는 않았다).
- **비용·크기**: 큼. 자체 모델 운영이 필요하고 우리 프로젝트 규모에 맞지 않는다 **[추측]**.

## 방법 2. 입력에 용어를 넣어 학습·유도(Dinu 방식, 인라인 표기)

- **무엇**: 원문의 용어 옆에 목표 용어를 붙여서(`Sheen <셰인함>`) 모델이 쓰도록 학습시킨다.
- **근거**: Dinu 외 2019. 용어 사용률이 기본 76.9% → 93.4%(바꿔 넣기)로 오르고 속도는 그대로, 강제 방식보다 변형(활용형)에 너그럽다 **[확인]** (https://ar5iv.labs.arxiv.org/html/1906.01105).
- **푸나**: 부분적으로. 모델이 문맥을 보고 쓰기 때문에 "뜻 설명 + 이름" 구조를 유지할 수 있다. 하지만 모델을 새로 학습시켜야 한다.
- **스트리밍**: 맞는다. **비용**: 학습이 필요해 우리에게는 큼 **[추측]**. 같은 생각을 프롬프트로 옮긴 것이 방법 3.

## 방법 3. 프롬프트에 용어집을 넣기(관련된 것만 골라 넣는 RAG 포함)

- **무엇**: 질문에 나온 낱말과 관련된 영어→공식 번역 짝만 골라 프롬프트에 붙인다. 검색해서 붙이는 방식(RAG)이다.
- **근거**: Ghazvininejad 외(Meta) 2023 DiPMT는 낱말마다 사전 후보를 프롬프트에 주면 영역 밖 번역에서 평균 약 9.4 BLEU 올랐다고 한다. 모델이 힌트를 무시하거나, 후보가 여럿이면 엉뚱한 것을 고르기도 한다 **[확인]** (https://ar5iv.labs.arxiv.org/html/2302.07856). Moslem 외 2023(WMT)은 프롬프트에 용어 목록을 넣는 것을 포함해 비교했고, 후속 학위논문은 사람 평가에서 용어집 프롬프트가 아랍어·프랑스어·스페인어에서 더 좋았다고 한다 **[확인, 검색 요약으로만 보았고 논문 본문은 못 읽음]** (https://arxiv.org/pdf/2401.14559). WMT 2025 참가작 Lingua Custodia는 기본 4B 모델의 용어 일치가 40-55% 수준에서 시작했다고 보고한다 **[확인]** (https://arxiv.org/html/2510.17504v1). 즉 프롬프트만으로는 100%가 안 된다.
- **푸나**: 반쯤. 대부분 이미 하고 있는 일이다(우리는 공식 번역을 근거 글에 가지고 있다). "Sheen = 셰인함" 같은 짝을 모델이 보고 쓰게 할 수는 있지만, 어색한 공식 번역을 어떻게 쓸지(설명과 함께 쓸지)는 시스템 프롬프트로 정해야 한다. 모델이 따르지 않는 경우는 남는다.
- **스트리밍**: 맞는다(생성 전에 한 번만 붙임). **비용**: 낮음. 이미 하고 있으면 추가 개발은 시스템 프롬프트 손질 수준.

## 방법 4. 표시(태그)를 달게 하고 코드가 치환

- **무엇**: 모델에게 "메뉴·옵션 이름은 영어 원문 그대로 `[[Sheen]]`처럼 감싸라"고 시키고, 코드가 표 조회로 화면 글자를 꽂는다. 뜻 설명은 감싸지 않고 따로 쓴다. 번역 업계의 마크업·플레이스홀더(자리표시자) 방식과 같은 발상이다.
- **근거**:
  - Azure Translator는 `<mstrans:dictionary translation="...">`로 감싼 구절의 번역을 정해 준다. 다만 문서가 "고유명사·제품명 같은 복합 명사에서만 안전하다"고 밝힌다 **[확인]** (https://learn.microsoft.com/en-us/azure/ai-services/translator/dynamic-dictionary). 번역하지 않을 부분은 `translate="no"` 표시를 단다 **[확인]** (https://learn.microsoft.com/en-us/azure/ai-services/translator/text-translation/how-to/prevent-translation).
  - Hanneman & Dinu 2020은 기계 번역에서 마크업 태그를 어떻게 표현할지와 학습으로 태그 위치를 익히게 할 수 있는지를 비교했다. 결론은 방식마다 장단점이 있다는 것 **[확인, 초록만 읽음]** (https://aclanthology.org/2020.wmt-1.138/).
  - Claude 문서는 프롬프트를 XML 태그로 구조화하라고 하고, 출력을 태그 안에 쓰게 해서 후처리할 수 있다고 안내한다 **[확인]** (https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices).
- **푸나**: 푼다. 핵심은 모델이 한국어 번역어를 직접 쓰는 일을 아예 없애는 것이다. 모델은 "이게 메뉴 이름이다"만 판단하고(이 판단은 문맥을 보는 모델이 가장 잘한다 **[추측]**), 코드는 글자를 조회만 한다. "선택되지 않은 것 포함(Unselected)"에서는 모델이 `선택되지 않은 것 포함 [[Unselected]]`로 쓰면 설명은 살고 이름만 치환된다. "침대 천의 광택(Sheen)"도 설명과 이름이 나뉜다. 어색한 공식 번역은 코드가 `셰인함(Sheen)`처럼 영어를 함께 붙이고 앞에 모델의 설명을 그대로 두면 읽기가 덜 나빠진다 **[추측]**.
- **스트리밍**: 맞지만 조건이 있다. `[[`가 열린 뒤 `]]`가 올 때까지 글자를 잠깐 붙잡아 두었다가 한 번에 바꿔 내보내면 된다. 지연은 이름 하나의 길이만큼으로 작다 **[추측, 논문 근거 없음. 일반 구현 상식]**. 한편 모델이 태그를 빼먹는 경우(쓰기로 해 놓고 일반 글로 쓰는 경우)가 남아 지금의 "괄호 앞 한국어 교정"을 보조로 둘 필요가 있다 **[추측]**.
- **비용·크기**: 낮음-중간. 시스템 프롬프트와 스트림 처리기. 유료 호출 추가 없음.

## 방법 5. 생성 뒤 용어 교정(APE: 모델이 다시 손보기)

- **무엇**: 먼저 번역(또는 답)을 만들고, 두 번째 호출에서 "이 용어를 쓰도록 고쳐라. 나머지는 그대로"라고 시킨다.
- **근거**: Moslem 외 2023은 gpt-3.5-turbo에 "나머지는 그대로 두고 용어를 넣어 고쳐라"를 시켰고, 용어 사용률을 평균 38.98% → 72.88%로 올렸다 (독일어-영어는 38.81 → 53.85, 영어-체코어는 36.87 → 82.16). 자동 점수로는 품질이 떨어지지 않았고, 사람 평가는 없다. 그리고 이 단계가 추가 비용과 지연을 만든다고 스스로 적었다 **[확인]** (https://ar5iv.labs.arxiv.org/html/2310.14451). Bogoychev 외(arXiv 2310.05824)도 "번역 후 LLM이 용어를 반영해 다듬기"로 재현율이 더 오른다고 보고했다 **[확인, 초록만 읽음]** (https://arxiv.org/abs/2310.05824). DuTerm(WMT 2025)은 1단계 번역 후 GPT-4o가 용어를 지키며 다듬는 2단계 구조를 쓴다. 용어를 제대로 준 설정에서 용어 성공률이 0.98-0.99였다 **[확인]** (https://arxiv.org/html/2511.07461v1).
- **푸나**: 푼다(문맥을 보는 모델이 판단하므로). 하지만 모델을 한 번 더 부르니 돈과 시간이 든다.
- **스트리밍**: 맞지 않는다. 답이 다 나온 뒤에야 고칠 수 있다. 이미 화면에 나간 글을 되감아 바꾸는 방식이면 사용자가 글이 바뀌는 것을 본다 **[추측]**.
- **비용·크기**: 호출이 늘어난다(유료). 우리 조건(유료 호출 적게)에 맞지 않는다.

## 방법 6. 용어 사전을 후처리 치환기로 쓰는 것(우리가 지금 하는 것)과 그 확장

- **무엇**: 표 조회·치환(문자열 사전). 실제 제품에서는 DeepL 용어집, Google 번역 용어집이 이 방식이다. Google은 기본이 대소문자 구분 일치이고 불용어는 건너뛴다고 쓰며, 활용형 처리는 문서에 없다 **[확인]** (https://docs.cloud.google.com/translate/docs/advanced/glossary). DeepL 문서 해당 쪽에는 일치 규칙·활용형 설명이 없다 **[확인, 문서에 없다는 것만]** (https://developers.deepl.com/docs/api-reference/glossaries).
- **푸나**: 문맥 판단은 못 푼다. 이 방법은 "이 낱말이 나오면 이 낱말로"의 몫이다. Dinu도 강제 치환이 활용형과 부딪히는 문제를 지적한다.
- **스트리밍**: 맞는다(우리는 이미 한다). **비용**: 이미 있음.

## 방법 7. 문맥 판단을 작은 모델·분류기에 맡기기

- **무엇**: 괄호 앞 한국어가 "설명"인지 "이름 옮김"인지를 작은 분류 모델이나 짧은 LLM 호출 한 번으로 가른다.
- **근거**: 이 문제(번역어가 문맥에서 용어 번역인지 판단)와 정확히 맞는 논문은 찾지 못했다 **[확인: 못 찾음]**. 가까운 연구는 교차 언어 어휘 대체 과제와 단어 뜻 구별(WSD)이다. 요약 글에서 번역 오류 중 단어 뜻 오류가 평균 약 42%로 가장 많다고 한다 (https://arxiv.org/pdf/2307.04018, **검색 요약으로만 확인**). 우리 문제에 바로 쓸 학습 자료나 방법은 이 조사에서 찾지 못했다.
- **푸나**: 푼다고 기대할 수 있으나 증거 없음 **[추측]**. 한국어 소규모 분류 학습 자료를 우리가 만들어야 한다.
- **스트리밍**: 이름 하나를 확정할 때까지 지연이 필요하다. 호출이 들어가면 느려진다.
- **비용·크기**: 자료 만들기·학습·운영이 필요해 중간 이상.

## 방법 8. 한 번에 모아 놓고 사람이 검수하는 용어집(소프트웨어 현지화 업계의 기본)

- **무엇**: 번역 관리 도구들은 사람이 만든 용어집을 번역가·번역기에 보여 주고, 위반을 점검하는 품질 검사(QA)로 잡는다. 이 쪽 제품 설명서는 이번에 일일이 읽지 못했다 **[확인 못 함]**.
- **우리와의 관계**: 우리는 이미 공식 ko.po를 용어집으로 갖고 있고(`menu_names.py` 머리말), 못 가른 경우는 "용어집 위반 검사 + 사람이 본 목록 쌓기"로 줄일 수 있다 **[추측]**.

## 처방 후보 순위

1. **방법 4(태그로 표시하게 하고 코드가 치환), 현재 치환기는 보조로 유지.** 이유: 어려운 두 경우(설명 vs 이름, 어색한 공식 번역)를 모델 판단과 코드 조회로 나눠서 푸는 유일한 방법이다. 유료 호출이 늘지 않고 스트리밍과 맞는다. 위험은 모델이 태그를 빼먹는 것. 그래서 지금 방식을 안전망으로 남기고, 표시 대응이 얼마나 되는지 실제 답 기록으로 먼저 재 봐야 한다 **[추측, 시험 필요]**.
2. **방법 3(관련 용어 짝만 프롬프트에 붙이기), 1번과 같이.** 이유: 비용이 낮고 1번의 태그 쓰는 법을 같이 알려 줄 수 있다. 단독으로는 용어 일치가 완전하지 않다는 근거가 있다(Lingua Custodia, Moslem).
3. **방법 7(작은 분류기·짧은 호출)은 1번을 해 본 뒤 남은 경우에만.** 이유: 근거 연구가 없고 자료 만들기가 필요하다.
4. **방법 5(2차 호출로 다시 고치기).** 이유: 효과는 근거가 있으나 유료·지연·스트리밍 불일치로 조건에 안 맞는다.
5. **방법 1·2(디코딩 강제·학습).** 이유: 자체 모델이 필요해 범위 밖.
