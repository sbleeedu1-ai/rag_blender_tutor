# 채점 체크리스트

채점·장면·재기 기준. 2026-11-03 만듦, 2026-11-04 사용자와 다시 정리(HISTORY [160]), 2026-11-11 판단 대상 정리로 더함(HISTORY [276]). 2026-11-11 `docs/experiment.md`에서 떼어 옮김(채점자가 줄 번호 대신 이 파일 전체를 읽게).

채점은 이 체크리스트를 받은 새 하위 에이전트가 한다(메인 세션의 짐작이 섞이지 않게). 메인 세션은 결과를 사용자에게 보이고, 판단이 갈린 것은 사용자에게 묻는다.
엄격한 쪽을 기준으로 한다(사용자 "엄격한게 맞기는 하지", 2026-11-03).
근거: 프로토타입 판단 9개(사용자와 정함)와 명세·티켓 45개·HISTORY [1]-[159]에 흩어진 결정(HISTORY [160]).
웹 질문을 문항으로 바꿀 때는 본문과 답글을 열어 실제 증상과 해결책을 확인한 뒤 정답 청크를 정한다. 한국어 원문의 말투(반말, 한영 섞기, 소리 나는 대로 쓴 기능 이름)는 살린다. 확인 못 한 질문은 파일에 "본문 안 읽음"으로 표시한다(HISTORY [97]).

## 1. 맞음 / 부분 / 틀림

- **맞음**: 초보자가 그대로 따라 해서 된다(명세).
- **부분**: 방향과 핵심 단계는 맞는데, 따라 하다 한 번은 막힌다.
- **틀림**: 따라 하면 안 되거나, 지켜야 할 원칙(아래 종류별 기준)을 어겼다.
- 부분과 틀림의 경계: 막혀도 답 안의 말로 풀 수 있으면 부분, 막힌 뒤 풀 길이 없으면 틀림(예: 되돌리기 없이 이미 없어진 면을 누르라 함, 2026-11-11 HISTORY [276]).
- 정답은 **실제 5.2 화면과 동작**이다. 설명서 문장이 낡았거나 화면과 다르면 화면을 따른다(예: 설명서에 남은 'Textured' 보기는 5.2에 없다).

## 2. 문항 종류별 기준

| 종류 | 맞음이 되려면 |
|---|---|
| 정답형(연습 과정 단계·메뉴 위치·범위 밖·시나리오) | 핵심을 담고, 누를 곳이 화면 어디인지까지 말한다. 핵심 가운데 확인용·조건부·설명용 줄(예: "숫자를 맞추고 싶으면 Ctrl + A")은 빠져도 질문의 목적을 이루면 깎지 않는다. 그 줄이 없어 결과를 못 보거나 한 번 막히면 부분(예: 불리언 뒤 자르는 물체를 숨기는 법이 없어 구멍이 안 보임) |
| 설명서에 없는 질문 | "설명서에 없다"고 밝히고 지어내지 않는다. 가까운 쪽을 권하면 좋지만 그 권유가 사실에 맞아야 한다. 근거 없이 더 나쁜 길(되지만 덜 좋은 길)을 권하면 부분, 따라 해도 목적에 닿지 않는 길을 권하면 틀림(예: FBX로 넘어가지 않는 Rigid Body를 게임 엔진 충돌 해결로 권함). "없다"를 밝히지 않고 사실에 맞는 일반 조언만 하면 부분, 설명서에 없는 판단을 설명서에서 나온 것처럼 말하면 틀림(예: "설명서 기준으로 보면 … 된다") |
| 함정 | 틀린 전제(4.5와 5.2 차이 포함)를 먼저 바로잡는다. 전제를 일부라도 인정하거나(예: 없어진 칸을 "다른 곳으로 옮겨졌어요", "모니터가 이상한 것만은 아닙니다") 전제 쪽 해결을 먼저 권하면 뒤가 맞아도 틀림. 맞장구 한마디 뒤 곧바로 분명히 바로잡으면 부분(예: "나눠야 하죠?"에 "맞아요. … 다시 떼지 않고") |
| 연습 과정 권하기(티켓 22) | 연습 과정 밖 단순 질문에 권하면 틀림. 없는 물건을 만들고 싶다는 질문에 "가장 가까운 건 …"이면 맞음, 안 권하면 부분. 학습 방법 상담(예: "감을 어떻게 길러요?")은 권해도 안 권해도 깎지 않는다(연습 과정을 넓힐 때 다시 정함) |
| 시나리오형(티켓 29) | 한 대화를 실제로 이어 묻고 질문마다 따로 채점한다 |
| GPT 빈손 | 같은 기준("그대로 따라 해서 되나") 하나로 채점. 설명서에 없는 질문에서는 사실에 맞는 일반 답도 맞음(티켓 10). GPT에는 연습 과정 정보를 주지 않으며 결과표에 그렇게 적는다 |

## 3. 깎는 규칙

- 누를 곳을 **엉뚱한 데로** 가리키면 값 이름이 맞아도 틀림(다른 창·없는 메뉴, 예: 렌더 탭을 "상단 메뉴"). 같은 창 안에서 칸 이름(과 묶음 이름)은 맞고 자리 설명("왼쪽 아래")만 틀리면 부분(예: 창과 "아마츄어 항목의 자동 뼈대 오리엔테이션"은 맞는데 설정이 "왼쪽 아래"에 있다고 함).
- **누를 것 자체가 다른 것**(이름이 다름)을 맞는 길과 함께 주면 틀림(예: X-Ray를 켜려고 "구 모양 음영 버튼을 누르거나 Alt + Z"). 우연히 될 수 있어도 기대지 않는다.
- 핵심 단계는 맞는데 누를 곳의 **위치가 빠지면** 부분. 환경 설정처럼 잘 알려진 곳도 여는 경로(Edit > Preferences)가 빠지면 부분. 질문이 "뭐부터"인데 첫 단계를 뭉뚱그려도 부분.
- **사실과 다른 말**: Blender 동작·설명서 내용·작업 상태를 틀리게 말하거나 지어내면 따라 하는 단계가 되어도 틀림(예: "돌린 만큼 Dimensions 값도 바뀐다", 연결 안 된 점은 병합되지 않는다는 지어낸 설명, 이미 끝난 칸 지정이 남았다는 말). 작업 상태에 없는 것을 "없다"고 단정해도 같다(예: 모델에 넘어가지 않은 조명을 "없다"고 함). 낡은 설명서 문장을 그대로 옮겨 화면과 다른 값을 알려 줘도 같다(예: 5.2 기본 1.0인 FBX Scale을 설명서대로 "기본 10"). 표현이 서툴 뿐 사실을 지어내지 않았으면 맞음 + 메모. 예외: 아래 틀린 "설명서에 없어요" 사족과 숫자 값의 참고 치수.
- **틀린 "설명서에 없어요"**를 본론이 맞은 답에 덧붙이면 맞음에서 부분으로. 청크 파일에서 실제로 찾아본다(4절 3번).
- **표기**: 따로 깎지 않는다. 다만 표기 때문에 화면에서 못 찾게 되면 "따라 해서 된다"를 어긴 것이라 깎는다. **작업 상태가 한국어 화면(언어 ko_KR, 화면 번역 켜짐)인데 메뉴·버튼·옵션 이름을 영어로만 쓰면 부분**이다(채점자가 찾을 수 있을지 따로 짐작하지 않는다). 질문이 그 영어 이름을 먼저 쓴 경우와, 한국어 화면에서도 영어로 보이는 이름은 깎지 않는다(2026-11-13 HISTORY [310]). 표기 규칙 자체(메뉴 "한국어(영어)", 용어표, 마크다운 금지)는 답 모델 지시에 있다.
- **숫자 값**: 크기 치수는 참고값이라 조금 달라도 깎지 않는다. 결과를 바꾸는 값(회전 방향·축)은 계산해서 틀리면 틀림. 상태에서 읽은 값은 작업 상태 JSON과 대조한다.
- **그림**: "설명서 그림에 ○○가 나온다"고 했는데 넘어간 조각의 그림이 그렇지 않으면 틀림("설명서 그림을 함께 보세요"만 쓴 것은 깎지 않음). 답에 `[그림]` 표시가 그대로 새어 나와도 결함으로 본다.
- **실패 문구**(서버 오류 등)가 나온 질문은 틀림, 원인 칸에 "실패"라고 적는다(실패를 성공처럼 숨기지 않는다).
- 깎지 않고 **메모만**: 근거 조각에 더 쉬운 방법이 있는데 빠뜨림(따라 해서 되면 맞음), 화면 시점을 몰라서 생긴 문제(시점은 지금 모델에 넘기지 않는다).

## 4. 답을 채점할 때 (질문마다)

1. **답의 문장마다 출처를 찾는다**: 연습 과정의 그 단계 글(모델에 넘어간 것), 검색된 조각, 작업 상태. 연습 과정 글을 따른 말이 상태와 안 맞으면 답보다 **장면을 먼저 의심**하고 5절로 확인한다. 장면이 틀려서 생긴 문장은 답 탓으로 치지 않고, 장면을 고쳐 다시 잰다. 시험 도구 탓(장면 스크립트, 장면에 담을 수 없는 환경 설정)은 답 탓이 아니고, 제품이 모델에 넘기지 못한 정보 때문에 생긴 틀린 말은 답 탓이다(실제 사용자도 같은 답을 본다).
2. **따라 해서 되나**: 1-3절로 판정한다.
3. **"설명서에 없어요"·"방법이 없어요"는 확인한다**: 청크 파일(`data/chunks/manual_chunks.jsonl`)을 검색해 실제로 없는지 본다. 있으면 그 주장은 틀린 말이다. 채점자 자신이 "설명서에 없다"고 판단할 때도 같은 방법으로 확인한다.
4. **Blender 동작 주장은 확인한다**: 계산(회전 각도 등)은 상태 값으로 따져 보고, 필요하면 화면 없는 Blender로 실제로 해 본다. 짐작으로 틀렸다고 하지 않는다.
5. **상태 읽기**: 답이 말한 숫자·이름(선택 수, 배율, 활성 물체)을 작업 상태 JSON과 대조한다.
6. **연습 과정 권하기**: 2절 표대로. `답.jsonl`의 `답에 나온 연습 과정`을 본다.
7. **원인은 근거와 함께**: 검색 결과 목록과 정답 조각의 실제 글을 보고 6가지 중 하나로 나눈다. **검색 적중은 답에 필요한 내용이 든 조각이 실제로 들어왔을 때만** 인정한다(필요한 조각이 둘이면 둘 다). 프로그램의 적중(쪽·소제목 주소 기준)이 적중이라 해도 따로 본다.
8. **애매하면 판단 대상으로 표시**하고 이유를 적는다. 혼자 정하지 않는다.
9. 고치기 판단에 쓸 실패는 표시해 둔다: 그림을 봐야 답할 수 있는 질문의 실패(캡션 없는 그림 설명 추가 판단, 티켓 7), "X가 뭐야"형 실패(용어집 쪽 범위, 티켓 30), 옵션 하나를 콕 집은 질문의 검색 실패(티켓 19), 범위 밖 한국어 질문의 적중(전체 번역 판단, 티켓 6), 엉뚱한 연습 과정 권하기(티켓 29).

## 5. 장면(작업 상태)을 만들 때

1. 연습 과정 단계 문항이면 그 단계 **앞 단계까지 실제 Blender에서 따라 한 결과**와 같은가. 연습 과정 파일(`courses/*.yaml`)의 '쉬운 설명'·'안내'가 말하는 화면(예: 합친 뒤 재질 목록의 빈 칸)이 장면에 있는지 본다.
2. **장면 스크립트는 사람이 누르는 것과 같은 Blender 기능(연산자)으로 만든다.** 저장된 값(선택 표시 등)을 직접 고치지 않는다. 직접 고치면 손으로는 생길 수 없는 상태가 남는다(예: 점은 1개만 골라졌는데 모서리 6개가 골라짐으로 저장돼, 편집 모드로 열면 점 5개가 됨).
3. 실제로 막혔던 질문은 **비슷하게** 만든다. 사진과 똑같이 맞출 필요는 없지만, 사람이 손으로 만들 수 있는 상황이어야 한다(사용자 "완전히 똑같게 하는건 별로인듯 … 비슷하게만 하는 지금이 나아").
4. 질문 글이 장면 그림과 맞는가(질문은 "안 보여요"인데 그림에는 잘 보이는 식이면 고친다).
5. 그림을 눈으로 본다. 재질 색·셰이딩·모드가 의도대로 찍혔나(머티리얼 미리보기는 준비에 시간이 걸린다).
6. **장면 확인**: 상태 JSON이 그림(PNG)과 맞는지 대조한다(명세의 "상태 읽기 맞음/틀림"은 이것. 4절 5번과 구분한다).
7. 문항의 핵심·장면 설명이 장면과 연습 과정 글에 맞는가.

## 6. 재기와 숫자

- **고치기 전** 기준은 1회차만 채점한다.
- **고치는 중**에는 고친 문항만 3번씩 돌려 효과를 본다. 이 숫자는 결과표에 넣지 않는다.
- **결과표에 넣는 숫자**는 고치기를 한 묶음 끝낼 때마다 개발셋 전체를 1번 돌린 것이다. 분모가 고치기 전과 같고, 고친 것이 다른 문항을 망가뜨렸는지도 본다.
- 숫자마다 분모를 적고, 결과표 머리글에 채점자를 적는다(검색 적중 = 프로그램, 개발셋 답 = AI, 홀드아웃 답 = AI와 사용자 블라인드).
- **근거 표시 정확도**(답 끝 근거 링크가 답을 실제로 뒷받침하나)는 새 개발셋부터 잰다.
