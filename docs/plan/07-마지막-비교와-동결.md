### 4. 마지막 비교 (유료, 승인 뒤)

`experiment-checklist` 스킬의 실행 전 목록을 `docs/experiment.md`에 채운 뒤 돌린다.

- 54문항 × 5회 × 2판 = 540답. 판 순서는 되풀이마다 돌린다. 01의 기록(보낸 글, 시각, 토큰)을 남긴다.
- 채점: 판 이름을 가리고 섞어 묶는다. 채점자는 `answer-grader`(Sonnet 5.5, 노력치 medium, HISTORY [413]). **이중 채점**(같은 답을 서로 다른 채점자 둘이 따로 매긴다)이고, 숨긴 중복 답을 넣어 그 회의 채점 일치를 낸다. 채점자가 모델에 넘어간 글 전체를 받게 한다.
- `풀이.json`은 채점자가 쓰는 폴더 밖에 둔다. 채점자마다 임시 폴더를 따로 준다.
- 판 이름을 가려도 글투와 길이로 판을 짐작할 수 있다는 기록이 있다(`docs/experiment.md`의 지난 채점 절). 새 뼈대의 답이 지금 답과 길이·꼴이 눈에 띄게 다르면 그 사실을 결과에 적는다.
- 판정은 실행 전에 적는다. 넣을 것: ① 문항마다 5회 중 3회 이상 맞은 문항 수(두 채점이 갈린 답을 어떻게 셀지 먼저 정한다. 지난 기준은 "낮은 쪽") ② 평균 ③ 차례 단위 부호 검정(같은 문항의 되풀이는 독립이 아니다) ④ 지금 판에서는 3회 이상 맞았는데 고른 판에서 떨어진 문항 목록 ⑤ 첫 글자 시간. ⑤는 어느 차례를 셀지 실행 전에 정한다: 04에서 같은 엔진을 5초 안에 다시 부른 차례는 연결이 살아 있어 약 0.15초 빨랐다(쉰 시간 표, `docs/experiment.md` 04 실행 뒤 절, [488]). 실제 사용은 질문 사이에 오래 쉬므로 쉰 시간 5초 넘는 차례를 따로 낸다.
- 분야 고르기를 뺄지: ④의 목록에서 분야 묶음 줄이 가던 문항이 몇 개 떨어졌는지 세어 사용자에게 보이고 정한다. **두기로 하면** 06의 "옛 HANDOFF의 후보" 표 마지막 줄(질문 바꾸기와 동시에 시작해 약 1초 줄이기, 등급 없는 묶음 다시 만들기 [271])을 다시 꺼내 사용자에게 보인다.
- 결과를 사용자에게 보인다. 고른 판이 낫지 않으면 무엇을 얼릴지 사용자와 정한다(지금 판을 얼릴 수도 있다).

## 하지 말 것

- 봉인한 문항 자료를 열지 않는다. 여기서는 실행기를 개발 문항으로만 점검한다.
- 얼린 뒤에 제품 코드를 고치지 않는다.
- 봉인한 문항의 질문·정답을 개발 쪽 기록(HISTORY, 실험 기록의 개발 절, 지시문, 규칙)에 옮기지 않는다. 세션 기록을 찾을 때 제외 낱말은 `holdout,홀드아웃,봉인`이다.
- 한 번 돌린 54문항 점수로 판을 견주지 않는다.
- 채점 기준을 느슨하게 바꾸지 않는다(사용자가 엄격 채점을 정했다, HISTORY [318]).
- 채점은 `docs/agents/grading.md` **11-19 판**으로 한다([525]). 채점 지시문은 `data/eval/dev50/ceiling05_grade_instructions.md`를 그대로 쓰지 말고 고쳐 만든다: "Blender 동작은 조각 파일 … 로 확인 … [확인]" 줄을 grading.md 4절 4번의 확인 뜻으로 바꾸고, 결과 표에 '핵심 밖 동작 주장'·'막힘 메모' 칸을 더한다. `.claude/agents/answer-grader.md`도 같은 말이 있는지 본다.
- 날짜가 모자라다고 되풀이 횟수·문항·이중 채점을 스스로 줄이지 않는다. 줄이려면 줄일 것과 잃는 것을 보이고 사용자에게 묻는다.

- 파일을 지우지 않는다. 지울 것은 `/Volumes/mac_ssd/proj/trash/<날짜>/<시각>_<이름>`으로 옮기고 `trash/기록.txt`에 한 줄 적는다(`rm`은 훅이 막는다).
- 결과는 `results/<날짜>/<시각>_<이름>/`에 새로 남기고 덮어쓰지 않는다. 백그라운드 "완료" 알림을 믿지 말고 결과 파일의 줄 수를 직접 센다.
- 끝났다고 말하기 전에 끝 조건마다 돌린 명령과 출력을 보인다. 숫자에는 분모·채점자·실행 횟수를 붙인다.
- 결정·결과가 생기면 `HISTORY.md` 끝에 새 번호로 적는다(사용자 말은 그대로 인용). 프로그램 파일이나 주고받는 모양이 바뀌면 `STRUCTURE.md`도 같은 변경에서 고친다.
- main 병합은 사용자 확인 뒤에 한다. 병합한 브랜치는 `MERGED`를 확인한 뒤에만 지운다.
- 판단이 갈리면(확인이 예상과 다르게 나옴, 문서와 실제가 다름, 둘 중 무엇을 고를지) 추측으로 넘기지 말고, 사용자를 기다리지도 않는다. 본 것을 그대로(기대하는 답은 빼고) Fable 5.2 판단 에이전트(노력치 high)에게 주어 판단을 받고 그대로 진행한다. 판단과 근거는 `HISTORY.md`에 적어 마지막에 한 번에 보인다. 이것은 `AGENTS.md`의 "하위 에이전트 노력치는 medium 이하, high 이상은 사용자가 명시적으로 요청했을 때만"에서 사용자가 명시적으로 요청한 경우다(HISTORY [463]). 판단 에이전트 말고는 medium 이하 그대로다. Fable을 쓸 수 없는 도구에서는 그 도구에서 가장 높은 모델에 맡긴다.
- 판단 거리가 아닌 것은 멈추고 사용자에게 알린다: 필요한 자료나 파일이 없음, 훅이나 권한이 막음, "열지 않는 것"에 닿음.
- 사용자에게 먼저 묻는 것: 이 문서의 "사용자에게 물을 것", 돈 드는 실행, main 병합, 삭제, 봉인한 문항 열기, 사용자가 이미 정한 것(목표, 엄격 채점)을 바꾸는 일.
