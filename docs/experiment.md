- 기존 입력: 현재 제품의 질문 바꾸기 입력(질문과 기존 맥락; 맥락은 직전 질문·연습 단계·최근 조작). ‘질문만’이라는 표현 때문에 기존 맥락까지 없애지 않는다.
- 가 원형: 오늘 시험은 기존 지시문을 그대로 두고 사용자 글 끝에 늘 보내는 설정 값을 더했음. 사용자 "가 방식의 프롬프팅도 질문 바꾸기랑 동일한 프롬프트는 안 될거 같네" → 다음 지시문은 설계해야 하며, 바꾸면 가 개선판으로 구분한다. 원형의 +6을 개선판의 성적으로 쓰지 않는다.
- 단계3의 마지막 호출은 **질문을 주지 않고 작업 상태만 본다**(사용자 "아예 3번은 작업 상태만 보게 하는게 맞는거같음"). 질문을 다시 넣어 가 방식과 겹치게 하지 않는다. 상태의 특징·점검할 원인 후보를 검색어로 만드는 역할이며, 질문을 모르는 상태에서 실제 질문의 원인을 맞혔다고 평가하지 않는다.
- 상태만 보는 호출의 입력 범위(늘 보내는 값과 동일하게 할지 등)·지시문·합치는 구체 규칙·반복 수·통과 기준은 아직 미확정이다. 설계 때 먼저 정한다. 개발 문항별 예외를 제품 규칙에 넣지 않는다.
- 단계1-3은 최종8개 한도·합치는 규칙을 맞춰 입력 구성 차이를 비교한다. 정답 청크가 늘어난 경우뿐 아니라 기존 정답을 잃은 경우·시간·비용을 함께 본다.
- 단계1-3의 질문 바꾸기 호출은 각각3개이고 임베딩도 검색어3개를 대상으로 하지만, 입력·출력 길이에 따라 요금은 달라질 수 있다. 특히 단계3은 상태를 주는 호출이2개여서 단계2보다 입력 요금이 늘 수 있다. 새 시험 예산은 아직 승인받지 않았고 유료 실행하지 않는다.
- 하위 에이전트 금지는 유지한다. 이번 기록은 작업 순서 합의이며 실험 설계 완료·제품 구현·실험 통과를 뜻하지 않는다.

## 검색 개선 1번 설계 · 검색어 세 개의 결과를 합쳐 필요한 설명을 더 받는가 · 2026-11-12

**상태: 아래 추가 합의로 범위·예산을 갱신했다. 1번 실행·전체 채점·자기 검토를 마쳤으며 결과는 아래에 있다.**

### 목적과 이번 범위

사용자: "1,2,3 차례대로 진행하는데 하나끝나고 정리하고 하나진행하고 이렇게 가자고?",
"1번 테스트 돌리고 결과나오면 채점하고 정리해서 기록하고 그 다음 2번 진행하고 이런식으로", 이어 "ㅇㅇ 시작해".
따라서 1번의 설계 → 승인 → 실행 → 검색 본문 채점 → 검토 → 기록을 끝내고 사용자에게 결과를 보인 다음 2번을 설계한다.
2·3번의 지시문과 유료 실행은 이번 준비에 넣지 않는다.
답을 생성하지 않는 **검색 시험**이다. 여기의 충분/일부/없음은 설명 자료의 충분함이고, 실제 답변의 맞음/부분/틀림은 아니다.

이전 결정은 HISTORY [170]의 "후보 1순위 3개합치기", [282]의 "1번 기존 방식 3개 결과 합치기"다.
보관본 `archive/experiment_E2.md`의 검색 가설8은 luna에서 세 검색의 상위50개 합치기를 택했다:
"3개 합치기(나)는 같은 검색어로 견주어 가보다 +2·+3개, 더 기다리는 시간은 중앙 0.16초다."
지금은 Haiku 5.5이고 당시 지표는 받은 청크 수여서 이 숫자를 새 시험의 기대값이나 합격 기준으로 옮기지 않는다.

### 채점과 판정 제안

**숫자 기준은 모두 이번 Codex의 제안값이며 아직 사용자 승인값이 아니다. 결과 계산 전에 이 절을 보인다.**

- 주 지표: 정답 위치가 있는49개 ×3회 = **147건**에서, 최종8개 본문만으로 질문에 필요한 설명을 모두 제공하는 `충분` 건수. 핵심 가운데 조작·기능 설명은 본문에서 근거를 표시하고, 사용자 상태의 사실은 자료에 없는 설명을 꾸며 채우지 않는다. 필요한 설명 일부만 있으면 `일부`, 없으면 `없음`, 애매하면 `보류`. 충분함이 늘어야 답 모델에 줄 자료가 실제로 늘었다고 볼 수 있다.
- 보조 지표: 등록된 정답 주소 하나 이상/등록 주소 전부를 받은 건수, 문항별 개선·악화·동일, 반복별 수, 앞12판의 늘 받음·흔들림·못 받음 분류별 변화. `evaluate.hit`는 **주소 하나 이상**만 세므로 이 자동 숫자를 주 지표로 쓰지 않는다. 등록 주소가 대안인지 여러 필수 근거인지도 본문으로 판정한다.
- 주 채점은147건 양쪽 최종8개를 **전부** 본다. 개선·악화만 골라 채점하지 않는다. 같은8개 조합은 한 번 읽은 판단을 재사용할 수 있지만 모든 질문·반복에 판정과 본문 근거를 남긴다. 질문별 표에 양쪽 충분/일부/없음/보류와 바뀐 까닭을 적는다. `docs/agents/grading.md` 4절7번을 따른다.
- 정답 위치가 없는5개(Q15·Q39·Q42·Q48·Q49)도3회씩 검색하고15건 모두 본문을 읽어, 가까운 설명/필요한 정보 없음/관련 없는 내용으로 기록한다. 정답 주소가 없다는 이유로 검색 결과가 무조건 없어야 한다고 하지 않는다. 자동 적중147건의 분모에는 넣지 않고 전체54개·162건의 속도·실패·비용에는 넣는다. 이5개에 방향을 잘못 이끌 만한 변화가 있으면 처리와 이유를 정하기 전 통과로 닫지 않는다.
- 제품에서 따로 붙는 연습 단계의 먼저 볼 소제목과 짧은 조각 주변 보완은 최종8개와 구분해 보관한다. 주 지표는 검색8개만으로 채점하고, 제품 보완본문을 읽었을 때 판단이 달라지는지도 별도 기록한다. 먼저 볼 소제목 덕분의 성공을 검색 개선으로 세지 않는다. 연습 과정 추천·설정 묶음 전달·실제 답 품질은 이번 시험 밖이다.
- **효과 기준 제안:** 충분 건수의 합친 방식−기준 방식이 **+8건 이상 /147건**(약5.4%p), 반복별 순증가가3번 모두0 이상이고 그중2번 이상 양수. 49질문을 단위로3회 묶음을 함께 다시 뽑는95% 구간도 보고한다(씨앗20261112,10000회). 반복147건을 서로 독립인147질문이라고 보지 않는다. +8은 실용적인 개선 폭으로 이번에 제안한 값이며 이전 가 시험의 통과 기준을 승인된 값으로 가져온 것이 아니다. 원리상 차이는−147-+147 범위라 기준에 닿을 수 있으나, 실제 자료에서의 여유 폭은 실행 뒤 별도로 본다.
- **시간·안정 기준 제안:** 두 방식 모두 검색을 마친 짝에서 질문별 시간 차이의 중앙값 **+0.5초 이하**, 느린 쪽10% 지점 **+1초 이하**. 짝을 이루지 못한 경우도 전체162건 표에 실패로 남기고, 합친 쪽에서 새로 생긴 검색 실패가 **2건 이하**여야 한다. 시간 숫자는 기다림 증가를 제한하기 위한 제안값이고 제품의 전체 속도 목표를 대체하지 않는다.
- **판정 후 행동:** 효과·시간·안정 기준을 만족하고95% 구간의 하한도0보다 크고, 본문 `보류`와5개 정답 위치 없는 질문의 변화 처리가 끝나면1번을 잠정 후보로 남기고 기록을 정리한 뒤2번을 설계한다. 양수라도 기준에 못 닿거나95% 구간이0을 포함하면 개선을 확정하지 않고 불확실성을 기록한다. 충분 건수가 늘지 않거나 시간·안정 기준이 미달이면1번을 제품 채택 후보로 올리지 않고 실패 원인을 기록한 뒤2번의 비교 계획을 보인다. 어느 경우에도 제품 반영·유료 재시험·합치는 규칙 변경을 자동으로 하지 않는다.
