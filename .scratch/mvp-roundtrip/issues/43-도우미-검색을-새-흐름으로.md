## 배경

- 지금 도우미: 질문 + 메뉴 이름 덧붙이기 → large 임베딩 → 뜻 검색(BM25 끔) → 상위 6개([102]·[107]).
- 정한 흐름: 질문 → luna(생각 none) 질문 바꾸기 3번 동시 → 검색어 3개를 large 임베딩 한 번에 → 설명서 전체 뜻 검색 × 3 → RRF로 합쳐 상위 8개.
- **바뀐 흐름([127])**: 질문 → luna(none, 지금의 긴 지시) 3번 동시 → **먼저 온 1개**의 검색어만 large 임베딩 → 설명서 전체 뜻 검색 → 상위 8개. 예열은 옵션(기본 끔).
- 실측(`search_compare flow`, W1-W10 × 3회, [122]): 질문 넣고 상위 8개까지 중앙 2.53초·최대 5.95초, 시간의 약 86%가 luna 호출. 한 번 바꾸기는 중앙 2.15초.

## 할 일

1. **(완료, [127])** **2초 안 찾기(먼저)**: 같은 20문항으로 질문 바꾸기 시간과 기능 이름 품질을 잰다. `search_compare`의 `rewrite`/`flow`를 늘려 쓴다. 후보:
   - 분야 목록(68개)과 areas·exclude 칸을 뺀 짧은 지시(출력이 줄어듦)
   - 연결 다시 쓰기(지금은 호출마다 새로 연결, [125] 19번)
   - luna보다 작고 빠른 OpenAI 모델이 있는지 확인(리서치에서 확인 못 함), Haiku 5.5(키·회사가 하나 더 느는 부담 포함)
   - 유료 측정은 어림 비용을 보이고 확인받는다.
2. 도우미(`answer_engine`)에 새 흐름을 넣는다: 메뉴 이름 덧붙이기 빼기, 질문 바꾸기 3번 동시·먼저 온 1개, 상위 8개, 예열 옵션(기본 끔). 질문 바꾸기 모델은 OpenAI 방식 채팅 주소로 불러 나중에 로컬(llama-server, 티켓 42)로 바꿔 끼울 수 있게 둔다.
3. RRF를 `answer_engine`의 함수 하나로 합치고 `search_compare`가 그것을 쓴다(같은 점수 순서 기준 하나로, [125] 7번). [127]로 도우미가 검색어를 합치지 않게 되어 필요한지 다시 묻는다.
4. 질문 바꾸기가 실패·시간 초과일 때 도우미가 어떻게 할지(원래 질문으로 찾기 등)를 정해 사용자 확인.
5. 도우미 창에서 실제 질문으로 시간을 잰다(질문 준비 시간 목표는 1번 결과로 사용자와 다시 정한다).
