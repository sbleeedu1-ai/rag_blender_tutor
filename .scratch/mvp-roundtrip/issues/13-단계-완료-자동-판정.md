# 단계 완료 자동 판정

Type: grilling
Status: resolved
Blocked by: 08

## Question

단계가 끝났는지를 작업 상태로 자동 판정할 것인가? 한다면 어떤 단계까지, 어떤 상태 값(모드·선택 물체·물체 수·모디파이어 등)으로, 치수는 얼마나 느슨하게 보는가?

## 다른 티켓에서 넘어온 것

- (연습 과정 고르기) 진행 기록과 완료 판정은 단계 단위. 치수는 참고로만 두고 엄격하게 따지지 않는다
- (애드온 왕복 시제품) 모드·선택 물체·화면 언어는 애드온이 바로 읽는다(약 0.004ms). 물체 이름은 한국어 화면에서 한국어로 바뀔 수 있어("실린더") 이름으로 판정하면 위험하다
- (애드온 ↔ 서버 형식) 작업 상태에 이미 오는 칸: 모드, 활성 물체 종류·모디파이어 종류·배율·크기, 선택 물체 수, 편집 모드 선택 방식과 고른 개수, 장면 물체 수, 방금 실행한 조작 3개. 판정에 더 필요한 칸은 여기서 정해 더한다
- (대화 기억 범위) 진행 기록은 파일 경로마다 하나(현재 단계, 끝낸 단계 목록). 단계가 무엇으로 넘어가는지(자동 판정, 사용자가 누름, 둘 다)를 여기서 정한다

## Answer

2026-10-19 사용자와 질문 라운드(Q1-Q9)로 정함. 근거: 강좌 대조 조사(`research/03-course`)의 검·방패 단계 초안을 단계마다 "작업 상태로 알아챌 단서"로 훑음. glTF 내보내기 조작(`export_scene.gltf`)은 설치본 Blender 5.2에서 `bl_options = {'REGISTER', 'UNDO'}`를 확인(조작 기록에 남을 것으로 봄).

| 항목 | 결정 |
|---|---|
| 넘어가는 방식 | **자동으로 알아채서 묻기 + 버튼.** 끝난 조건이 맞으면 도우미 창이 "…한 것 같아요. 다음 단계(…)로 갈까요? [네] [아니요]"를 묻고, "네"를 눌러야 넘어간다. "다음 단계" 버튼은 언제나 쓸 수 있다. 진행 기록에는 사용자가 확인한 것만 남는다 |
| 판정하는 곳 | 도우미 창이 작업 상태를 받을 때마다 **AI 없이 정해 둔 조건**으로 맞춰 본다(비용 0, 즉시). 답 엔진은 그대로 아무것도 기억하지 않는다 |
| 조건 범위 | **지금 단계의 조건만** 본다(앞 단계 일을 미리 해도 알아채지 않음, 버튼·건너뛰기로). 조건은 가능하면 "방금 실행한 조작"과 묶는다. 예: 기본 정육면체는 처음부터 배율 1이므로 크기 확정은 "방금 Apply Scale + 배율 1,1,1" |
| 판정 붙이는 단계 | 단서가 있는 단계는 확실한 정도 높음·중간 모두 붙인다(틀려도 손해는 "물어보고 거절당함"). 끝난 조건은 연습 과정 파일에서 단계마다 **있어도 없어도 되는 칸**. 없으면 버튼만 |
| 치수 | **비율로만**(예: 칼날은 가장 긴 축이 두 번째 축의 3배 이상). 절대 숫자로 따지지 않는다 |
| 더할 작업 상태 칸 | **활성 물체의 재질 슬롯 수** 하나(색 입히기 단계). 나머지 검·방패 단계는 기존 칸으로 된다: 칼끝 모으기 = 편집 모드 + 방금 Merge, 부품 추가 = 장면 물체 수, 합치기 = 방금 Join, Solidify·Array = 모디파이어 종류(Array 원형 설정까지는 안 봄), 내보내기 = 방금 Export glTF(실제로 잡히는지 구현 때 확인, 안 잡히면 버튼만) |
| 묻는 방식 | ① 도우미 창 안에만 띄우고 창을 앞으로 끌어오지 않는다 ② 답하기 전에 조건이 깨지면(Ctrl+Z 등) 물음을 거둔다 ③ 한 단계에 한 번만 묻고, 거절하면 그 단계에서는 버튼으로만 ④ 넘어간 뒤 되돌려도 진행 기록은 그대로, 뒤로 가기는 건너뛰기로 |
| 판정 검수 | 명세 단계의 "검 따라 하기 검수" 때 (1) 물음이 뜬 순간마다 "방금 그 단계를 끝냈나" O/X 표시 (2) 도우미 창이 받은 작업 상태 흐름을 파일로 남겨, 조건을 고친 뒤 Blender 없이 다시 돌리는 자동 테스트로 쓴다(API 키 불필요, 개발용 평가와 따로). Blender 지식 없이 사용자가 검수할 수 있게 하려는 것 |
| 범위 밖 | 그림 비교 판정(사용자 제안: 저작권 없는 검 그림과 비슷한지). 화면 캡처 + 비전 AI 호출이 상태가 바뀔 때마다 들어 비용·속도 문제이고 "스크린샷 없이 빠르다"는 핵심 근거와 어긋나며, 화면 각도·색 차이로 틀리기 쉽고, "치수는 참고로만"과 부딪히고, 합치기·크기 확정처럼 그림이 안 바뀌는 단계가 있다. 단계마다 목표 모습 그림 보여 주기도 MVP 밖 확장 |

ADR은 만들지 않음: 조건과 묻는 방식은 나중에 바꾸기 쉽다. 용어집에 「끝난 조건」을 더함, 「작업 상태」 정의를 11칸 형식에 맞게 고침.
