### 1. 지금 시간이 어디에 쓰이나 (기록 다시 계산)

### 2. (권함 1) 흘려 받아 `query`가 닫히면 바로 끊기

**근거**
- [확인] 우리 지시는 이미 `{"query": ..., "areas": ..., "exclude": ...}` 순서로 쓰라고 한다(`blender_tutor/answer_engine.py`의 `REWRITE_PROMPT`). 모델은 앞에서부터 한 토큰씩 쓰므로, 뒤의 areas·exclude는 앞의 query 글을 바꾸지 않는다. 즉 **짧은 지시처럼 품질을 잃지 않고, 출력 뒷부분 생성 시간만 건너뛴다.**
- [확인] luna는 흘려 받기와 structured outputs를 지원한다([gpt-6-luna 모델 쪽](https://developers.openai.com/api/docs/models/gpt-6-luna)).
- [확인] JSON 모드(`json_object`)는 칸 순서를 보장한다는 말이 문서에 없다. Structured Outputs(`json_schema`, strict)는 "출력이 스키마의 키 순서대로 만들어진다"고 쓴다. 대신 "어떤 스키마든 첫 요청은 스키마 처리로 지연이 더 있고, 같은 스키마의 다음 요청은 없다"([Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)).
- [확인] 우리 답변 모델 코드(`blender_tutor/answer_model.py`)가 이미 Chat Completions 흘려 받기를 읽으므로 같은 방식을 쓸 수 있다.

**우리 흐름에 넣는 모양**
- `OpenAIModel.ask`에 `stream: True`를 주고, 조각을 이어 붙이다가 `"query": "...."`의 닫는 따옴표가 나오면 그 글을 꺼내 바로 돌려준다. 연결은 닫는다(남은 조각을 읽지 않음).
- 3번 동시 호출의 "먼저 온 1개"는 "먼저 query를 닫은 1개"가 된다.
- 칸 순서: 먼저 `json_object` 그대로 두고 실제 순서를 센다. query가 첫 칸이 아닌 답이 섞이면 `json_schema`(query 첫 칸)로 바꾼다. 스키마 첫 요청 지연은 도우미를 켠 뒤 첫 질문에 한 번 붙는다는 점을 함께 잰다.

**비용**: 같거나 조금 준다. [추측] 연결을 끊은 뒤 서버가 생성을 바로 멈추는지는 문서에서 찾지 못했다. 멈추지 않아도 지금과 같은 값이다.

**품질 위험**: 거의 없다. 다만 (1) query 안에 `\"` 같은 이스케이프가 나오면 닫는 따옴표 찾기가 틀릴 수 있으니 JSON 문자열 규칙대로 읽어야 하고, (2) 끊으면 JSON 전체 검사를 못 하므로 "query가 비었나·글자인가"만 본다.

**확인 실험**(약 $0.005): 긴 지시, W1-W10·A1-A10 × 1회, 질문마다 3호출 동시. 호출마다 `보냄`, `첫 조각`, `query 닫힘`, `끝` 시각과 `usage`(흘려 받기에서 `stream_options.include_usage`)를 남긴다. 보는 것:
1. `query 닫힘 − 보냄`이 `끝 − 보냄`보다 얼마나 짧은가(중앙·90%).
2. `첫 조각 − 보냄` = 고정 시간. 이것이 1초 근처면 나머지 방법(출력 줄이기 등)의 한계가 보인다.
3. query가 첫 칸인 비율(180개 중).
4. `reasoning_tokens`가 0인지(none이 정말 생각 토큰을 안 쓰는지 확인).
5. 검색어 글이 흘려 받지 않은 때와 같은 분포인지(같은 질문의 검색어 3개 비교, 적중은 상위 8개로).

### 3. (권함 2) 첫 질문이 1초 느린 까닭 가르기

**지금 아는 것**
- [확인] 첫 요청은 luna 3.5-4.4초, 임베딩 1.86초로 늦었다([127]). 도우미 창에서도 첫 질문 +약 1초([130]·[131]). luna와 임베딩 **두 주소가 모두** 첫 번째만 늦다.
- [확인, 이 PC에서 무료로 잼] 파이썬 쪽 준비는 작다: SSL 설정 만들기 0.015-0.019초, DNS 첫 조회 0.010초(다음은 0.0003초), 프록시 설정 읽기 0.0001초. TCP+TLS 연결은 [127]에서 0.03초. → 우리 PC 쪽 준비만으로는 1초가 설명되지 않는다.
- [추측] TLS가 0.03초면 한국 근처 중계 서버(CDN 가장자리)에서 연결이 끝난다는 뜻이고, 거기서 미국의 OpenAI 서버까지는 따로 간다. 한동안 요청이 없으면 그 뒤쪽 길·인증 정보 캐시가 식어 첫 요청이 느릴 수 있다. 두 주소가 모두 늦은 점과 맞지만 확인하지 않았다.

**무료 실험**: 새 파이썬 프로세스에서 `GET https://api.openai.com/v1/models`(토큰 요금 없음)를 5번 연속, 10분 쉬고 다시 5번. 첫 번째만 약 1초 늦으면 모델이 아니라 연결·경로·계정 쪽 원인이다. 같은 프로세스에서 이어서 luna를 한 번 불러(약 $0.0001) 첫 luna가 여전히 늦은지도 본다.

**결과에 따른 모양**: 원인이 경로 쪽이면, 도우미를 켤 때 또는 F10을 누를 때 **모델 목록 요청 하나**(무료, 사용자 글을 보내지 않음)로 길을 열어 두는 방법이 있다. 사용자는 예열을 "몰래 처리한다는 인상"으로 옵션으로만 두기로 했으므로([127]), 이것도 사용자에게 다시 묻는다. 효과는 첫 질문만이고 중앙값은 그대로다.

**참고 [확인]**: GPT-5.6 이후 모델은 Responses API에서 `prompt_cache_options.prewarm: true`로 출력 없이 캐시만 미리 채울 수 있고, 그 토큰은 캐시 쓰기 값으로 매긴다([Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)). 그러나 우리 입력은 1,024토큰보다 짧아 캐시 자체가 안 걸린다(4번). WebSocket 모드에도 `generate: false`로 "다음 차례가 더 빨리 시작하게 요청 상태를 준비"하는 기능이 있다([WebSocket mode](https://developers.openai.com/api/docs/guides/websocket-mode)).

### 4. (권함 3) 동시 호출 수 늘리기

- [확인] 기록에서 실제로 본 값: 호출 하나 중앙 1.52초·90% 1.87초, 3개 중 먼저 온 것 중앙 1.41초·90% 1.60초. 같은 질문 안 3호출의 차이(가장 늦은 것 − 가장 빠른 것)는 중앙 0.32초.
- [어림] 호출 180개에서 아무렇게나 뽑아 "k개 중 가장 빠른 것"을 2만 번 흉내 내면 중앙 1개 1.53 / 3개 1.37 / 4개 1.33 / 5개 1.30 / 6개 1.29초, 90% 지점 1.90 / 1.56 / 1.48 / 1.44 / 1.42초. 실제 3개 값(1.41)이 흉내 값(1.37)보다 늦은 것은 같은 순간의 호출끼리 함께 느려지기 때문이므로, 5개의 실제 이득은 흉내보다 작다: 중앙 약 −0.05초, 90% 약 −0.1초.
- 비용: luna 한 호출 약 581×$0.10 + 45×$0.50 = 약 $0.00008. 3개 $0.00024 → 5개 $0.0004. 답변 모델(질문당 약 $0.0003, [131] 10문항 $0.0030)까지 합친 질문당 비용은 약 +30%로, 10배 기준에 한참 못 미친다.
- [확인] luna 기본 한도는 분당 5,000요청(Build 등급)이라 한도 걱정은 없다([모델 쪽](https://developers.openai.com/api/docs/models/gpt-6-luna)).
- 확인 실험(약 $0.01): 1번 실험과 함께 같은 질문을 5호출로도 보내, 먼저 온 1개·먼저 query를 닫은 1개 시간을 3호출과 견준다.

### 순위에서 내린 방법

#### 프롬프트 캐시 — 지금은 걸리지 않고, 걸려도 시간 이득이 작다 (비용 쪽 이야기)

- [확인] GPT-5.6 이후 최소 캐시 길이 1,024토큰. 앞부분 전체가 똑같아야 적중. luna 캐시 읽기 $0.01(입력의 10%), 30분 캐시 쓰기 $0.125(1.25배), 12시간 쓰기 $0.25. 캐시는 서버 한 대에 머물고, 같은 앞부분이 분당 15요청을 넘으면 다른 서버로 넘칠 수 있다. GPT-5.6 이후 `prompt_cache_key`는 주로 고객별 계산을 나누는 용도. 캐시가 "입력 처리 시간을 줄인다"고 쓰지만 수치는 없고, "모든 요청이 더 빨라짐을 보장하지 않는다"([Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching), [가격](https://developers.openai.com/api/docs/pricing)).
- [확인] 질문 바꾸기 입력은 약 581토큰(0번) → **지금 캐시가 걸리지 않는다**. 답변 모델도 앞쪽 고정 지시(`INSTRUCTIONS`, 447글자)가 짧고 그 뒤는 질문마다 다른 청크라 걸리지 않는다.
- [어림] 지시를 1,024토큰 넘게 늘려 캐시를 걸어도, 공식 안내상 입력 처리는 지연의 작은 몫(입력 절반에 1-5%)이라 0.05초 안팎 이득으로 본다. 오히려 늘린 지시가 품질을 바꿀 수 있다(짧은 지시에서 품질이 떨어졌던 것처럼, [127]). → **시간 목표에는 거의 도움이 안 되어 내렸다.** 실제로 재고 싶으면 `usage.prompt_tokens_details.cached_tokens`로 적중을 확인하며 10호출씩 견주면 된다(약 $0.002).

#### Predicted Outputs — luna 미지원
- [확인] 지원 모델은 gpt-4o·4o-mini·4.1·4.1-mini·4.1-nano뿐이고, 맞히지 못한 예측 토큰도 출력 값으로 매긴다([Predicted Outputs](https://developers.openai.com/api/docs/guides/predicted-outputs)). 게다가 검색어는 질문마다 달라 미리 알 수 있는 출력이 아니다.

#### Realtime API — luna 미지원
- [확인] luna 모델 쪽에 Realtime "Not supported"([모델 쪽](https://developers.openai.com/api/docs/models/gpt-6-luna)).

#### 지역 처리(데이터 레지던시) — 한국에서 처리하는 곳이 없다
- [확인] `kr.api.openai.com`·`jp.api.openai.com`은 **저장만** 그 지역이고 처리는 아니다. 처리까지 지역에서 하는 곳은 미국·EU·UAE뿐. 미국 밖 지역은 별도 승인(abuse monitoring 통제·보존 계약 수정)이 필요하다([Your data](https://developers.openai.com/api/docs/guides/your-data)). 지역 처리 주소는 3월 5일 이후 출시 모델에 10% 할증([가격](https://developers.openai.com/api/docs/pricing)). → 한국 사용자 지연을 줄일 길이 아니다.

#### Fast(옛 이름 Priority) — 이미 잼, 다시 볼 여지는 조금
- [확인] Priority는 2026-07-30에 Fast로 이름이 바뀌었고, luna Fast는 2배 값($0.20/$1.00), 문서는 "최대 2.5배 빠름"([가격](https://developers.openai.com/api/docs/pricing), [Fast mode](https://developers.openai.com/api/docs/guides/fast-mode)). 몰리면 기본 속도로 내려가고 응답에 `default`로 표시된다.
- [확인] 우리 측정: 짧은 지시에서 중앙 1.37 → 1.23초(약 10%), 30개 모두 fast 처리([127]).
- [어림] 질문 바꾸기에만 쓰면 질문당 +$0.00024(답변 합친 질문당 약 +45%)에 약 −0.13초, 답변 모델에도 쓰면 첫 조각 −0.07초 안팎(10% 가정). 10배 기준 안이라 비용 위험은 아니다. 사용자가 "비용 때문에 그닥"으로 내렸던 것이므로, 1-3번 뒤에도 2초에 못 미치면 다시 물을 후보로만 적는다.

#### Flex — 더 느리다
- [확인] luna Flex는 Batch와 같은 반값([가격](https://developers.openai.com/api/docs/pricing)). 느린 처리를 받아들이는 대신 싼 등급이라 우리 목표와 반대.

#### Responses API로 옮기기 — 우리 한 번짜리 호출에는 이득 근거가 없다
- [확인] OpenAI는 Responses가 Chat Completions보다 캐시 활용이 40-80% 낫다고 쓰지만(내부 시험), 이유는 여러 차례 대화에서 생각 항목을 이어 붙여 캐시가 끊기지 않기 때문이다([Migrate to Responses](https://developers.openai.com/api/docs/guides/migrate-to-responses), [Reasoning items cookbook](https://developers.openai.com/cookbook/examples/responses_api/reasoning_items)). 우리 질문 바꾸기는 한 번짜리이고 캐시 최소 길이에도 못 미친다. 한 번짜리 호출의 지연 차이를 다룬 공식 숫자는 찾지 못했다.

#### WebSocket 모드 — 효과 미확인, 순위 밖 실험 후보
- [확인] Responses API에 연결 하나를 열어 두고 새 입력만 보내는 방식. "도구 호출이 20번 넘는 흐름에서 끝까지 시간이 최대 약 40% 빨라졌다." 연결 하나에 동시 진행 응답 16개까지, 60분 뒤 다시 연결. `generate: false`로 요청 상태를 미리 준비할 수 있다([WebSocket mode](https://developers.openai.com/api/docs/guides/websocket-mode)).
- [추측] 이득의 출처는 긴 사슬에서 대화 전체를 다시 보내지 않는 것이다. 우리는 연결 맺기가 0.03초라 연결 쪽 이득은 없다. 서버 쪽 요청당 준비 시간이 줄어드는지는 문서에 없다. 1-3번 뒤에도 모자라면 같은 20문항으로 HTTP와 WebSocket의 첫 조각 시간을 견줘 볼 수 있다(약 $0.005, 웹소켓 라이브러리 필요).

#### `max_tokens`(출력 한도) — 안전장치로만
- [확인] 공식 안내는 출력을 줄이는 수단으로 `max_tokens`·stop을 들고, JSON 모드에서 지시가 없으면 "토큰 한도까지 계속 쓸 수 있다"고 경고한다([Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization), [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)). 한도로 자르면 JSON이 깨지므로, 시간 줄이기는 2번(흘려 받아 끊기)이 맞고, 한도는 120토큰쯤의 사고 방지로만.

#### reasoning_effort none
- [확인] luna는 none·low·medium(기본)·high·xhigh·max를 받는다([모델 쪽](https://developers.openai.com/api/docs/models/gpt-6-luna)). none에서 생각 토큰이 실제로 0인지는 우리 기록에 남아 있지 않다(질문 바꾸기 쪽 `reasoning_tokens` 기록 없음). 1번 실험에서 함께 본다.

확인한 날짜: 2026-11-02 · 조사: Claude(Opus 5.5) 하위 에이전트 · 코드를 고치지 않았고 유료 API를 부르지 않았다. 숫자는 저장소에 이미 있는 결과 파일을 다시 계산한 것과 공식 문서·논문에서 읽은 것이다.

판단 기준(조정자 지시): **첫 글자 시간 단축 효과와 적중률 유지가 1순위**, 비용은 질문당 10배 넘게 늘 때만 위험으로 적는다.

표시: **[확인]** 출처나 저장소 결과에서 직접 읽은 사실 · **[계산]** 저장소 결과 파일로 내가 다시 계산한 값(방법을 적음) · **[추측]** 검증하지 않은 판단.

처음 나오는 말 풀이

- **첫 글자 시간(TTFT)**: 질문을 보낸 뒤 화면에 답의 첫 글자가 뜰 때까지 걸린 시간.
- **흘려 받기(streaming)**: 모델이 답을 다 쓸 때까지 기다리지 않고 쓰는 대로 조각조각 받는 것.
- **겹쳐 돌리기(speculative execution)**: 다음 단계에 필요할지 모르는 일을 미리 시작해 두고, 맞으면 쓰고 틀리면 버리는 것.
- **헤지 요청(hedged request)**: 같은 요청을 여러 번 동시에 보내 먼저 온 답을 쓰는 것. 지금 쓰는 "luna 3번 동시 → 먼저 온 1개"가 이것이다.
- **고르기(라우팅)**: 질문 종류에 따라 다른 길로 보내는 것.
- **의미 캐시(semantic cache)**: 전에 받은 질문과 뜻이 비슷한 질문이 오면 저장해 둔 결과를 다시 쓰는 것.
- **예상 질문 색인(doc2query)**: 설명서 청크마다 "이 청크로 답할 질문"을 미리 만들어 함께 검색되게 해 두는 것.
- **RRF**: 여러 순위를 1/(60+순위) 점수로 더해 하나로 합치는 방법.

### 방법별 근거

#### A. 질문 바꾸기를 흘려 받아 query가 닫히면 바로 검색 (권함 1)

- 하려는 일: 지금 `Rewriter.ask`는 답 전체(`{"query": ..., "areas": [...], "exclude": [...]}`)를 받은 뒤 검색어를 꺼낸다. 흘려 받으면서 `"query": "…"`의 닫는 따옴표가 오는 순간 임베딩을 시작하고, 뒤의 areas·exclude는 기다리지 않는다.
- 적중률이 그대로인 이유: [추측이지만 원리상 강함] 언어 모델은 앞에서부터 한 토큰씩 쓰므로, 먼저 쓰는 query는 뒤에 쓸 areas·exclude의 영향을 받을 수 없다. 긴 지시가 짧은 지시보다 잘 찾은 차이(86.7% 대 77.3%, [127])는 **입력**(분야 목록을 보여 주는 것)에서 오고, areas·exclude를 **쓰는 일**에서 오지 않는다. 지시는 그대로 두므로 검색어도 같다. 단, 모델이 JSON 칸 순서를 바꿔 query를 뒤에 쓰는 경우가 있는지는 확인해야 한다.
- 기대 효과 [계산·추측]
  - 출력 토큰 평균: 긴 지시 44.6, 짧은 지시 26.1(124302 `요약.md`의 출력 토큰 ÷ 180). 검색어 낱말 수는 둘이 비슷했다(13.6 대 12.5낱말). 따라서 긴 지시 출력 중 **약 18토큰이 areas·exclude 몫**이다.
  - 호출 하나 중앙값 긴 1.52초 대 짧은 1.35초, 차이 0.17초. 이 차이에는 입력이 약 400토큰 짧아진 효과도 들어 있는데, OpenAI는 "입력을 반으로 줄여도 1-5%"라고 쓰므로 대부분이 출력 몫으로 본다. → **약 0.1-0.15초 단축**.
  - [확인] OpenAI 지연 최적화 안내: "출력 토큰을 50% 줄이면 지연이 약 50% 줄 수 있다"([OpenAI latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization), "Generate fewer tokens"). 다만 [121]에서 "번역만"은 출력이 짧은데도 빠르지 않았다. 그래서 단축 폭은 실측해야 한다.
- 구현 크기: 중간보다 작음. `Rewriter`를 흘려 받기로 바꾸고(답변 모델 `OpenAIAnswerModel`이 이미 흘려 받으므로 같은 방식), 조각이 붙은 글에서 query 값이 닫혔는지 보는 작은 함수. 시험은 가짜 조각으로.
- 실험(약 $0.015-0.02): 지금 긴 지시 그대로, 20문항 × 3회차 × 3번 동시, 흘려 받으면서 한 호출 안에서 (가) query가 닫힌 시각 (나) 답이 끝난 시각을 함께 남긴다. 같은 호출에서 둘을 재므로 날·시간대 차이가 섞이지 않는다. query가 늘 첫 칸이었는지도 센다. [127]의 긴 지시 180호출 실제 비용이 $0.0145였다.

#### B. 동시 호출 3개 → 5개 (권함 1에 묶음)

- [확인] 같은 요청을 여러 번 보내 먼저 온 것을 쓰는 "헤지 요청"은 Dean·Barroso의 "The Tail at Scale"(Communications of the ACM, 2013)이 꼬리 지연(가끔 생기는 아주 늦은 응답)을 줄이는 방법으로 제안했다([Google Research 목록](https://research.google/pubs/pub40801/), [MIT 6.1800 읽기 과제 쪽](https://web.mit.edu/6.1800/www/readings/03-tail.shtml)). 논문 원문 쪽(cacm.acm.org)은 403으로 열리지 않아 수치("1,800ms → 74ms, 요청 2% 증가")는 [2차 요약](https://ufried.com/blog/tail_at_scale/)에서만 봤다. **원문 수치는 확인하지 못했다.**
- [계산] 우리 자료로 본 효과(`hedge.py`, 같은 스크래치 폴더)

| 동시 호출 수 | 바꾸기 중앙값(초) | 90% 지점(초) | 검색까지 2초 넘은 비율 |
|---|---|---|---|
| 1(실제, 줄의 첫 호출) | 1.50 | 1.95 | 28% |
| 2(실제, 줄의 앞 2개 중 빠른 것) | 1.44 | 1.75 | 10% |
| 3(실제, 지금) | 1.41 | 1.60 | 3% |
| 5(독립 가정 표본 뽑기) | 1.30 | 1.45 | — |
| 8(독립 가정) | 1.26 | 1.39 | — |

  - 계산 방법: 1-3은 같은 줄(같은 질문·같은 시각)의 실제 호출에서 최소값. 5·8은 180개 호출 시간에서 독립으로 n개를 뽑아 최소값을 2만 번 구했다. 독립 가정은 **낙관적**이다: 같은 줄 호출끼리 비슷하게 늦다(줄 평균끼리의 표준편차 0.37초 > 줄 안 표준편차 0.16초). 독립 가정의 n=3 중앙값(1.37초)이 실제(1.41초)보다 0.04초 빠른 것도 이 때문이다.
  - 따라서 3 → 5개는 **중앙 약 0.05-0.1초, 늦은 쪽(90%) 약 0.1-0.15초** 단축으로 어림한다. 바닥(약 1.1초) 때문에 더 늘려도 효과가 빨리 줄어든다.
- 비용: 질문 바꾸기 호출이 5/3배. 질문 하나에 바꾸기 약 $0.00008 × 5 = 약 $0.0004로 답변 호출(약 $0.0003, [131] 10문항 $0.0030)과 합쳐도 질문당 10배에 한참 못 미친다.
- 실험: A 실험에서 5개로 보내고, 앞 3개만 쓴 경우와 5개를 쓴 경우를 같은 기록에서 함께 계산한다(추가 비용 약 $0.01).

#### C. 입력 중 미리 바꾸기 (권함 3)

- 하려는 일: 도우미 창의 입력 칸에서 글이 멈춘 지 일정 시간(예: 0.4초)이 지나면 그 글로 질문 바꾸기를 미리 보낸다. 사용자가 보낸 글이 그 글과 같으면 이미 와 있거나 오는 중인 결과를 쓰고, 다르면 버리고 새로 보낸다. 검색창의 "입력하는 동안 미리 찾기"와 같은 생각이다.
- [확인] OpenAI 지연 안내는 순서가 정해진 단계라도 "겹쳐 돌리기(speculative execution)"를 쓸 수 있다고 쓴다([같은 안내](https://developers.openai.com/api/docs/guides/latency-optimization), "Parallelize").
- 기대 효과 [추측]: 타자를 멈춘 뒤 Enter를 누르기까지의 시간만큼 바꾸기 1.41초가 가려진다. 이 간격을 잰 공개 자료는 찾지 않았고, 우리 사용자에서 직접 재는 것이 맞다. [131] 창 측정의 "질문 준비(F10 → 보냄) 1.41초"는 질문을 붙여 넣은 경우라 쓸 수 없다.
- 위험: 적중률 위험은 없다(같은 글일 때만 씀). 대신 **보내지 않은 글이 OpenAI로 나간다.** 사용자가 [127]에서 예열을 "몰래 처리한다는 인상"이라며 옵션으로만 둔 것과 같은 종류의 걱정이라, 기본값과 안내 문구를 사용자가 정해야 한다. 비용은 타자 중 멈출 때마다 호출이 늘어 질문당 2-4배로 어림한다 [추측].
- 실험(무료부터): 도우미 시간 기록에 "마지막 글자 바뀜 → 보냄" 간격만 더해 실제 타자로 10-20개 질문을 넣어 본다. 간격 중앙값이 0.5초를 넘으면 그때 구현을 검토한다.

#### D. 근거·검색어를 답보다 먼저 보이기 (사용자 결정 필요)

- 하려는 일: 바꾸기가 끝난 약 1.4초에 "설명서에서 찾는 중: Axis Locking …", 검색이 끝난 약 1.7초에 근거 제목 목록을 먼저 띄우고, 답 글은 그 아래 이어서 흘린다.
- [확인] OpenAI 안내: 사용자가 기다리게 하기보다 진행을 보게 하라, 흘려 받기가 "가장 효과적"([같은 안내](https://developers.openai.com/api/docs/guides/latency-optimization), "Make your users wait less").
- [확인] Nielsen(1993, NN/g 발췌): 1초는 "생각의 흐름이 끊기지 않는 한계", 1초를 넘는 지연은 컴퓨터가 일하고 있음을 보여 주라([Nielsen, Response Times: The 3 Important Limits](https://www.nngroup.com/articles/response-times-3-important-limits/), 원출처 Miller 1968·Card 외 1991).
- [확인] 반대 방향 근거: Tan·Messerschmidt·Yin·Nov(arXiv 2604.06183, CHI 2026 예정)는 첫 글자 2·9·20초를 비교해, 2초 조건의 답을 사용자가 오히려 "덜 사려 깊고 덜 유용하다"고 평가했다고 보고했다([arXiv 2604.06183](https://arxiv.org/abs/2604.06183)). 과제는 글쓰기·조언이었고 초보자 도움말과 다르다. 2.5초 → 2초의 차이를 사용자가 크게 느끼지 않을 수도 있다는 참고로만 적는다.
- 적중률 위험: 없다. 검색어가 엉뚱하면(예: A6 한 호출의 Curve Modifier, [127]) 그것이 그대로 보인다는 점이 위험이다 [추측].
- 측정 정의: 지금 "첫 글자"는 답 글의 첫 조각이다. 상태 줄을 첫 글자로 치면 중앙값 약 1.4초가 되지만, 이것은 목표의 뜻을 바꾸는 일이라 **사용자가 정한다.** 치지 않더라도 체감용으로 함께 넣을 수 있다.
- 구현 크기: 작음(엔진이 `Piece`와 다른 상태 알림을 하나 더 내고 창이 보이면 됨).

#### E. 예상 질문 색인·미리 채운 의미 캐시를 바꾸기와 겹쳐 찾기 (권함 2)

- 하려는 일: 질문이 오면 luna 바꾸기 3-5개를 보내는 **동시에** 한국어 질문을 바로 임베딩해 "한국어 예상 질문 색인"(설명서 청크마다 luna가 미리 만든 초보자식 한국어 질문들, 또는 연습 과정 단계마다 미리 만든 질문 → 검색어 짝)에서 찾는다. 가장 가까운 예상 질문의 점수가 문턱값을 넘으면 그 청크로 바로 답변 모델을 출발시키고, 넘지 않으면 지금처럼 바꾸기를 기다린다.
- 기대 효과 [계산·추측]: 맞으면 첫 글자 ≈ 임베딩 0.27 + 검색 0.04 + 답변 첫 조각 0.76 ≈ **1.1초**(약 1.4초 단축). 못 맞으면 겹쳐 돌린 임베딩이 바꾸기 1.4초 안에 끝나므로 **지금보다 늦어지지 않는다.** 전체 중앙값은 "자신 있게 맞히는 비율"에 달려 있다.
- 새 근거(이전 조사 이후): [확인] 교차 언어로 "문서 쪽에 사용자 언어 질문을 붙여 조밀 검색에 쓰는" 연구는 이번에도 찾지 못했다(검색어 바꾸기 쪽 [arXiv 2511.19325](https://arxiv.org/abs/2511.19325)와 단일 언어 [LLM-QE, arXiv 2502.17057](https://arxiv.org/abs/2502.17057)만 나옴). 의미 캐시는 [확인] MeanCache(Gill 외, IPDPS 2025)가 "LLM 서비스 질문의 약 31%가 반복 질문"이라는 보고를 인용한다([arXiv 2403.02694](https://arxiv.org/abs/2403.02694)). 일반 서비스 기록 값이라 우리 수업(같은 연습 과정을 여러 학생이 진행)에 그대로 옮길 수 없지만, 연습 과정 단계마다 비슷한 질문이 몰릴 가능성은 있다 [추측].
- 적중률 위험과 무료로 본 것 [계산]: 지금 청크 색인에서는 한국어 질문의 1위 점수가 맞힘을 가려 주지 못한다. `102717_full_large_original_scopes`의 "BM25 끔" 1회차에서 1위 점수가 가장 높은 W8(0.479)·A2(0.476)는 못 찾았고, 맞힌 W10은 0.319였다(스크립트 `conf.py`). 그래서 **지금 색인 그대로는 "자신 있을 때만" 고르기가 안 되고**, 문턱값이 뜻을 가지려면 한국어 대 한국어로 비교하는 예상 질문 색인이 있어야 한다. 그때도 문턱값이 갈라 줄지는 실험 전에는 모른다.
- 평가 부풀림 위험: A문항은 AI가 쓴 질문이라 AI가 만든 예상 질문과 닮아 점수가 높게 나올 수 있다(이전 조사 Rahmani 외 2024·Dai 외 2024). **문턱값은 A로 정하고 W로 확인**하거나, 둘을 따로 적는다.
- 비용: 예상 질문 만들기 설명서 전체 약 $0.6-1.2(이전 조사의 어림), 질문마다 한국어 임베딩 1번 추가(아주 적음). 질문당 비용은 거의 그대로.

#### F. 질문 바꾸기와 답변을 한 호출로 합치기 (권하지 않음)

- [확인] OpenAI 안내는 순서대로인 단계를 한 프롬프트로 합치라고 하고, 예로 "질문 바꾸기 + 검색이 필요한지 판단"을 하나로 합쳤다([같은 안내](https://developers.openai.com/api/docs/guides/latency-optimization), "Make fewer requests"). 하지만 그 예는 **검색 앞의 두 단계**를 합친 것이다.

[추측] 한 요청 안에서 끝나 우리 쪽 임베딩 왕복(0.27초)은 사라질 수 있지만, 서버 안에서도 "검색어 쓰기 → 검색 → 답 쓰기"가 순서대로 일어나 1.4초 몫이 사라진다는 보장이 없다. 지연 수치는 공식 문서에 없다. 우리 청크·소제목 경로·근거 링크·평가 체계를 다시 만들어야 해 구현이 가장 크다. 시험해 본다면 20문항 × 1회 첫 글자만 재는 데 몇 센트지만, 1-3번 뒤로 미룬다.

3. 두 보고서가 놓친 것: **답변 모델도 2개 동시로 보내 먼저 첫 조각을 낸 쪽을 쓰기**, **Fast를 질문 바꾸기·답변 모두에**(조정된 판단 기준에서는 비용 위험이 아님), **흘려 받되 연결을 끊지 말기**(끊으면 요금 기록과 (나)의 칸을 잃는다).
4. 권하는 순서: ① 흘려 받아 query가 닫히면 바로 검색(끊지 않음) ② 동시 3 → 5 ③ 답변 2개 동시 ④ Fast 다시 묻기 ⑤ 그래도 모자라면 B의 E(예상 질문 색인)·C(입력 중 미리 바꾸기, 동의 필요). 무료로 "첫 질문 +1초" 원인 가르기(A의 2번)는 아무 때나.
5. 약 $0.05-0.06짜리 실험 하나로 ①-④와 (가)·(나)를 함께 확인하는 설계를 맨 아래에 적었다.

#### 1-2. "luna 호출 하나 바닥 약 1.1초"

- [계산] 긴 지시 180호출 최소 1.120초, 하위 5개 1.120-1.143초. 짧은 지시 최소 0.918초, 10% 지점 1.155초. 숫자는 맞다.

#### 1-3. 호출당 입력 약 581토큰·출력 45토큰

#### 1-4. 흘려 받기 절약 — A(0.2-0.5초)와 B(0.1-0.15초)가 부딪힌다. B 쪽이 맞다

- A의 근거: 호출 시간을 검색어 길이에 직선으로 맞춘 기울기(약 0.012-0.02초/토큰) × areas·exclude 약 25토큰.
  - [계산] 다시 돌리니 첫 요청 뺀 기울기 0.028초/낱말(≈0.02초/토큰), 상관 0.37(첫 요청 포함). 상관이 약하고, 긴 검색어가 나오는 질문이 원래 느린 질문일 수 있어(질문 길이·맥락이 같이 늚) 기울기가 부풀 수 있다 [추측].
- 더 곧은 근거는 **짝 비교**다: [계산] 같은 질문·같은 회차의 긴 지시 대 짧은 지시 호출 중앙의 차이는 **중앙 0.127초, 평균 0.204초**. 이 차이에는 출력 약 18.5토큰(44.6 − 26.1)과 입력 약 400토큰이 함께 들어 있다. 입력 몫은 공식 안내상 작다(아래 2-1). 그러면 출력 한 토큰에 **약 0.007초(초당 약 140토큰)**이고, query 뒤 남은 출력(areas·exclude·닫는 기호, 약 18-20토큰)을 건너뛰는 이득은 **호출당 약 0.13초(0.1-0.15초)**다.
- areas·exclude 몫도 A는 약 25토큰, B는 약 18토큰. 짧은 지시 출력 26.1토큰이 `{"query": ...}`뿐인 것을 보면 B의 계산(44.6 − 26.1)이 원본에 더 붙어 있다. 다만 짧은 지시의 검색어가 조금 짧아(12.5 대 13.6낱말) 실제 몫은 약 17-20토큰.
- 헤지(3개 중 먼저 온 것)에서도 이득은 비슷하다 [추측]: 모든 호출이 같은 양만큼 줄기 때문.

#### 1-5. 5개 동시 호출 효과

- [계산] `hedge.py` 다시 돌림: 실제 1/2/3개 중앙 1.498/1.438/1.407초, 90% 1.946/1.746/1.600초. 독립 가정 5개 1.302초·90% 1.447초. 두 보고서 숫자와 같다.
- 독립 가정이 낙관적이라는 두 보고서의 말을 숫자로 확인하려고 **같은 순간 호출끼리 함께 느려지는 모형**(줄 평균 + 줄 안 흔들림)으로 다시 흉내 냈다(`hedge_corr.py`): 3개 중앙 1.382·90% 1.669, **5개 1.321·1.593**. 실제 3개(1.407·1.600)와 가깝다. 3 → 5의 이득은 **중앙 약 0.06초, 90% 약 0.08초** [계산]. 두 보고서의 "중앙 0.05-0.1초"와 맞고, B의 "90% 0.1-0.15초"는 조금 크다.
- 비용 [계산]: 호출 하나 581×$0.10/100만 + 45×$0.50/100만 = $0.00008. 3개 $0.00024 → 5개 $0.0004, 답변 약 $0.0003을 합친 질문당 +약 30%. 10배 기준에 한참 못 미친다. 두 보고서 같음.

#### 1-6. B의 "기능 이름 있으면 건너뛰기 84 → 60%", "한국어 검색 섞기 84 → 64%"

- [계산] `analyze.py` 다시 돌림: 이름 든 8문항(손으로 고름)을 한국어 그대로로 건너뛰면 전체 **0.60**(그 8문항만 27.3% 대 바꾸기 81.8%), 번역만이면 0.68. 바꾸기 + 한국어 그대로 RRF **0.64**, + 번역만 0.76, 상위 8개 겹침 평균 1.3개. 모두 B와 같다.
- 근거의 한계: 1회차 한 번, 20문항(한 문항이 2.5-5%p), "이름 든 문항" 고르기가 손으로 한 것, 한국어 그대로는 다른 실행(`102717`)의 결과다. 그래도 차이가 20%p 이상이라 "권하지 않음"의 결론은 흔들리지 않는다.
- B 요약 줄(35줄)의 "82% → 27%"는 이름 든 8문항만의 숫자다. 전체로는 84 → 60%. 읽을 때 헷갈릴 수 있다.
- `conf.py`(한국어 질문 1위 점수가 맞힘을 가르지 못함)도 다시 돌려 같았다: 1위 점수가 가장 높은 W8(0.479)·A2(0.476)는 못 찾고, W10(0.319)은 찾음.

#### 1-7. 작은 어긋남

- A 23줄 "긴 지시의 86.7% 그대로": 86.7%는 3개를 RRF로 합친 값이고, 지금 도우미(먼저 온 1개)는 **85.3%**다([127], [계산] 0.853).

### 2. 근거가 약하거나 틀린 주장, 부딪히는 주장

#### 2-1. "답변 입력 약 6천 토큰" → 실제 약 2,000-2,500토큰 (A 136줄, 검토 지시문)

- [계산] `092554_t33_none/답.jsonl`의 검색 결과 주소로 답변 모델 입력을 다시 만들었다(`answer_input.py`, 같은 주소의 첫 조각만 써서 조금 작게 나옴). 사용자 글 4,735-8,967**글자**(중앙 약 6,900), 그중 설명서 영어 668-1,393낱말(중앙 1,034), 지시 646-807글자, 작업 상태 등 약 650글자. 영어 1낱말 ≈ 1.3토큰, 한국어 지시·상태를 더하면 **약 2,000-2,500토큰**.
- [계산] 요금으로 위쪽 한계를 확인: none 10문항 답변 $0.003018 → 질문당 $0.0003. 입력 단가 $0.10/100만이라 출력이 0이어도 입력은 **3,000토큰을 넘을 수 없다**. 답 글 평균 약 300글자(출력 약 150-250토큰 [추측])를 빼면 약 1,800-2,300토큰.
- 결론: 6천은 글자 수를 토큰으로 읽은 것으로 보인다. 이 값이 작으면 "입력을 줄여 첫 조각 줄이기"의 여지는 더 작다.

#### 2-2. 입력 길이·청크 수와 첫 토큰 시간의 공식 근거

- [확인] OpenAI 지연 안내([Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization)): "cutting 50% of your prompt may only result in a 1–5% latency improvement", 그리고 "truly massive context sizes(문서·이미지)"가 아니면 다른 데 힘을 쓰라고 한다. **첫 토큰 시간만 따로 다룬 숫자는 이 문서에 없다.**
- [추측] 1-5%는 생성까지 포함한 전체 지연 기준이다. 첫 토큰 시간에서는 입력 읽기 몫이 상대적으로 크지만, 약 2,000토큰은 대형 서버에서 수십 ms 수준으로 본다. 청크 8 → 4개로 줄여도 0.05초 안팎 이득에 적중 위험(상위 4개 57.5% 대 8개 85%, [117])이 커서 권하지 않는다. 두 보고서의 결론(답변 입력 줄이기는 작다)은 맞고, 근거 숫자(6천)만 고친다.

#### 2-3. "흘려 받다가 query가 닫히면 연결을 끊는다"(A 55줄)는 잃는 것이 있다

- [확인] 우리 코드는 요금·토큰을 흘려 받기 **마지막 조각의 usage**로 센다(`answer_model.py`의 `stream_options.include_usage`, 질문 바꾸기 쪽은 지금 응답 전체의 usage). 끊으면 평가 `설정.json`의 요금 기록이 빠지고, A가 실험 4번으로 보려는 `reasoning_tokens`도 못 본다.
- 끊어도 서버가 생성을 멈추는지는 문서에서 찾지 못했다(A도 같음). 그래서 이득이 비용 쪽에도 없다.
- **권함**: query가 닫히면 그 글로 바로 임베딩을 시작하되, 그 호출은 뒤에서 끝까지 읽게 둔다. 시간 이득은 같고, 요금·생각 토큰·뒤 칸(아래 (나))을 잃지 않는다. 지금도 늦은 2개 호출은 뒤에서 끝나게 두고 있어(`answer_engine.py` 390줄) 같은 방식이다.

#### 2-4. JSON 칸 순서

- 두 보고서 모두 "json_object는 순서 보장이 없다, 실측으로 센다"로 같다. A가 덧붙인 json_schema(strict)의 "첫 요청 스키마 처리 지연"은 도우미를 켠 뒤 첫 질문에만 붙는다. 첫 질문은 이미 +1초 문제가 있으므로 실험에서 둘을 섞지 않게 따로 재야 한다.

#### 2-5. 그 밖에 부딪히는 곳

- 순위: A는 "흘려 받기"를 1번, B는 "흘려 받기 + 5개"를 1번으로 묶었다. 내용은 같다.
- B는 Fast를 다루지 않았고, A는 "사용자가 비용 때문에 내린 것"이라 뒤로 뺐다. 이번 판단 기준(비용은 10배 넘을 때만 위험)에서는 Fast를 다시 올려야 한다(3-2).
- B의 D(상태 줄 먼저 띄우기)는 사용자 결정으로 첫 글자에 치지 않는다. 시간 단축에서 뺀다.

### 3. 둘 다 놓친 방법

#### 3-1. 답변 모델도 2개 동시로 보내고, 먼저 첫 조각을 낸 쪽을 쓴다

- 하려는 일: 검색이 끝나면 같은 답변 요청을 2개 보내, 먼저 첫 조각을 낸 흐름만 화면에 흘리고 다른 하나는 닫는다(또는 뒤에서 끝까지 읽어 요금만 센다).
- 근거: 질문 바꾸기에서 1 → 2개가 중앙 1.498 → 1.438초(−0.06), 90% 1.946 → 1.746초(−0.2)였다 [계산, 실제 같은 줄]. 답변 첫 조각도 같은 서버의 같은 고정 몫이라 비슷하게 흔들린다고 보면 **중앙 약 −0.05초, 늦은 쪽 −0.1-0.2초** [추측].
- 비용: 답변 $0.0003 → $0.0006, 질문당 약 +55%. 10배 아래.
- 위험: 두 답의 내용이 다를 뿐 둘 다 같은 근거로 쓴 답이라 품질 위험은 없다. 구현은 `answer()`에서 두 흐름 중 첫 조각이 먼저 온 쪽을 고르는 작은 부분(스레드 2개).

#### 3-2. Fast를 질문 바꾸기와 답변 둘 다에

- [확인] [127]: 짧은 지시에서 호출 중앙 1.37 → 1.23초(약 10%), 30개 모두 fast 처리. 값은 2배.
- [어림] 두 luna 호출에 모두 쓰면 약 −0.14(바꾸기) + 약 −0.08(답변 첫 조각, 10% 가정) ≈ **−0.2초**. 질문당 비용은 약 2배로, 10배 기준 안이다.
- 사용자는 [127]에서 "fast 는 비용 문제 때문에 그닥"이라 했다. 판단 기준이 바뀌었으므로 **다시 물을 일**이다. 단 10%는 10문항·짧은 지시 한 번이라 다시 재야 한다.

#### 3-3. 질문 바꾸기를 query만 내게 하고 긴 지시는 유지 — 흘려 받기에 밀린다

- 시간 이득은 흘려 받아 query에서 시작하는 것과 **같다**(query가 닫히는 시각까지 쓰는 토큰이 같음). 다른 점은 비용이 조금 주는 것뿐이고, 분야를 고르게 하던 출력을 빼면 검색어가 바뀔 위험이 생긴다(긴 지시의 이득이 입력에서 오는지, areas를 쓰는 일에서 오는지는 아직 가르지 않았다 — B는 입력 쪽이라 "추측"으로 둠). 그래서 권하지 않는다. 대신 실험에서 한 조건으로 넣으면 "긴 지시 이득이 어디서 오나"를 함께 가를 수 있다(4번 설계의 선택 조건).

#### 3-4. "검색어가 흘러나오는 즉시 답변 호출까지 겹치기"

- query가 닫힌 뒤의 길은 임베딩(0.27) → 검색(0.04) → 답변 요청뿐이라 더 겹칠 곳은 거의 없다. 남는 손잡이:
  - **임베딩도 2개 동시**: 중앙은 그대로, 임베딩 최대 1.86초 같은 꼬리만 준다 [추측]. 비용은 아주 적다. 우선순위 낮음.
  - **먼저 닫힌 query 하나로 출발**(지금 방식 그대로). 두 번째 query를 기다려 합치면 적중은 조금 오르지만(86.7% 대 85.3%) 시간이 는다. 그대로 둔다.
- 답변 요청을 검색 전에 미리 열어 두는 것은 의미가 없다: 연결 맺기 0.03초([127]). 서버 쪽 요청 준비를 미리 하는 기능(Responses의 `prompt_cache_options.prewarm`, WebSocket `generate: false`)은 A가 적은 대로 효과 미확인이다.

#### 3-5. 큰 손잡이는 여전히 B의 E·C뿐

- 위 1-4의 작은 손잡이를 다 더하면 약 −0.25-0.5초다(아래 표). 2초 안이 실측에서 안 되면, luna 고정 몫 하나를 통째로 숨기는 B의 E(예상 질문 색인으로 자신 있을 때 바꾸기를 건너뜀)나 C(입력 중 미리 바꾸기, 보내지 않은 글이 나가므로 사용자 동의 필요)가 남는다.

### 4. 미뤄 둔 두 가지와 엮이는 곳

#### (가) 답변 모델이 실제 쓴 근거 번호만 표시(답 끝 숨은 표시)

- 첫 글자 시간에는 거의 영향이 없다: 번호를 붙이려면 설명서 내용에 청크 번호를 다는 정도(입력 수십 토큰)이고, 표시는 답 **끝**에 붙어 답 끝 시간만 몇 토큰 늘린다 [추측].
- 엮이는 곳:
  - 화면에 흘릴 때 숨은 표시가 보이지 않게 모아 두는 처리가 필요하다. 지금 `[[ ]]` 메뉴 표시를 모으는 `_MenuMarks`와 같은 자리다.
  - 3-1(답변 2개 동시)과 함께 하면 고른 흐름의 표시만 쓴다. 충돌 없음.
  - 답변 지시(`INSTRUCTIONS`)를 바꾸므로, 시간 실험과 같은 실행에서 따로 조건을 두면 "표시를 빠뜨린 비율"을 공짜에 가깝게 잴 수 있다.

#### (나) 질문 바꾸기 JSON에 "찾을 필요 없음" 칸

- **흘려 받기와 같은 지시·같은 출력 칸을 건드린다.**
  - 칸을 query **앞**에 두면 query가 닫히는 시각이 몇 토큰(약 0.03-0.05초) 늦어진다.
  - query **뒤**에 두면 시간은 그대로다. 단 2-3의 "끊지 말고 끝까지 읽기"를 해야 이 칸을 받는다. 근거 표시는 답이 끝날 때(`Done`) 정하므로, 뒤 칸은 그 전에 도착한다(답 끝 약 3.9초 대 바꾸기 끝 약 1.5초).
- 지시를 바꾸면 검색어도 바뀔 수 있어 적중을 다시 재야 한다([132]에서 Claude가 이미 밝힌 점). 흘려 받기 실험과 **같은 실행**에서 조건 하나로 넣으면 적중 재기를 따로 하지 않아도 된다.
- json_object는 칸 순서를 보장하지 않으므로, query 앞뒤 어디에 나오는지도 함께 센다.
- (가)가 같은 문제(인사에 근거가 붙음)를 지시 변경 없이 질문 바꾸기 쪽 위험 없이 풀므로, [132]에서 Claude가 권한 대로 (가)를 먼저 하고 (나)는 (가)가 표시를 자주 빠뜨릴 때만 보는 것이 맞다 [추측].

### 6. 실험 하나로 여러 가설 확인하기 (약 $0.05-0.06)

**구성**: 지금 도우미와 같은 설정(luna none, large, 설명서 전체, 상위 8개), W1-W10·A1-A10 20문항 × 2회차, 강의실 PC. 조건을 질문마다 번갈아 섞어 시간대 차이가 한쪽에 몰리지 않게 한다. 실행 시작 전에 `GET /v1/models`를 5번(무료, A의 2번)으로 첫 요청 문제도 함께 본다.

질문 하나마다:
1. **질문 바꾸기 5개 동시, 흘려 받기, 끝까지 읽기**(긴 지시 그대로). 호출마다 `보냄`·`첫 조각`·`query 닫힘`·`끝` 시각, usage(생각 토큰 포함), 칸 순서를 남긴다.
2. 가장 먼저 query가 닫힌 것으로 임베딩·검색(시각 기록).
3. **답변 모델 2개 동시, 흘려 받기**. 각 흐름의 `첫 조각`·`끝`과 usage. 2회차 중 한 회차는 답변 지시에 (가) 숨은 근거 번호 표시를 더한다.
4. (선택, +약 $0.006) 같은 질문에 **(나) 칸을 query 뒤에 넣은 지시**로 3개 더 보내 검색어 적중을 지금 지시와 견준다. 인사·감사 같은 비설명서 질문 3-5개를 더해 칸이 제대로 켜지는지 본다.
5. (선택, +약 $0.01) 10문항 × 1회차를 Fast로 1-3과 같게.

**새 호출 없이 기록에서 계산하는 것**

| 가설 | 계산 |
|---|---|
| ① 흘려 받기 이득 | 호출마다 `끝 − query 닫힘`, 그리고 5개 중 먼저 query 닫힘 대 먼저 끝남 |
| 고정 몫 약 0.8초 | `첫 조각 − 보냄`의 분포(질문 바꾸기·답변 모두) |
| ② 3 → 5 | 같은 기록에서 앞 3개만 쓴 최소 대 5개 최소 |
| ③ 답변 2개 동시 | 앞 1개만 쓴 첫 조각 대 2개 중 먼저 |
| 단계별 시간 | 같은 실행 안에서 바꾸기·임베딩·검색·답변 첫 조각(지금은 다른 날 측정을 뺀 값) |
| 생각 토큰 0 여부 | usage의 `reasoning_tokens` |
| query 첫 칸 비율 | 칸 순서 기록(200호출) |
| 검색어 적중 그대로인지 | 먼저 온 query의 상위 8개 적중을 [127]의 85.3%와 견줌(20문항이라 ±5%p는 우연일 수 있음) |
| (가) 지킴 비율 | 숨은 표시가 있는 답 비율, 표시된 번호가 검색 결과 안에 있는지 |
| (나) 적중 영향·칸 동작 | 4번 조건의 적중, 비설명서 질문에서 칸 값 |
| ④ Fast 이득 | 5번 조건 대 같은 문항 기본 |

**비용 어림** [계산]: 질문 바꾸기 20 × 2 × 5 = 200호출 × $0.00008 = $0.016. 답변 40 × 2 = 80호출 × $0.0003 = $0.024. 임베딩 아주 적음. 선택 조건 합 약 $0.016. **합계 약 $0.04(필수) - $0.06(선택 포함).**

- 실험 코드는 평가 도구(`search_compare flow` 또는 엔진 평가 `run`)에 흘려 받기·답변 동시 호출을 더해야 한다. 그 변경 자체가 ①·③의 구현과 겹치므로, 도우미 코드에 먼저 넣고 같은 코드로 재는 편이 덜 든다 [추측].
