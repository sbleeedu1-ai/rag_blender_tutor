# 작업 상태 범용 시험 계획

- 날짜: 2026-11-05. 작성: 메인 세션(Claude). **실행 전 계획이다.** 숫자 기준은 Claude가 제안한 값이고 사용자가 고칠 수 있다.
- 읽은 것: 이번 세션 대화, 전체 세션 114개의 사용자 메시지 중 작업 상태·감지 낱말로 거른 것(낱말로 거른 것이라 전부 읽은 것은 아니다), `HISTORY.md` 감지·상태 항목, `docs/experiment.md` 체크리스트와 가설, `spec.md`, `STRUCTURE.md`, 애드온 `read_state`, `conditions.py`, 연습 과정 파일, 사용자 사용 기록(`streams`), `bpy` 조사·분류 문서.

## 1. 앞 시험에서 고칠 점

`164619_state_diff`는 **개발 문항에 맞춘 시험**이었다. 장면이 개발 문항용이고, 성공 기준이 "그 문항의 원인이 잡히나"였으며, "늘 바뀌는 값" 목록은 Claude가 눈으로 정했고, 거르기 목록은 결과를 보고 정했다. 이대로는 범용이라고 말할 수 없다.

## 2. 이번 목표

사용자 말: "늘 바뀌는거 / 계산해야 아는거 -> 매번 보낼것들이 뭔지 구분을 해야할거 아니야", "그 외에 것들은 뭐가 있는지 파악하려는거고", "우리 범용적으로 쓸거 만드는거다".

Blender 값을 **질문과 상관없이 값이 움직이는 모양으로** 나누고, 측정으로 정한다.

| 묶음 | 뜻 | 넘기는 법 | 어떻게 정하나 |
|---|---|---|---|
| ㄱ. 늘 바뀌는 값 | 평범하게 작업하면 계속 바뀌는 값(예: 위치) | 매번 보냄(대상은 작게) | 조작 실행 측정 |
| ㄴ. 계산해야 아는 값 | 칸에 없고 자료를 훑어야 나오는 값(예: 겹친 점) | 매번 계산, 보내는 규칙은 시험 뒤 결정 | 정답을 아는 도형으로 측정 |
| ㄷ. 일부러 바꿔야 바뀌는 값 | 평소엔 그대로이고 사용자가 건드려야 바뀌는 값(예: 비례 편집) | 공장값과 다를 때만 보냄 | 조작 실행 측정 |
| ㄹ. 안 바뀌거나 쓸 수 없는 값 | 고정값, 내부용, 비밀, 읽으면 죽는 값 | 보내지 않음 | 측정 + 크래시 시험 |

사용자 말의 "매번 보낼 것"에 Claude가 앞에서 "계산 값은 문제가 있을 때만"이라고 다르게 말했다. 계산 값을 어떻게 보낼지는 **아직 정해지지 않았고** 7절 시험 6 결과와 함께 사용자가 정한다.

한 가지 빈 곳이 있다. 기본값 그대로인데 뜻이 있는 값(지금 셰이딩이 무엇인지 등)은 ㄷ 규칙으로는 안 간다. 이런 값을 범용으로 찾는 길이 시험 5다.

**쓰지 않는 것**: 상·중·하 등급으로 고르기(사용자 "애초에 이젠 등급을 빼기로 했으니"). 칸 목록과 "내부용·비밀·읽기 주의" 정보만 재료로 쓴다.

**이번에 안 재는 것**: 답이 나아지는지(사용자: "일단 원인을 파악하는거만 해도 큰거니까").

## 3. 체크리스트

### 가. 범용인가

- [ ] 시험 장면을 개발 장면에서 가져오지 않는다. 공장 상태에서 조작으로 새로 만든다.
- [ ] 기준과 묶음을 정할 때 개발 문항·질문·정답을 보지 않는다. 개발 문항 대조는 **설계가 끝난 뒤** 점검으로만 한다(시험 10).
- [ ] 점검 결과를 보고 규칙을 고치면 그 사실과 고친 줄을 적는다. 고친 뒤의 숫자는 낙관적이라고 표시한다.
- [ ] "초보자 범위 밖"으로 빼지 않는다. 물체 종류, 모드, 모디파이어, 제약, 노드, 시퀀서, 시뮬, 그리스 펜슬을 모두 본다(사용자 "초보자 위주라고 해도 … 범위를 벗어나는 질문에 대답하는거도 목표"). 줄이면 뺀 것과 이유를 적는다.
- [ ] 분류·판단 칸의 기대값을 하위 에이전트 지시에 넣지 않는다.
- [ ] 판단 기준을 결과를 보기 전에 적는다(4절). 보고 나서 바꾸면 드러낸다.

### 나. 실제 환경

- [ ] 창 있는 Blender와 화면 없는 Blender를 줄 단위로 비교한다. 다르면 창 있는 쪽을 기준으로 한다(앞선 조사: 창이 값을 바꿈).
- [ ] 스크립트로 부른 조작은 조작 기록에 안 남는다. 기록·최근 조작을 보는 시험은 흉내 낸 키 입력(`--enable-event-simulate`)을 쓰고, 실제 키보드가 아님을 적는다.
- [ ] F10의 문맥은 마우스 아래 영역이다. 타이머에서는 `context.area`가 없다. 3D 화면이 여럿·사분할·전체 화면·3D 화면 없음일 때를 본다(지금 코드는 가장 큰 3D 화면).
- [ ] 편집 모드에서 `obj.data`는 낡을 수 있다. 조각 모드 직후 값이 늦을 수 있다. 메시 값은 모드마다 확인한다.
- [ ] 진행 중 조작(S·G 등) 동안의 값은 확정 전 값이다(HISTORY [53]-[55] 부근 사용자 확인).
- [ ] 값은 적힌 타입이 아니라 자식 타입으로 온다(`Modifier` → `BevelModifier`).
- [ ] 공장 기준은 `bpy.data.*.new`가 아니라 **사람이 쓰는 조작으로 만든 물체**로 잡는다. 앞 시험의 `use_mirror_vertex_groups` 같은 잡음이 이 차이에서 나왔다(추정, 시험 3에서 확인).
- [ ] 값이 PC·언어·버전을 타는지 본다: 화면 배율·GPU·창 크기·경로·한국어 화면·Blender 5.2.x.
- [ ] 사용자 시작 파일을 바꾼 경우, 번들 애드온을 켠 경우, 설정을 바꾼 경우를 본다.

### 다. 흐름에 맞나

- [ ] 애드온은 **0.5초마다** 상태를 읽고 바뀌면 보낸다. 넓게 읽기를 여기에 넣으면 작업이 끊길 수 있다. 시험 8에서 재고 나서 정한다.
- [ ] F10 없이 도우미 창을 마우스로 눌러 질문하는 길(명세 14번)에서도 넓은 값을 쓸 수 있어야 한다. 지금 도우미 → 애드온 요청 길이 있는지 확인한다.
- [ ] 진행 관리(감지·끝난 조건)도 같은 상태를 쓴다. 공장값 비교가 감지에 쓸 값을 빼지 않아야 한다.
- [ ] 상태 칸 추가는 애드온 `read_state`, `work_state.py`, 흐름 재생 테스트, `STRUCTURE.md`까지 걸린다(이번에는 고치지 않음, 구현 비용으로 적어 둠).
- [ ] 값이 길어지면 시간·비용·묻힘이 생긴다(사용자 "수천개 단위가 되면 처리에 좀 영향이"). 줄 수와 글자 수를 함께 잰다.
- [ ] 흐름 기록 파일(`streams`) 크기가 어떻게 되는지 어림한다.

### 라. 안전

- [ ] 돈이 드는 호출 없음. API 키·`data/.env`를 읽지 않는다.
- [ ] `data/holdout*`, `data/archive/`를 열지 않는다. 수집 원자료도 이번에는 쓰지 않는다(홀드아웃 오염 문제가 풀리기 전).
- [ ] 사용자 애드온을 켜지 않는다(도우미가 뜸, 2차 조사 부작용).
- [ ] 모든 Blender 실행은 임시 설정 폴더를 쓴다. 전후로 `quit.blend`, `userpref.blend`, `startup.blend`, `recent-files.txt`, `bookmarks.txt` 해시를 비교한다.
- [ ] 개발 장면 폴더와 `data/`에 파일이 새로 생기지 않는지 전후 목록을 비교한다(3차 조사 캐시 폴더 사고). 시험 파일은 임시 폴더에서만 저장한다. 유체·파티클 캐시 경로도 그쪽으로 간다.
- [ ] `--console-crash-handler`로 크래시 창을 막고, 시간 제한은 자기 프로세스 번호만 끈다.
- [ ] 비밀 값을 결과에 남기지 않는다: `UserExtensionRepo.access_token`은 읽지 않고, 경로는 앞부분을 가린다.
- [ ] 결과는 `results/<날짜>/<시각>_<이름>/`에 새로 쓰고 덮어쓰지 않는다. 지우지 않는다. 프로그램 코드는 고치지 않는다.
- [ ] 실패한 시도와 건너뛴 것을 숨기지 않고 표에 남긴다.

## 4. 가설과 판단 기준

| 번호 | 가설 | 맞다고 볼 기준(실행 전 제안) | 틀리면 |
|---|---|---|---|
| H1 | 값은 움직임으로 뚜렷이 갈린다. ㄱ은 적고 ㄷ이 대부분이다 | 읽을 수 있는 값 중 ㄱ이 5% 이하이고, 어느 묶음인지 경계가 모호한 값이 10% 이하 | 값 단위 대신 다른 기준 필요 |
| H2 | 공장값은 믿을 만한 기준이다 | 같은 PC에서 두 번 실행한 값이 PC·경로 관련 칸을 빼고 같음. 창 유무 차이 칸 목록을 설명할 수 있음 | 사용자 PC에서 기준을 만드는 방법을 함께 시험 |
| H3 | 종류별 기준을 사람 조작으로 만들면 만든 직후의 차이가 0에 가깝다 | 조작으로 새로 만든 물체·모디파이어·제약·재질의 달라진 값이 종류마다 3개 이하 | 기준 만드는 법을 다시 짬 |
| H4 | 긴 작업에서도 달라진 값(ㄱ 제외)이 감당할 만하다 | 3가지 긴 작업 끝에 활성 물체 기준 중앙 30줄 이하, 최대 100줄 이하 | 묶어 보내기나 대상 줄이기 |
| H5 | 사람이 화면에서 늘 보는 칸이 "기본값이어도 보낼 값"의 범용 기준이 된다 | 3D 화면 머리줄·상태 줄·도구 줄 칸이 한 화면 80개 이하이고, 말로 옮길 수 있음 | 질문 조사로 정하는 쪽 |
| H6 | 계산 값은 정답을 아는 도형에서 맞고, 정상 도형에서 거짓 경보가 없다 | 값마다 정답 일치. 기본 도형 전 종류에서 거짓 경보 0. 10만 면에서 합 300ms 이하 | 값 빼기, 면 수 상한, 말 바꾸기 |
| H7 | Blender가 죽는 값은 특정 경로·상태에 몰려 있고 찾아낼 수 있다 | 상태를 넓혀도 새로 나오는 곳이 줄어든다(마지막 상태 묶음에서 새로 0개). 찾은 자리마다 재현됨 | 애드온은 시험한 칸만 읽는 허용 목록 |
| H8 | 넓은 읽기는 0.5초 타이머에 못 넣고 F10 때만 가능하다 | 타이머 안 5ms 이하면 타이머에 넣을 수 있음. 넘으면 F10·질문 때만. F10 때 100ms 이하 | 일부씩 나눠 읽기, 변경 알림 |
| H9 | 조작 전후 값 표가 감지를 더 정확하게 한다 | 감지가 없는 조작 11개와 사용자가 겪은 오감지 사례 중 절반 이상에 쓸 값이 나옴. 조작끼리 값으로 구별됨 | 버튼으로 남김 |
| H10 | 범용으로 만든 규칙이 개발 문항의 원인도 잡는다(점검) | 상태로 알 수 있는 원인의 80% 이상 | 무엇이 빠졌는지 보고, 규칙을 고치면 표시 |

## 5. 시험 장면(개발 장면 안 씀)

공장 상태에서 조작으로 만든다. 저장은 임시 폴더에만.

- **물체 종류**: 메시 기본 도형 전 종류, 곡선, 표면, 메타볼, 글자, 그리스 펜슬, 아마추어, 격자, 빈 물체, 이미지, 조명 4종, 카메라, 스피커, 볼륨, 포인트 클라우드, 헤어, 힘.
- **모드**: 그 종류에서 들어갈 수 있는 모드 전부.
- **붙이는 것**: 모디파이어 전 종류(그리스 펜슬 포함), 제약 전 종류, 재질, 재질 노드 전 종류, 지오메트리 노드, 파티클·물리.
- **화면**: 편집기 전 종류, 사분할, 전체 화면, 3D 화면 없음, 창 여러 개, 작업 공간 전 종류, 로컬 뷰.
- **문맥 끝값**: 빈 장면, 활성 물체 없음, 숨긴 활성 물체, 라이브러리 연결 물체, 저장 안 한 파일.
- **긴 작업 3가지**: (가) 사용 기록에서 뽑은 조작 흐름을 수백 번(`streams` 182파일, 상태 3,140줄, 조작 36종. 많이 나온 것 `transform.resize`, `view3d.select`, `transform.translate`) (나) 연습 과정 검을 끝까지 (다) 조각·노드·애니메이션을 섞은 흐름.

- 임시 설정 폴더로 띄웠을 때 사용자 설정·애드온이 안 읽히는지 먼저 본다.
- 전후 해시·파일 목록 비교 스크립트를 만든다.
- 일부러 크래시를 내어 자기 프로세스만 끝나는지 본다.

## 7. 시험

**시험 1. 무엇을 읽을 수 있나(범위 정하기).** 모든 시험 장면에서 경로를 따라 읽을 수 있는 값을 모은다. 칸 목록(11,449개)과 맞춰, 어떤 칸이 어떤 상태에서 실제로 닿는지 표로 만든다. 닿지 않은 칸은 까닭과 함께 남긴다.

**시험 2. 값이 언제 바뀌나(H1, ㄱ·ㄷ·ㄹ 나누기).** 조작을 전수 실행해 전후 값을 비교한다.
- 대상: 조작 2,605개 × 시험 장면 대표 상태들. 지금 할 수 있는 것(poll 참)을 기본 입력으로 실행한다. 조작마다 임시 파일을 다시 열어 상태를 되돌린다.
- 안 돌리는 조작: 종료, 파일 저장·내보내기(임시 폴더로 돌릴 수 있으면 돌림), 네트워크·확장 설치, 환경 설정 저장, 긴 렌더, 파일을 지우는 조작, 파이썬 실행. 뺀 조작과 이유를 줄마다 남긴다.
- 대화 상자가 필요해 실행이 안 되는 조작은 "실행 안 됨"으로 남긴다.
- 나누는 규칙(실행 전 제안): 실행한 조작의 5% 이상에서 바뀌면 ㄱ. 그보다 적게 조작에서 바뀌면 ㄷ. 어떤 조작으로도 안 바뀌면 "일단 ㄹ"이고, 사용자가 패널에서 값을 직접 고칠 수 있는 칸(읽기 전용 아님)이면 ㄷ으로 올린다.
- 결과: 칸 × 묶음 표, 조작 × 바뀐 칸 표. 이 표가 "그 외에 뭐가 있는지"의 답이자 시험 9의 재료다.

**시험 3. 공장값 기준(H2·H3).**
- 같은 PC 두 번 비교, 창 있음과 없음 비교.
- 언어를 한국어로 바꾼 경우, 번들 애드온을 켠 경우.
- 종류별로 조작으로 새로 만든 직후의 차이.
- 사용자 실제 설정의 복사본을 임시 폴더에서 읽어 몇 줄 달라지는지(승인 필요).
- 다른 PC(집)에서 같은 스크립트를 돌려 비교(사용자가 집에서 실행, 나중에).
- 기준을 어떻게 들고 있을지 후보 비교: 파일로 싣기 / 사용자 PC에서 처음 켤 때 만들기.

**시험 4. 긴 작업 잡음(H4).** 긴 작업 3가지에서 조작 10·50·끝 시점마다 달라진 값을 세고, 묶음 ㄱ을 뺀 줄 수와 글자 수를 잰다. 대상 범위(활성 물체만 / 선택 물체 / 장면 전체)별로 잰다. 실제 작업 파일이 있으면 함께 잰다(사용자 파일, 승인 필요).

**시험 5. 사람이 늘 보는 칸(H5).** 창 있는 Blender에서 그리는 순간 `layout.introspect()`로 3D 화면 머리줄·도구 줄·상태 줄·N 패널·오버레이 글에 보이는 칸을 모드별로 읽는다. 스크린샷 없이 그 화면 정보를 얼마나 말로 옮길 수 있는지, 값 몇 개인지 본다. 기본값이어도 보낼 후보가 여기서 나온다.

**시험 6. 계산 값(H6).** 분류 2의 계산 값 96개 전부. 줄 수를 줄이려면 뺀 것과 이유를 적는다.
- 값마다 **정답을 아는 도형**을 조작으로 만든다: 뒤집은 면 수, 겹친 점, 구멍, 면 셋 붙은 변, 떨어진 점, 숨김, 부모 회전 등. 닫힌 메시와 열린 메시를 나눈다.
- 물체 모드와 편집 모드에서 각각, 원본이 바뀌지 않는지 해시로 확인한다.
- 기본 도형 전 종류에서 거짓 경보를 센다.
- 1천·1만·10만·100만 면에서 시간을 잰다.

**시험 7. Blender가 죽는 곳(H7).** 하위 에이전트(Opus high)가 맡는다. 모든 시험 장면 상태에서 제한 없이 값을 따라 읽는다. 읽기 전에 자리를 기록하고, 죽으면 그 자리를 건너뛰어 이어 간다. 함수는 읽기로 나뉜 것만 부른다. `local_view` 사례를 창 유무로 재현한다. 결과: 칸, 상태, 재현 횟수, 공통점. 상태 묶음마다 새로 나온 수를 그려 더 찾을 게 남았는지 본다. 원인이 애드온 코드 경로와 관련 있는지 본다.

**시험 8. 언제 읽나(H8).** 창 있는 Blender, 면 수 3가지.
- 타이머 안에서 범위별 읽는 시간, 화면이 끊기는지(프레임 시간).
- 흉내 낸 F10으로 마우스를 편집기마다 두고 문맥과 값 차이.
- 3D 화면 여러 개·사분할·전체 화면·3D 화면 없음.
- F10 없이 질문하는 길에서 값을 받을 방법 확인(코드 읽기).

**시험 9. 연습 과정 감지(H9).** 코드는 고치지 않고 후보만 낸다.
- 지금 상태: 단계 21개 중 끝난 조건 19개. 조작 77개 중 감지 66개, 없는 11개(색 고르기, 깎는 폭 줄이기, 내보내기 창 열기 등). 조건 15종.
- 시험: 조작마다 흉내 낸 키 입력으로 실제 경로를 실행하고 전후 값을 본다. 조작 기록의 입력값(값·축)도 본다.
- 살펴볼 사용자 사례: 축을 바꿔 확정해도 넘어감(S Z 뒤 휠), S 누르기만 해도 감지, 다른 숫자를 쳐도 넘어감, `+` 누른 순간 넘어감, 되돌린 뒤 다시 감지하기, 다른 부품을 옮겼을 때 놓침, 내보내기.
- 결과: 사례마다 구별해 주는 값이 있나, 조건 후보, 거짓 감지 위험. `tests/fixtures` 흐름 재생은 칸이 늘어난 뒤에 쓴다.

**시험 10. 점검(H10, 설계 끝난 뒤).** 앞 시험의 규칙을 고정한 다음 개발 장면 39개와 문항별 원인, 질문 조사 3-다의 원인 묶음과 맞춘다. 범용 규칙으로 잡히는지 보는 **점검이지 설계 재료가 아니다.** 놓친 것은 까닭을 적고 규칙을 고치면 표시한다.

## 8. 순서와 맡기기

1. 6절 안전 장치.
2. 시험 7(크래시)을 **가장 먼저**. 뒤 시험들이 그 목록을 써야 안 죽는다.
3. 시험 1 → 2 → 3 → 4 → 5.
4. 시험 6, 8, 9.
5. 규칙 고정 → 시험 10.
6. 결과를 `docs/experiment.md`에 앞 가설들과 같은 모양으로 남기고, 후보 초안을 다시 쓴다.

시험 7과 2·6은 양이 많아 하위 에이전트에 맡기고 메인 세션이 표본을 다시 돌려 대조한다. 지시에 기대 결과와 개발 문항을 넣지 않는다.

## 9. 시험으로도 모르는 것

- 실제 키보드·마우스(흉내 입력과 다를 수 있음). 마지막에 사람이 또는 agent-desktop으로 일부 확인.
- 실제 사용자 파일의 다양함. 파일을 받기 전까지는 만든 긴 작업으로 대신한다.
- 넘겼을 때 답이 나아지는지. 구현 뒤 유료 측정으로 본다.
- 안 시도한 상태의 크래시. 그래서 애드온은 시험을 통과한 범위만 읽는다.
