# bge-m3보다 가벼운 로컬 임베딩 모델 후보 조사

확인한 날짜: 2026-10-29 · 조사: Claude(Opus 5.5) 하위 에이전트 · 모델을 내려받거나 재지 않았다(값은 모두 모델 카드·논문·Hugging Face API에서 읽은 것과 그것으로 어림한 것).

**질문.** BAAI/bge-m3(약 568M 매개변수)보다 훨씬 가벼우면서, **한국어 질문 → 영어 설명서 청크** 교차 언어 검색(질문과 문서의 언어가 다른 검색)을 할 수 있는 로컬 임베딩 모델은 무엇인가. 임베딩은 설명서 원문(영어) 청크만 하기로 정해졌으므로, **한국어 질문 → 영어 청크 성능이 가장 중요한 기준**이다. 설명서 전체는 약 8,997청크다(1,379청크는 한국어 번역을 붙인 초보자 범위). 조건은 이 PC(i7-4770, AVX2만, RAM 16GB, 사실상 CPU)에서 모델 불러오기 5-8초 이내, 질문 하나 임베딩 0.1초 안팎이다. 나중에 도우미(애드온 + Python 도우미 창)와 함께 배포할 수도 있으므로 배포 부담도 함께 본다.

- **임베딩**: 글을 숫자 묶음(벡터)으로 바꿔, 뜻이 가까운 글을 찾게 하는 것.
- **매개변수**: 모델 안의 숫자 개수. 많을수록 대개 파일이 크고 느리다.
- **ONNX**: 모델을 PyTorch 없이도 돌릴 수 있게 저장하는 공통 형식. `onnxruntime`이라는 작은 실행 라이브러리로 돌린다.
- **int8 양자화**: 모델 숫자를 32비트에서 8비트로 줄여 파일을 약 1/4로 만드는 것. 대개 빨라지고 정확도는 조금 떨어질 수 있다.

## 한 쪽 요약

**결론.** 아래 세 개를 이 PC에서 직접 재 보기를 권한다. 1순위는 IBM granite 97M r2다.

1. **ibm-granite/granite-embedding-97m-multilingual-r2** (97M, 2026-04 공개, Apache-2.0)
   - 크기가 bge-m3의 약 1/6인데, IBM 발표 기준 다국어 검색 점수(MTEB Multilingual Retrieval)가 **60.3**이다. 같은 계열 표에서 bge-m3는 54.6이다. 다만 두 숫자는 서로 다른 문서에서 왔다(아래 주의).
   - 한국어가 "검색·교차 언어 학습을 따로 한 52개 언어"에 들어 있다.
   - **이 PC의 CPU(AVX2)에 맞춘 int8 ONNX 파일(98MB)**을 공식으로 준다. 그래서 PyTorch 없이 `onnxruntime`만으로 배포할 수 있다.
   - 접두어("query: " 같은 앞말)가 필요 없다.
2. **intfloat/multilingual-e5-small** (118M, MIT)
   - 오래 쓰여 검증된 가벼운 기준선이다.
   - 한국어 검색 점수가 있다. Mr.TyDi 한국어 MRR@10 54.3(e5 카드 기준, 한국어 → 한국어 시험). 한 한국어 모델 제작자가 잰 한국어 검색 7종 평균은 0.671로, 같은 표에서 bge-m3는 0.724다.
   - 학습에 번역 문장 쌍(NLLB 24억 쌍)을 썼다. 그래서 언어 사이 정렬을 기대할 수 있다(교차 언어 검색 숫자는 못 찾음).
   - "query: "·"passage: " 접두어가 꼭 필요하다. 입력 최대 512토큰이다.
3. **google/embeddinggemma-300m** (308M, Gemma 이용약관)
   - 품질 쪽 후보다. 500M 아래 모델 중 다국어 검색 점수가 가장 높다(62.5).
   - 교차 언어 검색 숫자도 있다. XOR-Retrieve(여러 언어 질문으로 영어 문단 찾기)에서 84.14로, text-embedding-3-large(68.76)보다 높다(Google이 잰 값).
   - 대신 원본 파일이 1.2GB라 PyTorch로 처음 불러오면 8초를 넘길 가능성이 크다(어림). 커뮤니티가 만든 4비트 ONNX(약 200MB)를 쓰면 줄어들 수 있다.
   - 내려받기에 Hugging Face 로그인·약관 동의가 필요하다. 재배포하려면 약관 사본과 Notice 파일을 함께 넣어야 한다.

**예비 후보**: Snowflake/snowflake-arctic-embed-m-v2.0(305M, Apache-2.0, 공식 int8 ONNX 311MB). 셋 중 하나가 탈락하면 넣는다.

**하한선 참고**: minishlab/potion-multilingual-128M(정적 임베딩, numpy만 필요, 사실상 즉시 계산). 검색 품질은 크게 낮다(Retrieval 37.86). "가장 싼 방법이 얼마나 되나"를 1분 안에 보는 용도로만 권한다.

**뺀 것**: jina-embeddings-v3·v5(비상업 라이선스 CC BY-NC 4.0), Qwen3-Embedding-0.6B(bge-m3만큼 무겁다), KoE5·BGE-m3-ko(bge-m3·e5-large 크기 그대로), paraphrase-multilingual-MiniLM-L12-v2(입력 128토큰에서 잘림, 검색용 학습 아님), static-similarity-mrl-multilingual-v1(카드가 "검색용이 아니다"라고 밝힘), gte-multilingual-base(원격 코드 실행 필요, 공식 ONNX 없음, 같은 바탕의 arctic-m-v2.0이 대신함).

  - 처음 불러오기(콜드, 모델 파일이 아직 메모리에 없는 상태) **24.5초**(HISTORY.md의 강의실 PC 준비 기록).
  - 다시 불러오기(웜, 같은 세션에서 앞서 DB를 만들어 Windows 디스크 캐시에 파일이 남은 상태) **3.8초**(2026-10-29 본 측정, 조정자 전달).
  - 질문 하나 임베딩 **약 0.18초**(중앙값, 같은 본 측정).
- 차이 약 21초는 대부분 **디스크에서 2.27GB 파일을 읽는 시간**으로 보인다(추측). 1초에 약 110MB를 읽은 셈이다. 다른 원인(백신 검사, 처음 import 할 때 파이썬 파일 컴파일)도 섞였을 수 있다.
- 도우미는 Blender를 켤 때 함께 켜진다. 그래서 사용자가 겪는 것은 대개 **콜드**다(PC를 켜고 처음 Blender를 열 때). **5-8초 조건은 콜드 기준으로 보는 게 맞다**고 권한다.
- bge-m3 내려받기가 4.3GB였던 이유: 저장소에 PyTorch 파일(2.27GB)과 ONNX 파일(2.27GB)이 둘 다 있다. 실제로 불러오는 것은 그중 하나다([Hugging Face API 파일 목록](https://huggingface.co/api/models/BAAI/bge-m3?blobs=true)).

### 이 PC에서의 시간과 배포 부담(어림)

어림 방법 [어림]:

- 콜드 불러오기 ≈ 라이브러리 불러오기 + 파일 크기 ÷ 약 110MB/초(bge-m3 콜드-웜 차이로 계산한 디스크 속도).
- 라이브러리 불러오기: PyTorch + sentence-transformers는 약 2-3초, onnxruntime + tokenizers는 1초 안쪽으로 가정했다(직접 재지 않음).

설명서 전체 DB 생성 시간(8,997청크, 한 번만) [어림]:

- 기준: bge-m3는 이 PC CPU에서 200청크 원문에 378초였다(HISTORY 기록). 1청크에 약 1.9초다. 같은 속도면 8,997청크에 **약 17,000초, 4-5시간**이다.

| bge-m3 | 약 4-5시간(200청크 실측에서 늘림) |

- ONNX int8로 돌리면 더 줄 수 있지만 얼마나 줄지는 공식 수치가 없다.

배포할 실행 라이브러리 크기 [확인]:

- PyTorch CPU판: 이 PC `.venv`에 설치된 `torch` 폴더가 **552MB**다(직접 잼). PyPI의 Windows 휠(설치 파일)은 127MB다([PyPI torch 2.15.0](https://pypi.org/project/torch/)). 여기에 `transformers` 폴더 120MB(직접 잼)와 sentence-transformers가 더 든다.
- onnxruntime: Windows 휠 **약 15MB**([PyPI onnxruntime 1.31.1](https://pypi.org/project/onnxruntime/)). 글자를 토큰으로 자르는 `tokenizers` 휠은 2.9MB, numpy 휠은 12.6MB다.
- model2vec: 휠 90KB. 필요한 것은 numpy·tokenizers·safetensors 정도다([PyPI model2vec 0.10.0](https://pypi.org/project/model2vec/)).
- → **PyTorch 없이 onnxruntime으로 가면 실행 라이브러리가 약 1/20로 줄고, 콜드 불러오기에서 PyTorch를 불러오는 시간도 빠진다.** 배포까지 생각하면 공식 int8 ONNX가 있는 granite r2가 가장 유리하다.

## 근거

### 1. ibm-granite/granite-embedding-97m-multilingual-r2

## 이 PC에서 재 봐야 할 것

1. **콜드 불러오기**: PC를 다시 켠 직후(또는 Windows 대기 메모리를 비운 뒤) 도우미를 켜는 것과 같은 방식으로 불러오는 시간. 라이브러리 import 시간과 모델 파일 읽기 시간을 나눠 적는다. 웜 불러오기도 따로 적는다.
2. **질문 하나 임베딩 시간**: 기존 20질문을 하나씩, 첫 호출(데움)을 빼고 중앙값과 가장 느린 값. bge-m3 0.18초와 견준다.
3. **정답 적중(가장 중요)**: 기존 search_compare 200청크·20질문으로, 원문(영어) 청크만 임베딩한 조건에서 bge-m3·text-embedding-3-large와 견준다. 질문 뒤 영어 기능 이름을 붙인 경우와 뺀 경우를 함께 본다.
4. **PyTorch판과 ONNX int8판의 차이**: 같은 모델에서 적중이 떨어지지 않는지. 특히 e5-small의 AVX-512 VNNI용 int8 파일을 이 PC(AVX2)에서 쓸 때.
5. **접두어 처리**: e5는 `query: `/`passage: `, EmbeddingGemma는 `task: search result | query: `를 빠뜨리지 않았는지. 빠지면 점수가 낮게 나와 모델 탓으로 잘못 볼 수 있다.
6. 200청크 DB 생성 시간(참고용, bge-m3 CPU 원문 378초와 견줌). 이것으로 8,997청크 전체 시간을 다시 어림한다.

## 못 찾은 것

1. 가벼운 후보들의 **한국어 → 영어** 교차 언어 검색 숫자(MKQA 한국어 같은 것). bge-m3 논문 숫자에는 이 후보들이 없다.
2. XOR-Retrieve 7개 언어에 한국어가 들어 있는지(페이지에 목록이 없었다), EmbeddingGemma의 언어별 XOR 점수.
3. granite r2 논문 본문의 교차 언어 시험 이름·숫자(초록만 읽음).
4. 어느 후보든 CPU 불러오기·질문 임베딩 시간 공식 수치(위 시간은 모두 어림).
5. granite r2의 "MTEB Multilingual Retrieval(18종)"과 EmbeddingGemma 논문 MMTEB Retrieval이 같은 문항 묶음인지.
6. AVX-512 VNNI용 int8 ONNX를 AVX2 CPU에서 돌릴 때 정확도가 얼마나 떨어지는지(onnxruntime 문서를 이번에 열지 못함).
7. EmbeddingGemma 카드에 한국어가 명시돼 있는지(카드 요약에 "100개 넘는 언어"만 나옴).
