## 문서에서 새로 안 것

1. 조작 기록에 남는 조건이 문서에 없다는 점이 확인됐다. 우리가 믿은 "사람 입력만" 또는 "REGISTER 표시"는 둘 다 문서가 아니라 실행 관찰에서 나온 말이고, 자체 자료가 이미 어긋난다: `view3d.select`는 REGISTER가 없는데 기록에 남고(ops.json, HISTORY [53]), `undo=True` 파이썬 호출은 기록에 남는다(142259_h7_cases 42번). 시험 쪽 영향: 26번(조작 기록)과 '직전 조작'을 `bpy.ops.xxx("EXEC_DEFAULT", True, ...)` 한 줄로 만들 수 있다. 가설 7이 "26번 못 만듦"으로 둔 부분이 이것으로 풀린다. 이미 flow_walk.py가 이 방식(`True`)을 쓰고 있다.
2. `Operator.options.is_invoke`가 있다(bpy.types.OperatorOptions.txt: "True when invoked (even if only the execute callbacks available)", `is_repeat`, `is_repeat_last`도 있음). 기록된 조작이 사람이 부른 것인지(invoke) 스크립트가 부른 것인지 가르는 값이다. 애드온이 기록을 읽을 때 쓸 수 있다.
3. 키보드 단축키로 실행하면 항상 `invoke()`를 쓰고 바꿀 수 없다(bpy.types.Operator.txt: "Running an operator via a key shortcut always uses invoke(), and this behavior cannot be changed."). 우리 흐름은 `EXEC_DEFAULT`로 `execute()`만 부르므로 사람의 키보드 경로와 다르다. 모달 시작·기본 속성 채움(invoke가 하는 일) 차이가 생긴다. 사람 입력과 같게 보려면 `INVOKE_DEFAULT`나 `event_simulate`가 필요하다.
4. 모달 조작은 새 이벤트가 올 때만 돈다(Operator.txt: "when no new events are detected, the modal operator will not run"). `event_simulate`로 만든 이벤트가 창 이벤트 큐에서 처리되어야 하고, `WindowManager.is_event_handling_break`("Remaining events in the queue are delayed until the next main loop iteration")가 이벤트가 밀리는 단서가 될 수 있다. 우리는 0.4-0.5초 쉬고 읽었다(sim_cause.py:27). `is_event_handling_break`는 어느 시험도 읽지 않았다.
5. `event_simulate`가 안 되는 까닭의 단서는 문서에 없다. 다만 우리 자료에서 실패한 9개 실행 모두 `"splash": true`(시작 화면 켜짐)였고(144748_h8_sim_cause 0-8.json), HISTORY [157]에서 실제 입력이 되려면 먼저 Esc로 시작 화면을 닫아야 했다. 11-05의 성공은 긴 단계(modules·ops 등) 뒤에 돌아 시작 화면이 닫힌 뒤였을 수 있다(추측: 11-05 실행에서 `show_splash`·시작 화면 상태는 안 남아 있음). 문서 사실이 아니라 이번 자료에서 본 겹침이라, 확인하려면 시작 화면을 닫거나 `show_splash=False`로 한 번 돌려 보면 된다(Blender 실행 필요라 이번에는 안 함).
6. `WindowManager.is_interface_locked`(bpy.types.WindowManager.txt: "If true, the interface is currently locked by a running job and data should not be modified from application timers. Otherwise, the running job might conflict with the handler causing unexpected results or even crashes."). 타이머에서 조작을 부르는 우리 시험 도구 전체에 해당하는 주의다. 렌더·굽기 같은 작업이 도는 상태 시험에서는 이 값을 먼저 확인해야 한다.
7. 호출 규칙: 오류 보고가 하나라도 있으면 `FINISHED`여도 `RuntimeError`가 난다(bpy.ops.txt). 5번 함정. 취소인데 오류 보고가 없으면 예외 없이 `{'CANCELLED'}`다. 즉 "예외 없이 CANCELLED"와 "예외"는 서로 다른 뜻이다.
8. 문맥 덮어쓰기: `context.copy()`를 바탕으로 쓰라고 권한다(bpy.ops.txt "You will nearly always want to use a copy of the actual current context as basis"). 우리는 window·area·region만 주는데, 일부 조작은 다른 멤버를 본다. `override.logging_set(True, hide_missing=True)`로 어떤 멤버를 조작이 읽는지 기록할 수 있다(ContextTempOverride.txt, Context.txt). 죽거나 poll이 거짓인 725개 조작의 까닭을 찾을 때 쓸 수 있는 문서 방법이다. 또 전체 화면·임시 화면으로 바꾸는 `screen=` 덮어쓰기는 지원하지 않는다(Context.txt Note: "Switching to or away from full-screen areas & temporary screens isn't supported").
9. poll 실패 이유를 말해 주는 `poll_message_set`이 있으나 많이 쓰이지 않는다(info_gotchas_operators.txt). 오류 문장에 이유가 있으면 `poll 오류` 기록의 `msg`에 남는다(op_walk.py:261).
10. 화면 캡처: `Window.screenshot(region=...)`이 Blender 안에서 창 픽셀을 RGBA `memoryview`로 돌려준다(bpy.types.Window.txt, PNG 저장 예제 포함). HISTORY [157]이 "화면 내용은 스크린샷으로만 볼 수 있다, 실제 입력은 PC를 차지한다"고 한 부분에서 그림을 뽑는 데는 마우스·키보드를 쓰는 외부 도구가 필요 없을 수 있다. 같은 문서에 `Window.cursor_warp(x, y)`(커서 위치 지정)도 있으나 이벤트 흉내와의 관계는 설명이 없다.
11. 붓질·끌기 입력의 모양: `stroke`는 `OperatorStrokeElement` 모음으로, 원소마다 `location`(3칸), `mouse`·`mouse_event`(2칸), `pressure`, `size`, `time`, `is_start`, `x_tilt`, `y_tilt`가 있다(OperatorStrokeElement.txt). `sculpt.brush_stroke(stroke=..., override_location=...)`는 `mouse_event` 위치에서 물체 공간 위치를 다시 계산하는 옵션이 있다(bpy.ops.sculpt.txt "Override the given "location" array by recalculating object space positions from the provided "mouse_event" positions"). 가설 4-2의 "조각 붓질이 없다"는 한계를 `EXEC_DEFAULT`로 붓질 값을 직접 만들어 채울 길이 문서에 있다는 뜻이다. 우리 ops.json에서 stroke/path/event_history 모음을 가진 조작은 37개다. 실제로 값이 되는지는 안 해 봤다.
12. `bpy.ops.*`로 데이터를 넘기지 못한다는 점(info_gotchas_operators.txt "Can't pass data such as objects, meshes or materials to operate on (operators use the context instead)")과 스레드 금지(info_gotchas_threading.txt "While threads are running, no code ... may use bpy")는 타이머·핸들러 쪽 도구가 지킬 문서 조건이다. 우리 시험 도구의 `depsgraph_update_post` 핸들러(flow_walk.py:35)는 읽기만 하므로 문제 없다. bpy.app.handlers.txt는 "Altering data from handlers should be done carefully"라 한다.
13. 상태 시험 스크립트의 틀린 인자 하나가 문서와 다르다(34번: `paths_calculate`의 인자). 문서 글자판으로 조작 호출 인자를 모두 대조하는 검사를 만들 수 있다(ops.json에 인자 목록이 있고 문서에도 서명이 있으나, 이번에는 하지 않았다).
14. 문서 오류로 보이는 곳: `Window.event_simulate`의 "Returns: Item, Added key map item, Return type: Event"는 설명이 다른 조작의 것을 붙여 넣은 것 같다. 우리는 반환값을 쓰지 않으므로 영향 없음.
