# 질문 바꾸기·HyDE·doc2query·로컬 소형 모델·리랭커 조사

확인한 날짜: 2026-10-30 · 조사: Claude(Opus 5.5) 하위 에이전트 · 모델을 내려받거나 API를 부르거나 실험을 돌리지 않았다. 숫자는 논문 원문(arXiv·ACL Anthology PDF를 직접 읽음)·모델 주인이 쓴 Hugging Face 카드·공식 문서에서 읽은 것과, 그것과 저장소 기록(HISTORY [93]-[120])으로 어림한 것이다. 어림은 따로 표시했다.

**질문.** Blender 5.2 공식 설명서(영어, 8,997청크)에서 초보자의 한국어 자유 질문에 맞는 쪽을 찾을 때, 지금 가장 잘 된 방법은 gpt-6-luna(생각 수준 none)가 질문을 영어 검색어로 바꾼 뒤 text-embedding-3-large로 찾는 것이다(상위 6개 72.5%, 10개 85%, 30개 92.5%, [117]·[120]). 그런데 바꾸기가 중앙 1.50초·최대 3.62초라 "질문 준비 0.5초" 목표와 부딪힌다. 공개 자료로 다음 다섯 가지를 확인한다.

1. 질문 바꾸기(쿼리 재작성)의 효과와 시간을 줄이는 방법
2. HyDE(가짜 답 글을 만들어 그것으로 찾기)
3. doc2query 계열(설명서 쪽마다 예상 질문을 미리 만들어 색인)
4. 강의실 PC(i7-4770, GPU 없음)에서 돌 작은 생성 모델로 luna를 대신할 수 있나
5. 리랭커(찾은 후보를 다시 고르는 단계)

### 처음 나오는 말 풀이

- **질문 바꾸기(쿼리 재작성, query rewriting)**: 사용자 질문을 검색이 잘 되는 다른 글(여기서는 영어 검색어)로 바꾸는 것.
- **질문 늘리기(쿼리 확장, query expansion)**: 질문 뒤에 관련 낱말이나 글을 덧붙여 찾을 거리를 늘리는 것. 질문 바꾸기와 겹친다.
- **HyDE**: 질문에 대한 "그럴듯한 가짜 답 글"을 AI에게 쓰게 하고, 그 글과 비슷한 실제 문서를 찾는 방법.
- **doc2query**: 문서 쪽마다 "이 글로 답할 수 있는 질문"을 미리 만들어 문서와 함께 색인해 두는 방법. 질문할 때는 AI를 부르지 않는다.
- **색인(인덱스)**: 검색하려고 미리 만들어 둔 목록. 우리 경우는 청크마다 계산해 둔 벡터 묶음.
- **BM25**: 질문과 문서에 같은 낱말이 얼마나 겹치는지로 점수를 매기는 오래된 낱말 검색 방법.
- **조밀 검색(dense retrieval)**: 임베딩(글을 숫자 묶음으로 바꾼 것)끼리 가까운 것을 찾는 검색. 우리 large·Gemma 검색이 이것이다.
- **교차 언어 검색(CLIR)**: 질문 언어와 문서 언어가 다른 검색. 우리는 한국어 질문 → 영어 설명서.
- **리랭커(재순위 모델)**: 1차 검색이 낸 후보 수십 개를 질문과 하나씩(또는 한꺼번에) 다시 읽고 순서를 다시 매기는 모델.
- **크로스 인코더**: 질문과 문서 한 쌍을 한 번에 넣어 "얼마나 맞는지" 점수 하나를 내는 리랭커. 쌍마다 계산하므로 후보가 많으면 느리다.
- **LLM 목록 재순위(listwise)**: 큰 언어 모델에게 후보 여러 개를 한꺼번에 보여 주고 순서를 쓰게 하는 방법(RankGPT 등).
- **프롬프트 처리(prefill)와 글 생성(decode)**: 생성 모델이 입력 글을 먼저 한꺼번에 읽는 단계와, 답을 한 토큰씩 쓰는 단계. CPU에서는 앞은 계산 속도, 뒤는 메모리 속도가 주로 막는다.
- **양자화(Q4 등)**: 모델 숫자를 4비트 정도로 줄여 파일과 메모리를 줄이는 것. 대개 빨라지고 품질이 조금 떨어질 수 있다.
- **GGUF·llama.cpp**: CPU에서 생성 모델을 돌리는 오픈소스 프로그램(llama.cpp)과 그 모델 파일 형식(GGUF).
- **증류(distillation)**: 큰 모델이 한 일을 작은 모델이 흉내 내도록 학습시키는 것.
- **평가 부풀림(순환)**: 같은 종류의 AI가 만든 평가 질문과 색인 질문이 서로 닮아, 실제 사용자 질문보다 점수가 높게 나오는 것.

표시: **[확인]** 출처에서 읽은 사실 · **[추측]** 우리 상황에 적용한 판단(검증 안 됨) · **[어림]** 출처 숫자와 저장소 기록으로 계산한 대략값.

## 한 쪽 요약

1. **질문 바꾸기는 공개 연구에서도 큰 모델일수록 효과가 크다.** [확인] query2doc(2023)은 BM25에서 TREC DL19 nDCG@10을 51.2 → 66.2로 올렸지만, 같은 방법을 1.3B 모델로 하면 52.0으로 거의 오르지 않았다([Wang 외 2023](https://arxiv.org/abs/2303.07678) 표 3). [확인] 반대로 질문 바꾸기만 하도록 학습시킨 770M 모델은 ChatGPT 바꾸기보다 나은 경우가 있었다([Ma 외 2023](https://arxiv.org/abs/2305.14283) 표 2). → 작은 모델을 "그냥 지시해서" 쓰면 기능 이름을 끌어내는 힘이 약할 가능성이 크고, 학습시키면 달라질 수 있다.
2. **이미 강한 검색기에는 늘리기가 오히려 해가 되기도 한다.** [확인] 24개 검색 모델을 비교한 연구는 "기준 성능이 높을수록 늘리기 이득이 줄고, 강한 모델에서는 대개 손해"라고 보고했다([Weller 외 2024](https://arxiv.org/abs/2309.08541)). [추측] 우리 한국어 질문 그대로는 large 10%로 "약한" 상황이라 바꾸기 이득이 컸던 것과 맞는다.
3. **HyDE는 바꾸기보다 출력이 길어 더 느릴 것이다.** [확인] HyDE는 한국어 포함 다국어 시험(Mr.TyDi)에서 mContriever 한국어 MRR@100을 22.3 → 30.6으로 올렸지만, 이것은 한국어 질문 → 한국어 문서였다([Gao 외 2023](https://aclanthology.org/2023.acl-long.99/) 표 3). [확인] OpenAI 공식 지연 시간 안내는 "출력 토큰을 반으로 줄이면 지연이 약 반으로 준다, 입력을 반으로 줄이면 1-5%만 준다"고 쓴다([OpenAI 지연 최적화](https://developers.openai.com/api/docs/guides/latency-optimization)). → 가짜 답 글은 지금 검색어(평균 출력 약 54토큰)보다 길어 0.5초 목표에서 더 멀어진다.
4. **doc2query가 0.5초 목표와 가장 잘 맞는다.** [확인] 질문할 때 AI 호출이 없다(색인할 때 한 번 만듦)([Nogueira 외 2019](https://arxiv.org/abs/1904.08375)). 잡음 질문을 걸러 내면 더 좋아졌다(MS MARCO RR@10 0.279 → 0.323)([Gospodinov 외 2023](https://arxiv.org/abs/2301.03266)). 예상 질문을 따로 색인하는 조밀 검색 방식도 보고가 있다(QuOTE, 심사 전 논문). [어림] 8,997청크에 질문 5개씩 만들면 luna 일반 호출로 약 $0.8-1.0, Batch로 약 $0.4-0.5, 만든 질문 임베딩(large) 약 $0.2.
5. **한국어 예상 질문을 영어 문서에 붙이는 연구는 학습 자료 쪽만 찾았다.** [확인] SWIM-IR은 PaLM 2로 영어 위키 문단에 한국어 포함 여러 언어 질문을 만들어 검색기를 학습시켰다([Thakur 외 2024](https://arxiv.org/abs/2311.05800)). 색인에 직접 붙여 쓴 교차 언어 doc2query 실험은 찾지 못했다.
6. **AI가 만든 평가 질문(A문항)은 부풀 수 있다는 근거가 있다.** [확인] LLM이 만든 합성 질문으로 평가하면 모든 시스템 점수가 실제 질문보다 높게 나왔다(순위는 비슷)([Rahmani 외 2024](https://arxiv.org/abs/2405.07767)). [확인] 조밀 검색기·리랭커는 LLM이 쓴 글을 사람 글보다 위로 올리는 경향이 있다([Dai 외 2024](https://arxiv.org/abs/2310.20501)). → doc2query 실험은 W·A를 따로 보고, W를 더 믿어야 한다.
7. **강의실 PC에서 작은 생성 모델이 0.5초 안에 바꾸기를 끝낼 가능성은 낮다.** [확인] i7-4770의 최대 메모리 대역폭은 25.6GB/s다([Intel ARK](https://www.intel.com/content/www/us/en/products/sku/75122/intel-core-i74770-processor-8m-cache-up-to-3-90-ghz/specifications.html)). 이 CPU에서 잰 공식·재현 가능한 llama.cpp 숫자는 찾지 못했다. [어림] 지시문을 미리 계산해 두고(접두어 캐시) 질문 약 50토큰·출력 약 25토큰이면 0.8B급 약 1.5-2초, 2B급 약 4초. 지금처럼 지시문 약 580토큰을 매번 읽으면 0.8B급도 5-10초. → 숫자는 `llama-bench`로 직접 재야 한다.
8. **키워드 뽑기만으로는 질문에 없는 기능 이름이 나오지 않는다.** [추측] 뽑기는 입력 글에서 고르는 일이라 정의상 그렇다. [확인] 작은 모델은 사실 지식이 적다고 모델 주인들이 직접 쓴다(Phi-4-mini 카드: "많은 사실 지식을 저장할 용량이 없다"). [확인] 드문 지식은 모델을 키워도 잘 늘지 않는다([Mallen 외 2023](https://arxiv.org/abs/2212.10511)).
9. **리랭커는 품질 여지가 있지만 강의실 PC CPU에서는 느리다.** [확인] bge-reranker-v2-m3은 bge-m3와 같은 몸통이다([카드](https://huggingface.co/BAAI/bge-reranker-v2-m3)). [어림] 이 PC에서 bge-m3가 200청크에 378초였으므로, 같은 몸통으로 후보 30개를 다시 읽으면 약 20-60초. 영어 전용 MiniLM-L6(22.7M)은 약 1초 안팎으로 어림되지만 영어 검색어만 받는다. [확인] 교차 언어에서는 번역 없이 리랭커를 쓰면 성능이 크게 떨어졌다([Zuo 외 2025](https://arxiv.org/abs/2509.14749)). → 리랭커에는 바꾼 영어 검색어를 넣는 쪽이 맞을 가능성이 크다.
10. **가장 먼저 할 실험은 "번역만" 조건이다.** 지금 72.5%가 언어 바꾸기 효과인지, 기능 이름 연결(Blender를 아는 통역) 효과인지 갈라야 작은 모델·doc2query·HyDE 중 무엇이 맞는지 정할 수 있다. 비용은 1센트 안팎이다.

## 이 프로젝트에 권하는 다음 실험 순서

모두 지금 20문항(W 10·A 10)·같은 채점(상위 4/6/8개, 필요하면 10/20/30개)·회차 3번으로 잴 수 있게 골랐다. 20문항에서 한 문항 차이는 5%p(정답 묶음이 둘이면 2.5%p)이므로, **10%p 안쪽 차이는 우연일 수 있다** [추측]. W와 A를 따로 적는다.

| 순서 | 실험 | 재는 것 | 비용·시간 [어림] | 왜 이 순서인가 |
|---|---|---|---|---|
| 1 | **번역만 조건**: luna(none)에게 "기능 이름을 덧붙이지 말고 질문을 영어로 옮기기만" 시킨 검색어로 large 검색 | 적중률(W/A 따로), 바꾸기 시간 | luna 60번 약 $0.002 + large 질문 임베딩 약 $0.005 | 언어 효과와 "증상 → 기능 이름" 효과를 가른다([118]에서 남은 일). 이 답에 따라 2-5번의 무게가 바뀐다: 번역만으로 70%대면 작은 번역 모델·doc2query 없이도 되고, 30%대면 지식이 핵심이다 |
| 2 | **짧은 바꾸기**: 분야 목록·areas·exclude를 빼고 query만, 20낱말 이하로 | 적중률, 시간 중앙·최대 | 약 $0.003 | 분야 거르기는 효과가 없었고([117]·[119]), 공식 안내상 출력 토큰을 줄이면 지연이 거의 비례해 준다. 지금 출력 평균 약 54토큰(3,243/60) 중 분야 칸 몫을 뺄 수 있다. 다른 더 작은 API 모델이 있으면 같은 조건으로 한 번 |
| 3 | **HyDE식**: luna가 "설명서에 있을 법한 짧은 영어 문단(60낱말 안쪽)"을 쓰고, 검색어 + 문단을 합쳐 검색 | 적중률, 시간 | 약 $0.005-0.01 | 품질 상한을 보려는 것. 출력이 길어 2번보다 느릴 것으로 예상한다. 이득이 작으면 바로 접는다 |
| 4 | **doc2query 시험판**: 200청크 묶음(정답·헷갈릴 청크 포함)에 청크마다 한국어 예상 질문 3-5개를 만들어 따로 색인, 한국어 질문 그대로 large·Gemma로 검색 | 적중률(W/A 따로), 질문 시간(AI 호출 없음) | luna 약 $0.01-0.03 + 임베딩 $0.005 | 질문할 때 AI 호출이 없어 0.5초 목표를 맞출 수 있는 유일한 후보다. 효과가 보이면 설명서 전체(어림 $0.6-1.2, 먼저 사용자 동의)로 넓혀 [117] 전체 조건과 견준다 |
| 5 | **로컬 소형 모델 속도 먼저**: 강의실 PC에서 `llama-bench`로 후보 2-3개의 프롬프트 처리·생성 속도를 재고, 접두어 캐시를 켠 `llama-server`로 20문항 바꾸기 시간 | 시간 중앙·최대, 그다음 적중률 | 무료, 반나절 | 어림으로는 luna(1.5초)보다 빠를 보장이 없다. 속도가 luna보다 나을 때만 품질을 잰다 |
| 6 | **리랭커**: 저장된 luna 검색 결과 상위 30개를 다시 순위 매김. 영어 전용 MiniLM-L6과 다국어 bge-reranker-v2-m3, 넣는 질문은 영어 검색어 / 한국어 원문 | 상위 6개 적중률, 질문당 시간 | 무료(로컬), 반나절 | [93] Q8대로 마지막. 상위 30개 92.5%까지 여지가 있으나 이 PC에서 느릴 것이다 |

덤(새 API 호출 없음): [117]에 이미 저장된 luna 바꾸기 3회차 검색 결과를 순위 합치기(RRF, 여러 순위를 1/(60+순위) 점수로 더하는 방법)로 섞어 보면, "여러 번 바꿔 병렬로 찾기"가 도움이 되는지 공짜로 볼 수 있다. 회차별 상위 6개가 72.5/75/77.5%로 달랐다([117]). 단 운영에서는 호출이 3배가 된다.

## 1. 질문 바꾸기(쿼리 재작성·늘리기)

### 출처에서 확인한 사실

- **query2doc** ([Wang·Yang·Wei, arXiv 2303.07678 v2 2023-10, EMNLP 2023](https://arxiv.org/abs/2303.07678)) [확인]
  - 방법: 예시 4개를 넣은 지시로 LLM이 질문에 대한 가짜 문단을 쓰고, "원래 질문 × 5번 + 가짜 문단"을 새 질문으로 BM25 검색(§3, §4.1).
  - 결과(표 1, text-davinci-003): BM25 MS MARCO dev MRR@10 18.4 → 21.4, TREC DL19 nDCG@10 51.2 → 66.2, DL20 47.7 → 62.9. 조밀 검색기에도 붙였지만 이득이 작아졌다: SimLM DL19 71.4 → 72.9, E5-base+KD 74.3 → 74.9.
  - 모델 크기(표 3, DL19/DL20): BM25 51.2/47.7, babbage(1.3B) 52.0/50.2, curie(6.7B) 55.1/50.1, davinci-001(175B) 63.5/58.2, davinci-003(175B) 66.2/62.9, gpt-4 69.2/64.5. 본문: "작은 모델이 쓴 글은 짧고 사실 오류가 더 많다."
  - 원래 질문을 빼고 가짜 문단만 쓰면 48.7로 BM25(51.2)보다 낮았다(표 4).
  - 시간(표 6, 한 스레드): BM25 색인 검색 16ms, query2doc은 LLM 호출 2000ms 넘음 + 색인 검색 177ms. "실제 배포에서는 이 점을 고려해야 한다"(Limitations).
- **Query Expansion by Prompting LLMs** ([Jagerman 외, arXiv 2305.03653, 2023-05](https://arxiv.org/abs/2305.03653)) [확인]
  - Flan-T5 60M-11B, Flan-UL2 20B로 지시 방식(가짜 문단 Q2D, 낱말 목록 Q2E, 단계별 생각 CoT, 앞서 찾은 문서 3개를 함께 주는 PRF)을 견줬다. BM25만 시험.
  - MS MARCO(표 1): BM25 Recall@1K 87.82·MRR@10 18.77. Flan-UL2 CoT 90.61·20.05, Q2E(낱말 목록) 88.04·18.84. 낱말 목록보다 문단·단계별 생각이 나았다.
  - §5.3: 큰 모델일수록 좋고, 770M에서는 PRF를 함께 준 CoT가 가장 나았다. "큰 모델이 필요하다는 점이 실제 적용을 제한할 수 있다. 증류는 앞으로의 일."
  - §5.2: 과학 분야 자료(trec-covid·scidocs 등)에서는 옛 방식 PRF가 더 나았고, "일반 LLM은 이런 자료에 충분한 분야 지식이 없을 수 있다"고 쓴다.
- **Rewrite-Retrieve-Read** ([Ma 외, arXiv 2305.14283 v3 2023-10, EMNLP 2023](https://arxiv.org/abs/2305.14283)) [확인]
  - 바꾸기 → 검색(Bing) → 읽기 순서. 바꾸는 쪽을 ChatGPT(고정)와, 강화 학습으로 다듬은 T5-large(770M) 두 가지로 견줬다(§4).
  - 표 2(EM): HotpotQA 검색 후 읽기 30.47, ChatGPT 바꾸기 32.80, 학습한 770M 바꾸기 34.38. AmbigNQ 45.80 / 46.40 / 47.80. PopQA 43.20 / 46.00 / 45.72.
  - → 작은 모델이라도 "바꾸기"만 학습시키면 큰 모델 바꾸기와 비슷하거나 나을 수 있다. 다만 영어 질문·웹 검색이다.
- **SoftQE** ([Pimpalkhute 외, arXiv 2402.12663, ECIR 2024](https://arxiv.org/abs/2402.12663)) [확인] LLM이 늘린 질문의 임베딩을 질문 임베딩 모델이 흉내 내도록 학습해, 질문할 때 LLM을 부르지 않는다. BEIR 분야 밖 5개에서 평균 2.83%p 올랐다(초록).
- **늘리기가 언제 실패하나** ([Weller 외, arXiv 2309.08541 v2 2024-02, EACL 2024](https://arxiv.org/abs/2309.08541)) [확인]
  - 늘리기 11가지 × 자료 12개 × 검색 모델 24개. "검색기 성능과 늘리기 이득 사이에 강한 음의 상관." 약한 모델에는 도움, 강한 모델에는 대개 손해.
  - 표 3(TREC DL19, nDCG@10 변화): DPR(기준 38.4) HyDE +18.8, Contriever-FT(62.3) +9.3, MonoT5-3B 리랭커(71.7) −4.0.
  - 권고: 약한 모델이거나, 대상 자료의 모양이 학습 자료와 많이 다를 때만 늘리기를 쓴다.
- **교차 언어에서의 늘리기** [확인]
  - [Macmillan-Scott 외, arXiv 2511.19325(2025-11, 심사 전)](https://arxiv.org/abs/2511.19325): 번역 + 가짜 문단 늘리기, BM25 검색. 언어는 아랍어·독일어·영어·스페인어·프랑스어·힌디어·인도네시아어·이탈리아어·일본어·네덜란드어·포르투갈어·러시아어·베트남어·중국어(표 2·3)로 **한국어는 없다**. 표 4: CLIRMatrix Hit@10 원래 질문 69.35 → Aya Expanse 8B 84.06, Gemma 3 12B 85.12, **Gemma 3 4B 76.98**(세 모델 중 가장 낮음). 질문이 매우 짧은 자료에서 예시를 넣은 지시(few-shot)는 예시 내용이 섞여 들어가는 문제가 있었다(§4.2). 문자가 다른 언어 사이가 특히 나빴다(초록).
  - [Zuo 외, arXiv 2509.14749, Findings of EMNLP 2025](https://arxiv.org/abs/2509.14749): 1차 검색은 다국어 조밀 검색기, 2차는 LLM 리랭커. "번역 없이 최신 리랭커를 교차 언어에 그대로 쓰면 크게 모자란다"(초록). 언어는 유럽 언어(CLEF)와 아프리카 언어(CIRAL)로 한국어는 없다.
- **시간 줄이기 공식 안내** ([OpenAI 지연 최적화](https://developers.openai.com/api/docs/guides/latency-optimization), 2026-10-30 확인) [확인]
  - "더 작은 모델이 대개 더 빠르다." "출력 토큰을 50% 줄이면 지연이 약 50% 줄 수 있다." "프롬프트를 50% 줄여도 1-5%만 나아질 수 있다." 독립된 단계는 병렬로, 스트리밍으로 기다리는 느낌을 줄이기, 고정된 답은 미리 계산하거나 캐시하기.
  - [프롬프트 캐시](https://developers.openai.com/api/docs/guides/prompt-caching): 앞부분이 같은 프롬프트의 입력 처리를 재사용해 시작이 빨라진다. 기본으로 켜져 있다. "GPT-5.6 이후 최소 캐시 길이 1,024토큰."

### 우리 상황에 적용한 추측

- [어림] 지금 luna 바꾸기 한 번은 입력 약 580토큰(34,893/60), 출력 약 54토큰(3,243/60)이다([117]). 입력이 1,024토큰보다 짧아 프롬프트 캐시는 아마 걸리지 않는다. 걸려도 공식 안내상 입력 쪽 이득은 작다.
- [추측] 시간을 줄이는 가장 확실한 손잡이는 **출력 줄이기**다. areas·exclude 칸을 빼고, 검색어 길이를 줄이면 된다. 분야 거르기는 효과가 없었으므로([117]·[119]) 잃는 것도 적다.
- [추측] 예시(few-shot)를 넣으면 입력이 늘어 시간은 조금, 품질은 득실이 섞일 수 있다(예시 내용이 섞이는 문제, 2511.19325 §4.2). 넣는다면 Blender와 무관한 형식 예시 한두 개가 안전하다.
- [추측] query2doc 표 3의 "1.3B는 거의 효과 없음"은 2020년대 초 GPT-3 계열 값이라 지금의 1-2B 모델(Qwen3.5·Kanana-2 등)에 그대로 옮길 수 없다. 방향(작을수록 지식이 모자람)만 참고한다.
- [추측] Weller의 결론에 비추면, 우리 72.5%의 이득은 "약한 상황(한국어 질문 그대로 10%)"이었기 때문일 수 있다. 바꾼 영어 검색어 뒤에 더 많은 글(HyDE)을 붙이면 이득이 작거나 손해일 수 있다. 3번 실험으로 확인한다.

## 2. HyDE

### 출처에서 확인한 사실

- 원 논문: [Gao·Ma·Lin·Callan, "Precise Zero-Shot Dense Retrieval without Relevance Labels", ACL 2023, 1762-1777쪽](https://aclanthology.org/2023.acl-long.99/)(arXiv 2212.10496, 2022-12) [확인]
  - 방법: InstructGPT(text-davinci-003)가 "질문에 답하는 문단을 쓰라"는 지시로 가짜 문서 N개를 쓰고(온도 0.7), Contriever(영어)·mContriever(다국어)로 임베딩해 평균을 낸다. 질문 자체 벡터도 함께 평균할 수 있다(식 8). 가짜 문서의 틀린 세부는 "임베딩이 걸러 준다"고 본다(§3).
  - 표 1(TREC DL19 nDCG@10): BM25 50.6, Contriever 44.5, **HyDE 61.3**, 정답으로 학습한 ContrieverFT 62.1.
  - 표 3(Mr.TyDi MRR@100, 한국어 질문 → 한국어 문서): BM25 28.5, mContriever 22.3, **HyDE 30.6**, mContrieverFT 34.2. 지시는 "한국어로 답하는 문단을 써라"(부록 A.1.8). §4.4: 영어가 아닌 언어는 생성 모델과 임베딩 모델 모두 학습이 덜 되어 차이가 남는다고 추정.
  - 표 4(DL19): 생성 모델을 FLAN-T5 11B로 바꾸면 48.9, Cohere 52B 53.8, GPT 175B 61.3. 작은 생성 모델일수록 이득이 작았다. 이미 학습된 검색기(ContrieverFT)에 약한 생성 모델을 붙이면 조금 나빠졌다.
  - 시간·비용 숫자는 논문에 없다. 공식 코드 저장소 [texttron/hyde](https://github.com/texttron/hyde) README에도 없다.
- 후속 비교 [확인]
  - Weller 외 2024 표 3: HyDE는 약한 DPR에 +18.8, MonoT5-3B 리랭커에는 −4.0(DL19).
  - QuOTE([Neeser 외, arXiv 2502.10976, 2025-02, 심사 전](https://arxiv.org/html/2502.10976v1)) 표 6·7: SQuAD에서 HyDE 상위 1개 76.60%로 그냥 청크 임베딩(79.31%)보다 낮았다. 질문 923개 전체 시간은 그냥 99.97초, HyDE 1176.20초. 본문은 HyDE가 질문마다 1-2초를 더한다고 쓴다.

### 우리 상황에 적용한 추측

- [추측] 우리 경우 HyDE는 "한국어 질문 → 영어 가짜 설명서 문단"이 된다. 이런 교차 언어 HyDE를 한국어로 잰 1차 자료는 찾지 못했다(HyDE 논문의 한국어 시험은 한국어 → 한국어).
- [추측] 가짜 문단은 지금 검색어보다 출력이 길어 시간이 늘어난다. 60낱말 문단이면 출력 약 80-100토큰으로, 공식 안내의 "출력에 비례"를 그대로 적용하면 지금 바꾸기(출력 약 54토큰)의 1.5-2배 시간이다 [어림].
- [추측] HyDE가 질문 바꾸기보다 나을 여지는 "설명서 문체를 흉내 낸 글이 설명서 청크와 더 가깝다"는 점이다. 반면 버전이 바뀐 기능·드문 기능(W6·W9)에서는 틀린 내용을 길게 지어낼 수 있다. 품질 상한을 보는 실험으로만 권한다.

## 3. doc2query 계열(예상 질문을 미리 만들어 색인)

### 출처에서 확인한 사실

- **doc2query** ([Nogueira·Yang·Lin·Cho, arXiv 1904.08375, 2019](https://arxiv.org/abs/1904.08375)) [확인] 문단마다 질문 10개를 표본 추출로 만들어 문단 뒤에 붙이고 BM25로 검색. 표 1: MS MARCO dev MRR@10 18.4 → 21.5, 검색 시간 50 → 90ms/질문.
- **docTTTTTquery**(T5-base) ([castorini/docTTTTTquery README](https://github.com/castorini/docTTTTTquery)) [확인] 리더보드(2019-11-30) MRR@10 BM25 18.6 → 27.2, 지연 55 → 64ms. 문단마다 질문 80개를 공개했고 실제로는 앞 40개만 쓴다("80개의 이득은 아주 작다"). 880만 문단에 질문 1개씩 만드는 데 선점형 TPU로 약 8시간·약 $20. T5-large로 해도 "더 낫지 않았다".
- **Doc2Query--** ([Gospodinov·MacAvaney·Macdonald, arXiv 2301.03266, ECIR 2023](https://arxiv.org/abs/2301.03266)) [확인] 만든 질문 중 문단과 관계가 약한(지어낸) 것을 관련도 모델로 걸러 낸다. 표 1: n=80 RR@10(dev) 0.279 → ELECTRA로 상위 30%만 남기면 0.323(+16%), 색인 1.41 → 0.95GB, 질문당 30 → 23ms. 생성 확률로 거르는 방법은 효과가 없었다(§4).
- **InPars** ([Bonifacio 외, arXiv 2202.05144, 2022](https://arxiv.org/abs/2202.05144)) [확인] GPT-3 Curie에게 예시 몇 개로 문서 10만 개에 질문을 만들게 하고, 확률 상위 1만 쌍으로 리랭커를 학습. → 색인용이 아니라 학습 자료용이다.
- **Promptagator** ([Dai 외, arXiv 2209.11755, 2022](https://arxiv.org/abs/2209.11755)) [확인] FLAN 137B에 예시 8개 이하로 과제별 질문을 만들고, "만든 질문으로 원래 문서가 다시 찾아지는가"(왕복 일관성)로 걸러 검색기를 학습.
- **다국어 doc2query** [확인]
  - [doc2query/msmarco-14langs-mt5-base-v1](https://huggingface.co/doc2query/msmarco-14langs-mt5-base-v1)(Apache-2.0): mT5-base를 mMARCO 14개 언어로 학습, 입력과 같은 언어로 질문을 만든다. 입력 320 낱말 조각에서 자른다.
  - mMARCO는 MS MARCO를 13개 언어로 번역한 자료이고([Bonifacio 외, arXiv 2108.13897](https://arxiv.org/abs/2108.13897) 표 2), 언어 목록에 **한국어가 없다**. 따라서 이 모델은 한국어 질문 생성용으로 학습되지 않았다.
  - SWIM-IR([Thakur 외, NAACL 2024](https://arxiv.org/abs/2311.05800)): PaLM 2가 영어 위키 문단을 읽고 다른 언어 질문을 만든 2,800만 쌍(표 1, L→EN 포함). 시험 자료 XOR-Retrieve(L→영어) 7개 언어에 **한국어가 있다**(표 2). 이것으로 학습한 검색기는 사람이 만든 자료로 학습한 mContriever-X와 견줄 만했다(초록). 비용: "당시 PaLM 2는 1,000글자에 약 0.0005달러"(§ 비용).
- **조밀 검색에서 예상 질문 따로 색인** [확인]
  - QuOTE([arXiv 2502.10976, 2025-02, 심사 전](https://arxiv.org/html/2502.10976v1)): 청크마다 질문 1-30개(10-15개가 알맞다고 봄)를 만들어 따로 임베딩하고, 찾은 뒤 원래 청크로 묶어 중복을 뺀다. 표 6: SQuAD 상위 1개 79.31 → 90.03%, NQ 32.92 → 38.00%. 표 7: 색인 시간 10.36 → 170.32초, 질문 시간 99.97 → 130.56초(923개). 주의: 같은 논문 안에서 기준값이 표마다 다르다(SQuAD 상위 1개 66.60·67.11·79.31·82.58%).
  - HyPE([Vake 외, arXiv 2607.29402](https://arxiv.org/abs/2607.29402)): 같은 생각(질문 대 질문 맞추기). 초록에 맥락 정밀도 최대 +42%p. arXiv 등록은 2026-07인데 저널 표시는 IEEE Access 2025로 날짜가 어긋난다. 본문은 읽지 않았다.
- **평가 부풀림·순환** [확인]
  - [Rahmani 외, "Synthetic Test Collections for Retrieval Evaluation", SIGIR 2024](https://arxiv.org/abs/2405.07767): T5·GPT-4로 만든 합성 질문으로 TREC DL 2023 시스템 순위를 매기면 실제 질문 순위와 비슷했다(Kendall τ 0.8151). 그러나 "모든 종류의 시스템이 합성 질문에서 실제 질문보다 일관되게 높은 점수를 받았다 — 합성 질문이 더 쉽고 성능을 과대평가하는 경향"(§3). 같은 LLM 기반 시스템을 특별히 편드는 뚜렷한 증거는 없었다(자료 하나뿐이라는 단서).
  - [Dai 외, "Neural Retrievers are Biased Towards LLM-Generated Content", KDD 2024](https://arxiv.org/abs/2310.20501): 조밀 검색기와 리랭커가 같은 내용이면 LLM이 쓴 글을 사람 글보다 위에 놓는다("source bias"). LLM 글은 "뜻이 더 모이고 잡음이 적어" 맞추기 쉽다고 분석(초록).

### 8,997청크에 만들 때 비용 어림 [어림]

방법만 적는다. API를 부르지 않았다.

- 바탕 숫자(저장소): 8,997청크의 OpenAI 임베딩 토큰 합 972,115(평균 약 108토큰, HISTORY [106]), luna 가격 입력 $0.10·출력 $0.50/백만 토큰, Batch는 반값(`.scratch/mvp-roundtrip/research/31-번역-모델-조사.md`가 공식 가격 쪽에서 확인), large $0.13/백만 토큰(`manual_vectors.py`).
- 가정: 지시문 약 250토큰, 쪽 경로 약 20토큰, 청크마다 한국어 질문 5개 × 약 30토큰 = 출력 약 150토큰. 한국어 토큰 수는 토크나이저에 따라 달라 ±50%로 본다.
- 청크 1개씩 부를 때: 입력 ≈ 8,997 × (250 + 108 + 20) ≈ 340만, 출력 ≈ 135만 → $0.34 + $0.68 ≈ **$1.0**. Batch면 **약 $0.5**.
- 청크 5개씩 묶어 부를 때: 지시문 몫이 1/5로 줄어 입력 ≈ 160만 → 약 $0.84, Batch 약 $0.42.
- 만든 질문 임베딩: 약 45,000개 × 30토큰 ≈ 135만 토큰 → large **약 $0.18**. Gemma로 로컬 임베딩하면 무료, 시간은 전체 DB(약 97만 토큰) 2,062초에서 늘려 약 50분.
- 합계: **약 $0.6-1.2**. 생성 시간은 하나씩 순서대로면 1.5-3초 × 8,997 ≈ 4-7시간, Batch는 즉시 응답이 아니다(처리 기한은 이번에 확인 안 함).
- 200청크 시험판은 위의 약 1/45로 $0.02-0.03.

### 우리 상황에 적용한 추측

- [추측] doc2query는 질문할 때 AI를 부르지 않으므로 질문 준비 시간이 "질문 임베딩 + 비교"뿐이다. 지금 기록으로 large 중앙 0.221초, Gemma 0.095초([119]). **0.5초 목표 안에 드는 유일한 후보**다.
- [추측] 한국어 예상 질문을 만들면 한국어 질문 ↔ 한국어 예상 질문 비교가 되어, 언어 차이와 "증상 말투 ↔ 기능 이름" 차이를 색인할 때 한 번에 메운다. 이때 Gemma의 한국어 강점([119] 질문 그대로 27.5% vs large 10%)이 살아날 수 있다. 그러면 [120]에서 Gemma를 접은 이유(바꾸기에 유료 luna 필요)가 사라진다.
- [추측] 위험 1(지식): 예상 질문을 만드는 모델도 청크를 보고 "초보자가 이 기능을 모를 때 어떻게 물을지"를 상상해야 한다. 청크에 증상 말이 없으면 기능 이름을 그대로 쓴 질문만 나올 수 있다. 지시에 "기능 이름을 모르는 사람이 증상으로 묻는 말"을 명시해야 한다.
- [추측] 위험 2(부풀림): A문항은 Claude가 정답 쪽을 염두에 두고 쓴 질문이다([96]). AI가 청크를 보고 만든 예상 질문과 말투·내용이 닮기 쉬워, A문항 점수가 W문항보다 더 오를 수 있다. Rahmani 2024의 "합성 질문이 더 쉽다"와 Dai 2024의 "LLM 글 선호"가 이 방향을 뒷받침한다. 줄이는 방법: ① W·A를 따로 적고 W를 판단 기준으로, ② 예상 질문 생성기는 A문항을 쓴 Claude와 다른 계열(luna)로, ③ A문항마다 가장 가까운 예상 질문과의 유사도를 함께 남겨 "거의 같은 문장"이 있는지 본다, ④ 마지막 확인용 질문(티켓 34)은 사람이 쓴 질문으로 분야를 넓힌다([118]).
- [추측] Doc2Query--처럼 거르기를 넣을 수 있다: 만든 질문으로 검색했을 때 원래 청크가 상위 k 안에 오지 않으면 버린다(Promptagator의 왕복 일관성). 처음 시험판에서는 거르지 않은 것과 거른 것을 둘 다 재 볼 만하다.
- [추측] 색인 방식은 QuOTE처럼 "예상 질문마다 따로 벡터 + 청크로 묶어 중복 제거"가 우리 numpy 전수 비교에 그대로 맞는다. 청크 벡터와 질문 벡터 점수 중 큰 값을 쓰는 방식도 같이 볼 수 있다.

### 우리 상황에 적용한 추측과 어림

[어림] 방법(공식 숫자 아님. 2-3배 틀릴 수 있다):

- 글 생성 속도의 위 한계 ≈ 메모리 대역폭 ÷ 토큰마다 읽는 모델 크기. Q4 양자화를 매개변수당 약 0.6바이트로 보면: 0.8B ≈ 0.5GB → 초당 최대 약 50토큰, 1.3B ≈ 0.8GB → 약 32, 2B ≈ 1.3GB → 약 20, 3.8B ≈ 2.3GB → 약 11. 실제로는 이 값의 50-70%로 본다.
- 프롬프트 처리는 계산이 막는다. 필요한 계산 ≈ 2 × 매개변수 × 입력 토큰. 이 PC의 실효 계산 속도는 EmbeddingGemma가 설명서 전체(약 97만 토큰)를 2,062초에 임베딩한 기록([117])에서 거꾸로 어림해 약 100 GFLOPS(초당 1,000억 번)로 둔다(EmbeddingGemma의 임베딩 표를 뺀 매개변수를 약 1억 개로 가정, 확인 안 함). llama.cpp의 양자화 계산은 이보다 빠를 수도 느릴 수도 있다.

| 지금 같은 지시문 약 580토큰을 매번 처리 | 약 9초 + 생성 | 약 15초 + 생성 | 약 23초 + 생성 | 약 45초 + 생성 |

- [추측] 지시문 캐시를 켜도 0.8B급이 luna 중앙 1.50초와 비슷하고, 0.5초 목표에는 못 미칠 가능성이 크다. 2B 넘는 모델은 luna보다 느릴 가능성이 크다. 대신 인터넷·비용이 들지 않고 최대 시간이 고르게 나올 수 있다.
- [추측] 처음 불러오기: 0.5-1.5GB 파일은 이 PC 디스크 읽기 어림(약 110MB/초, 2026-10-29 조사)으로 5-14초. 도우미가 켜 둔 채 쓰므로 한 번만 든다.
- [추측] Qwen3.5(Gated DeltaNet)·Gemma 4(층마다 임베딩) 같은 새 구조는 llama.cpp가 지원하는지, 지원해도 CPU 경로가 빠른지 확인하지 않았다. 재기 전에 llama.cpp 지원 목록부터 본다.
- [추측] 라이선스로 보면 공개 배포에 부담이 적은 것은 Qwen3.5(Apache-2.0)·Gemma 4(Apache-2.0)·Phi-4-mini(MIT)다. EXAONE 4.0은 NC라 배포가 막힐 수 있고, Kanana-2는 표시 의무가 있다. Llama 3.2는 한국어를 공식 지원하지 않는다. Gemma 3 1B는 다국어 점수가 무작위 수준이라 뺀다.

**재는 방법(권함)**: 강의실 PC, Blender 기본 장면 대기 상태([111]과 같게).

1. 후보 2-3개(예: Qwen3.5-0.8B, Kanana-2-1.3B-Instruct, Qwen3.5-2B 또는 Gemma 4 E2B)의 공식 또는 널리 쓰는 Q4_K_M GGUF를 받는다.
2. `llama-bench -t 4 -p 64,512 -n 32 -r 5 -o json`으로 프롬프트 처리·생성 속도를 잰다(스레드 4·8도 비교).
3. `llama-server`를 켜 두고 짧은 지시문(고정) + 20문항 × 3회를 보내 질문마다 시작부터 끝까지 시간을 잰다. 첫 요청(캐시 데움)은 따로 적는다.
4. 시간 중앙값이 luna(1.50초)보다 낫거나 비슷할 때만 그 검색어로 적중률을 잰다.

### 키워드 뽑기만으로 되나

- [추측] "질문에서 키워드를 뽑는 것"은 입력 글에 있는 낱말을 고르는 일이라, 질문에 없는 기능 이름(A9 "상자로 감싸 찌그러뜨리기" → Lattice)을 만들어 낼 수 없다. 뽑은 낱말을 사전으로 영어로 바꾸면 [113]의 메뉴 이름 덧붙이기와 같은 일이 되고, 그때 일상어가 엉뚱한 영어(Make·Floor·Wrap)로 붙어 손해였다.
- [추측] 작은 "생성" 모델은 기능 이름을 지어 낼 수는 있지만, 위 출처들(작은 모델의 사실 지식 부족, 드문 지식은 키워도 잘 안 늚)에 비추면 흔한 기능(Bevel·Mirror)보다 드문 기능(Lattice·Axis Locking·Displace)에서 먼저 틀릴 것이다. 실제로 그런지는 1번 "번역만" 실험과 5번 실험에서 증상형 문항(A1·A9·A10·W9 등)을 따로 보면 알 수 있다.
- [추측] 작은 모델에게 기능 이름 연결을 맡기기보다 "번역만" 시키고, 기능 이름 연결은 doc2query 색인이 맡는 조합도 생각할 수 있다. 1번 실험 결과가 이 조합의 의미를 정한다.

### 이 PC 비용 어림 [어림]

- 바탕: 후보 30개 × (영어 검색어 약 30 + 청크 평균 약 108 + 특수 토큰) ≈ 쌍마다 약 150토큰 → 질문 하나에 약 4,500토큰(상위 20개면 약 3,000).
- 앵커 1(직접 측정): 강의실 PC에서 bge-m3로 200청크 원문 DB를 만드는 데 378초, 청크당 약 1.9초(HISTORY [100]). bge-reranker-v2-m3은 같은 몸통이라 쌍 하나 ≈ 청크 하나로 보면 30쌍 약 57초. 200청크 묶음의 청크는 전체 평균보다 길었을 수 있어(e5가 200개 중 9개를 512토큰에서 자름, [111]) 이것은 위쪽 값이다.
- 앵커 2(계산량): 2 × 임베딩 표를 뺀 매개변수 × 토큰 ÷ 약 100 GFLOPS. bge-m3 몸통은 임베딩 뺀 303M(2026-10-29 조사, arctic-m-v2.0 카드 표)이라 약 27초.

## 출처가 오래됐거나 숫자가 서로 다른 것

- **오래된 모델**: query2doc(text-davinci-003, babbage·curie), HyDE(text-davinci-003, Contriever), InPars(GPT-3 Curie), Promptagator(FLAN 137B), RankGPT(gpt-3.5·gpt-4 2023)의 생성 모델은 지금 쓰지 않는 2020-2023년 모델이다. 방향만 참고하고 숫자를 지금 모델에 옮기지 않는다.
- **BM25 기준값이 출처마다 다르다**: MS MARCO dev MRR@10 18.4(doc2query·query2doc), 0.185(Doc2Query--), 18.77(Jagerman, Terrier BM25), 리더보드 18.6(docTTTTTquery README). TREC DL19 nDCG@10은 51.2(query2doc 재현), 50.6(HyDE), 50.58(RankGPT). 구현·설정 차이다.
- **docTTTTTquery**: dev 27.7(query2doc 표 1)·0.2768(Anserini 재현, README)·0.277(Doc2Query-- n=40), 리더보드(평가 세트) 27.2. 세트가 다르다.
- **bge-reranker-v2-m3 vs jina v2**: Jina 카드는 BEIR에서 bge가 조금 높고(53.65 vs 53.17) MKQA에서 jina가 높다. Qwen 카드는 MMTEB-R에서 jina 63.73, bge 58.36. 두 표 모두 경쟁사가 잰 값이고 시험이 다르다.
- **QuOTE**: 같은 논문 안에서 기준값이 표마다 다르다(위 3절). 심사 전 논문.
- **HyPE**: arXiv 등록 2026-07, 저널 표시 IEEE Access 2025로 날짜가 어긋난다.
- **크기 표시가 엇갈린 카드**: Kanana-2-1.3B(제목 1.3B, 메타데이터 1B), Qwen3.5-0.8B(본문 0.8B, 파일 0.9B), Phi-4-mini(본문 3.8B·옆 표시 4B, "24개 언어"라면서 목록은 23개), Gemma 4 E2B(실효 2.3B, 임베딩 포함 5.1B).
- **한국어 점수**: Kanana 카드(CoT, 탐욕 해독)와 EXAONE 카드(생각 켬/끔)의 KMMLU 계열 값은 조건이 달라 표끼리 견주지 않는다.
- 2026-10-29 조사의 "XOR-Retrieve에 한국어가 있는지 확인 못 함"은 이번에 SWIM-IR 논문 표 2에서 **한국어가 있다**고 확인했다.

## 확인하지 못한 것·남은 질문

1. 한국어 질문 → 영어 문서에서 HyDE·질문 바꾸기·doc2query를 견준 1차 자료(찾은 교차 언어 연구는 한국어가 없거나, 학습 자료 생성용이었다).
2. 예상 질문을 다른 언어로 만들어 색인에 직접 붙이는 교차 언어 doc2query 실험.

4. Qwen3.5·Gemma 4의 llama.cpp CPU 지원과 속도. Gemma 4 카드의 한국어 지원 명시.

8. gpt-6-luna보다 작은·빠른 OpenAI 모델이 지금 있는지, OpenAI Batch의 처리 기한(이번에 확인 안 함).
